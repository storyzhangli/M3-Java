# 费曼口述：为什么不能只按字符暴力切分
说话人1: 费曼口述，为什么不能只按字符暴力切分，共七十道关键问题，由浅入深分七个阶段，从文本切分的基本认知、字符暴力切分的主要问题、语义边界与上下文完整性、常见切分策略与适用场景、Chunk Size/Overlap 与 Token 限制、Spring AI 1.1.8 与 Java 工程实现，到生产级 RAG 质量评估，技术基线为 Java 21、Spring Boot 3.5.x、Spring AI 1.1.8，以生产级 RAG 文档处理与知识库构建为背景。

## 一、文本切分的基本认知
说话人1: 问题一，什么是文本分块（Chunking）？为什么 RAG 需要将长文档切分成多个 Chunk？
说话人1: 答，分块就是把长文档切成一小块一小块。为什么要切？因为整篇文档太长，Embedding 模型吃不下，检索也不精准。切成小块，语义集中，检索准，也方便拼上下文。

说话人1: 问题二，什么是固定长度切分？它与按段落、按标题和语义切分有什么区别？
说话人1: 答，固定长度切分：按字符数或者 Token 数硬切，不管语义。按段落切：按自然段落切。按标题切：按章节层级切。语义切：按意思是否完整切。一个是硬切，一个是看结构和语义。

说话人1: 问题三，为什么字符数量不等于 Token 数量？
说话人1: 答，因为 Token 是模型分词的单位。中文一个字大概 1 到 2 个 Token，英文一个单词可能一个 Token。字符数和 Token 数不是线性关系。

说话人1: 问题四，中文、英文、数字、代码和表格在 Token 数量上有什么差异？
说话人1: 答，中文一个字约 1.5 Token。英文一个单词约 1 Token。数字和代码符号，Token 密度更高。表格里的结构符号，也占 Token。

说话人1: 问题五，为什么相同字符长度的两段文本，实际 Token 数量可能不同？
说话人1: 答，因为中文和英文的 Token 换算不一样。都是 1000 个字符，中文可能 1500 Token，英文可能 800 Token。

说话人1: 问题六，什么是 Chunk Size？它应该按照字符数、Token 数还是其他指标定义？
说话人1: 答，Chunk Size 是每个块的大小。应该按 Token 数定义，因为 Embedding 模型和 LLM 都是按 Token 算的。按字符数不准。

说话人1: 问题七，什么是 Chunk Overlap？它主要解决什么问题？
说话人1: 答，Overlap 是相邻两块重叠的部分。解决的问题是：不要把一个完整的意思从中间切开，上下文断了。

说话人1: 问题八，为什么文本切分不仅是长度控制问题，也是语义完整性问题？
说话人1: 答，因为切的目的是检索。你切出来的块，语义要完整。不然检索到了，也是不完整的信息，模型用不了。

说话人1: 问题九，文档解析质量、文本清洗质量与 Chunk 质量之间有什么关系？
说话人1: 答，解析是第一步。解析错了，文本顺序乱了、丢了，切出来的 Chunk 也好不了。垃圾进垃圾出。

说话人1: 问题十，为什么不能认为 Chunk 越小，检索效果就一定越好？
说话人1: 答，因为太小了，语义不完整。一个 Chunk 只有半句话，Embedding 出来的向量表达的意思也不完整。检索不准。

## 二、字符暴力切分的主要问题
说话人1: 问题十一，什么是字符暴力切分？它通常采用什么实现方式？
说话人1: 答，就是硬切。比如 substring(text, 0, 500)，每 500 个字符切一刀。不管中间是什么内容。

说话人1: 问题十二，如果直接使用 Java substring() 按固定字符数切分，会产生哪些问题？
说话人1: 答，会把句子从中间切开，把段落拆开，把表格切两半。语义断了。

说话人1: 问题十三，为什么固定字符长度可能把一个完整句子从中间截断？
说话人1: 答，因为刚好切在句子中间。比如一个句子 600 字，Chunk Size 500，那第 500 字就把句子砍断了。

说话人1: 问题十四，为什么暴力切分可能破坏段落之间的逻辑关系？
说话人1: 答，段落是有逻辑的，前一段和后一段有关系。硬切可能把两段拆开，各自成一个 Chunk，逻辑就断了。

说话人1: 问题十五，为什么标题、正文和下级标题可能被拆分到不同 Chunk？
说话人1: 答，因为标题在前面，正文在后面。硬切的时候，刚好切在标题和正文之间。标题一个块，正文一个块。正文不知道自己讲的什么主题。

说话人1: 问题十六，为什么一个完整的技术定义可能被切成两个无法独立理解的片段？
说话人1: 答，比如"故障 E102 是指..."后面是定义。硬切可能把"故障 E102"切在前面的块，定义切在后面的块。每个块单独看，都不完整。

说话人1: 问题十七，如果切分位置落在 Markdown 表格中间，会对检索产生什么影响？
说话人1: 答，表格被切成两半。表头在一块，数据行在另一块。检索的时候，可能只召回数据行，没有表头。你看到数据，但不知道这是什么参数。

说话人1: 问题十八，如果切分位置落在 Java 代码块中间，会造成哪些问题？
说话人1: 答，代码被切两半。一半代码，语法都不完整。检索到了，也没法用。

说话人1: 问题十九，为什么 PDF 解析后的跨页内容尤其容易出现上下文断裂？
说话人1: 答，PDF 每页是分开的。跨页的内容，刚好在页尾和页首。暴力切分就把跨页的内容拆开了。

说话人1: 问题二十，如果设备型号、故障代码和故障处理步骤被分到不同 Chunk，会影响什么业务结果？
说话人1: 答，用户问"E102 怎么处理"。检索可能只召回故障代码那块，没有处理步骤。或者只召回步骤，不知道是哪个故障的。答案就不完整。

说话人1: 问题二十一，为什么字符暴力切分可能导致 Chunk 包含大量无意义的上下文？
说话人1: 答，因为硬切，一个 Chunk 里可能混了好几个不相关的段落。前面讲 A，后面讲 B。语义不集中。

说话人1: 问题二十二，如果 Chunk 切得过大，会对 Embedding、检索和 LLM 上下文产生什么影响？
说话人1: 答，Chunk 太大，Embedding 语义不集中，检索不准。拼到 Prompt 里，占 Token 多，成本高。

说话人1: 问题二十三，如果 Chunk 切得过小，会增加哪些检索和工程成本？
说话人1: 答，Chunk 小，数量多，向量数据库存的多。检索的时候要多召回几个，才能凑够上下文。

## 三、语义边界与上下文完整性
说话人1: 问题二十四，什么是语义边界？为什么句子、段落和章节通常是重要的切分边界？
说话人1: 答，语义边界就是意思完整的地方。句子是最小的完整意思。段落是一个小主题。章节是一个大主题。这些地方切，语义不会断。

说话人1: 问题二十五，为什么完整的语义单元比单纯满足字符长度更重要？
说话人1: 答，因为切的目的是让每个 Chunk 能独立表达一个完整意思。长度只是参考，语义完整才是目的。

说话人1: 问题二十六，如何判断一段文本是否适合独立成为一个 Chunk？
说话人1: 答，看这段文本单独拿出来，能不能看懂。有没有前因后果。缺不缺上下文。

说话人1: 问题二十七，为什么标题应该尽量与对应正文保持关联？
说话人1: 答，标题是正文的概括。Chunk 里有标题，你就知道这段讲的什么。没有标题，正文就是一段孤立的文字。

说话人1: 问题二十八，如何处理跨段落的因果关系、条件关系和步骤关系？
说话人1: 答，这些关系强的段落，尽量放在同一个 Chunk 里。不要拆开。

说话人1: 问题二十九，为什么需要保留文档标题、章节路径和来源信息？
说话人1: 答，这些是上下文。Chunk 里带上文档标题和章节路径，就知道这段内容出自哪里，主题是什么。

说话人1: 问题三十，如何避免 Chunk 只保留结论，却丢失结论成立的条件？
说话人1: 答，切的时候，把条件和结论放在一起。不要只切结论那一段。

说话人1: 问题三十一，什么是上下文丢失？它会如何影响 Embedding 表示和向量检索？
说话人1: 答，上下文丢失就是 Chunk 里只有部分内容，缺少背景。Embedding 出来的向量，语义就不完整。检索的时候，就不准。

说话人1: 问题三十二，为什么在 Chunk 中补充文档标题或章节路径，有助于恢复上下文？
说话人1: 答，因为标题告诉你这段内容的主题。加上标题，Chunk 的语义就完整多了。

说话人1: 问题三十三，如何处理跨 Chunk 的连续步骤、长列表和多级编号？
说话人1: 答，连续步骤尽量放一起。长列表太长的，拆的时候要注意，保持编号连续。

说话人1: 问题三十四，如果一个段落本身超过最大 Token 限制，应该如何进一步切分？
说话人1: 答，先按段落切，段落太大了，再按句子切。句子还大，再硬切。递归式的切。

## 四、常见切分策略与适用场景
说话人1: 问题三十五，固定长度切分适合什么类型的文档？它的局限性是什么？
说话人1: 答，适合结构简单、纯文本的文档。局限性：破坏语义，不适合结构化文档。

说话人1: 问题三十六，按句子切分如何避免破坏句子完整性？
说话人1: 答，以句号、问号、感叹号为分界。在句子之间切，不要从句子中间切。

说话人1: 问题三十七，按段落切分如何保留自然文本的语义结构？
说话人1: 答，段落本身就是自然的语义单元。按段落切，一个段落一个主题。

说话人1: 问题三十八，按标题层级切分如何处理 Markdown 文档？
说话人1: 答，按 # 标题分级。每个标题下面的内容，作为一个 Chunk。标题和正文在一起。

说话人1: 问题三十九，递归字符切分（Recursive Character Splitting）与直接字符暴力切分有什么区别？
说话人1: 答，暴力切是硬切。递归切是：先尝试按段落切，段落太大了，再按句子切，句子还大，再按字符切。一层一层试，尽量保持语义完整。

说话人1: 问题四十，递归切分为什么通常会优先尝试段落、换行、句子等分隔符？
说话人1: 答，因为这些是自然的语义边界。优先在这些地方切，尽量不破坏句子。

说话人1: 问题四十一，语义切分（Semantic Chunking）如何判断相邻文本是否属于同一语义单元？
说话人1: 答，用 Embedding 算相邻句子的相似度。相似度高，说明是同一个主题，放一起。相似度低，就是边界。

说话人1: 问题四十二，语义切分是否一定比递归切分效果好？它有哪些额外成本？
说话人1: 答，不一定。语义切分效果可能好，但成本高，因为每段都要算 Embedding。慢，贵。

说话人1: 问题四十三，不同格式的文档为什么需要采用不同的切分策略？
说话人1: 答，因为每种文档结构不一样。Markdown 有标题层级。PDF 有分栏。代码有代码块。不能一套策略打天下。

说话人1: 问题四十四，PDF、Word、Markdown、HTML 和代码文件分别应该重点考虑哪些结构信息？
说话人1: 答，PDF：分栏、页码、表格。Word：样式、标题层级。Markdown：标题、代码块。HTML：正文和导航分开。代码：函数、类。

## 五、Chunk Size、Overlap 与 Token 限制
说话人1: 问题四十五，Chunk Size 如何影响 Embedding 模型的输入长度和语义表达？
说话人1: 答，Chunk 太大，Embedding 输入超了。太小，语义不完整。要在中间找平衡。

说话人1: 问题四十六，Chunk Size 如何影响向量检索的召回率与精确率？
说话人1: 答，太大，语义不集中，精确率低。太小，信息不完整，召回率低。

说话人1: 问题四十七，Overlap 过小可能导致什么问题？过大又会产生什么副作用？
说话人1: 答，过小：上下文断了。过大：重复内容多，成本高，向量库冗余。

说话人1: 问题四十八，为什么 Overlap 会增加重复文本、Embedding 费用和向量存储量？
说话人1: 答，因为重叠的部分，被 Embedding 了两次。占更多存储，花更多钱。

说话人1: 问题四十九，如何根据 Embedding 模型的最大输入 Token 限制确定 Chunk Size？
说话人1: 答，Chunk Size 要小于模型最大输入。比如模型最大 8192 Token，Chunk Size 设成 512 或者 1024。留余量。

说话人1: 问题五十，为什么必须为模型输入预留 Token 余量，而不能直接使用最大限制？
说话人1: 答，因为实际文本 Token 数是估算的，可能不准。留余量，防止超了。

说话人1: 问题五十一，如何同时考虑 Chunk Size、Overlap、TopK 和最终 LLM 上下文窗口？
说话人1: 答，Chunk Size × TopK，加上 Overlap 重复的，加上 Prompt 其他内容，总和不能超过 LLM 的上下文窗口。

说话人1: 问题五十二，如何根据不同文档类型设计不同的 Chunk Size 和 Overlap？
说话人1: 答，技术文档、表格，Chunk 大一点。FAQ、短句，Chunk 小一点。不同类型不同参数。

说话人1: 问题五十三，为什么 Chunk 参数不能只依赖经验值，而应该通过检索评估进行调整？
说话人1: 答，因为不同文档、不同业务，最优参数不一样。要建测试集，跑不同参数，看哪个检索效果最好。

## 六、Spring AI 1.1.8 与 Java 工程实现
说话人1: 问题五十四，Spring AI 1.1.8 中的 TokenTextSplitter 解决什么问题？它采用什么切分思路？
说话人1: 答，解决按 Token 切分的问题。它是递归切分，优先按段落、句子切，尽量保持语义完整。

说话人1: 问题五十五，TokenTextSplitter 的 chunkSize、minChunkSizeChars、minChunkLengthToEmbed 和 maxNumChunks 分别控制什么？
说话人1: 答，chunkSize：每个块最大多少 Token。minChunkSizeChars：块最小多少字符。minChunkLengthToEmbed：太短的块不做 Embedding。maxNumChunks：最多切多少块。

说话人1: 问题五十六，为什么 minChunkSizeChars 不能简单理解为 Chunk Overlap？
说话人1: 答，因为它是最小块大小，不是重叠。和 Overlap 是两个概念。

说话人1: 问题五十七，Spring AI 1.1.x 的 TokenTextSplitter 是否原生提供独立的 Overlap 参数？如果没有，如何实现？
说话人1: 答，1.1.x 里没有专门的 Overlap 参数。要自己实现重叠，或者调整切分逻辑。

说话人1: 问题五十八，如何使用 Java 实现一个保留段落边界的递归切分器？
说话人1: 答，先按双换行切段落。段落太大，再按句号切句子。句子还大，再硬切。递归式的。

说话人1: 问题五十九，如何设计统一的 Chunk 元数据，包括文档 ID、章节路径、页码、Chunk 序号和来源？
说话人1: 答，每个 Chunk 都带这些字段。存向量数据库的时候，Metadata 里一起存。

说话人1: 问题六十，如何为不同文档类型配置不同的 TextSplitter？
说话人1: 答，PDF 用一个 splitter，Markdown 用另一个。根据文件类型选。

说话人1: 问题六十一，如何编写单元测试，验证 Chunk 长度、边界完整性、Overlap 和元数据保留？
说话人1: 答，写测试。给一段已知的文本，切完看块数对不对，长度对不对，边界是不是在句子之间，元数据有没有。

说话人1: 问题六十二，如何抽查原文与 Chunk 内容，发现解析异常、内容丢失和上下文断裂？
说话人1: 答，随机抽几个 Chunk，对比原文。看内容有没有丢，顺序对不对。

## 七、生产级 RAG 质量评估
说话人1: 问题六十三，为什么 Chunk 切分质量会直接影响 Embedding 表示和向量检索效果？
说话人1: 答，因为 Embedding 是基于 Chunk 内容生成的。Chunk 切得好，语义完整，Embedding 就准。切得不好，语义断了，Embedding 就不准。

说话人1: 问题六十四，如何通过 Recall@K、Precision@K 和 MRR 评估不同切分策略？
说话人1: 答，建测试集。一批问题，标注好正确的 Chunk。跑不同切分策略，看召回率、精确率、排序准不准。

说话人1: 问题六十五，如何设计一组测试问题，对比固定长度切分、递归切分和语义切分？
说话人1: 答，选典型的问题，比如问故障原因、问处理步骤。用不同切分策略建库，跑同样的问题，对比效果。

说话人1: 问题六十六，如果检索结果经常缺少故障原因或处理步骤，如何判断是否由 Chunk 边界不合理造成？
说话人1: 答，看召回的 Chunk。是不是原因和步骤被切到不同块里了。如果是，就是切分的问题。

说话人1: 问题六十七，如果 TopK 返回多个高度重复的 Chunk，应该从哪些切分和检索参数排查？
说话人1: 答，看 Overlap 是不是太大了，重复内容多。或者 Chunk 太小了，内容差不多。

说话人1: 问题六十八，如何评估 Chunk 数量、向量存储成本、检索质量和模型上下文成本之间的平衡？
说话人1: 答，看几个指标。检索质量够不够，成本高不高，存储多不多。找一个平衡点。

说话人1: 问题六十九，如果要为制造设备故障知识库设计切分方案，你会如何处理设备型号、故障代码、故障现象、原因分析和维修步骤之间的关联？

说话人1: 问题七十，面试官问：为什么不能只按字符暴力切分？你会如何从语义完整性、Token 限制、检索质量和生产成本四个层面回答？
说话人1: 答，我从四个层面说。
说话人1：第一，语义完整性。暴力切分不管语义，会把句子、段落、表格从中间切开。Chunk 出来是不完整的。
说话人1：第二，Token 限制。字符数不等于 Token 数。按字符切，实际 Token 可能超了 Embedding 模型的输入限制。
说话人1：第三，检索质量。切出来的 Chunk 语义不完整，Embedding 出来的向量就不准。检索召回的内容不对，答案就错。
说话人1：第四，生产成本。Chunk 切得不好，要更多 TopK 才能凑够上下文。Token 多了，成本就高。向量存储也多。
