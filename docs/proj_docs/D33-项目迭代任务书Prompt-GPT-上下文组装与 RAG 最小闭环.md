## 4. 最小架构与职责边界

具体包名和类名遵循 D33 现有工程规范，可调整命名，但必须保持职责分离。

### 4.1 RagOrchestrator

负责协调完整流程，不承载具体检索或模型调用细节：

1. 接收问题和可选检索过滤条件。
2. 调用 RetrievalService。
3. 将结果交给 ContextAssemblyService。
4. 判断是否具备生成条件。
5. 有证据时调用 GenerationService。
6. 汇总回答、来源及检索/生成状态。
7. 区分检索失败、无证据、上下文为空和生成失败。

禁止在编排层直接编写向量查询、Embedding 调用或底层 ChatModel 调用逻辑。

### 4.2 RetrievalService

职责：`Query Embedding → VectorStore → Top-K`。

- 复用Query Embedding 和相似度检索实现。
- 沿用已有Embedding 模型及 384 维向量空间。
- 沿用已验证的 Top-K 默认行为及过滤能力。
- 返回统一检索结果对象，包含实际存在的 Chunk 内容、来源元数据及可用的真实分数。
- 区分“检索成功但无结果”和“检索执行失败”。
- 不直接调用 ChatModel，不负责 Prompt 和回答生成。

### 4.3 ContextAssemblyService

职责：将候选 Chunk 处理为模型可用的证据上下文。

至少实现：

1. **有效性检查：** 排除空内容、无效记录及不允许参与回答的片段。
2. **去重：** 根据稳定 Chunk ID 或可靠内容标识去重。
3. **排序：** 保留检索顺序；如按分数排序，必须理解分数/距离的真实方向。
4. **预算控制：** 控制最终上下文长度，不能超过明确配置的预算。
5. **来源组织：** 为每个上下文片段分配唯一来源标识，并映射到真实 Chunk/document 元数据。
6. **结果说明：** 输出上下文、选中证据、被剔除片段及预算统计。

预算要求：

- 确认 ChatModel 上下文窗口，并为系统指令、问题、上下文和输出预留合理预算。
- 明确预算单位是 Token 还是字符。字符估算不得伪称 Token 数。
- 优先使用已有 Token 计数能力；没有时可采用可解释的保守估算并注明误差边界。
- 超预算时按明确策略减少 Chunk 或裁剪，不能静默破坏证据内容或来源标识。
- 记录预算上限、实际估算值、选中 Chunk 数和裁剪情况。

建议使用独立 ContextAssemblyResult，包含最终上下文、选中证据、来源映射和预算统计。

### 4.4 GenerationService

职责：独立负责 Prompt 构造和大模型调用。

- 接收用户问题和 ContextAssemblyResult，不自行访问 VectorStore。
- 构造明确的 RAG Prompt。
- 将检索上下文作为知识证据传给模型。
- 调用项目实际配置的 ChatModel/ChatClient。
- 处理模型超时、调用异常和空响应。
- 返回生成内容及模型调用状态。

Prompt 必须明确约束：

- 只能依据提供的上下文回答知识库事实问题。
- 上下文没有答案时，明确说明知识库证据不足。
- 不得根据模型自身常识补造设备型号、故障代码、维修步骤、参数或结论。
- 不得伪造来源、Chunk ID、文档名称、页码或引用。
- 不得把用户问题或模型生成内容当成知识库证据。
- 证据只能支持部分结论时，明确说明证据边界。

GenerationService 不得访问 VectorStore、Repository 或数据库。

### 4.5 RAG Response

对外响应至少表达：

- 回答内容。
- 来源列表。
- 检索状态。
- 生成状态。
- 必要错误码或错误说明。
- 可选检索数量、上下文预算统计和耗时。

来源必须来自本次实际检索且进入上下文的 Chunk。若无法验证模型逐条引用，返回“提供给模型的证据来源”，不得声称这些来源均被模型实际引用。

## 5. 核心实施需求

### 5.1 复用文档导入与向量检索

- 复用文档导入、Chunk 切分、向量入库、版本和幂等能力。
- 复用Query Embedding、Top-K 检索和已验证过滤能力。
- 不重复实现导入、切分、向量入库或检索基础设施。
- 确保只检索允许参与问答的有效文档版本。
- 通过真实数据验证文档导入后能够检索并进入上下文。

### 5.2 上下文组装

实现独立 ContextAssemblyService。验收重点：

- 重复 Chunk 不重复进入上下文。
- 片段顺序有明确、可解释规则。
- 空内容和无效内容不进入 Prompt。
- 上下文长度受预算控制。
- 来源标识唯一且能追溯真实文档和 Chunk。
- 被裁剪或排除的片段有必要记录。
- 不混入检索结果以外的虚构知识。

不加入复杂重排序、混合检索或外部知识扩展。

### 5.3 Prompt 与大模型生成

- 使用项目已配置且可用的 ChatModel。
- Prompt 清楚分隔系统规则、用户问题和检索上下文。
- 对证据不足、空上下文和无关问题设置拒答约束。
- 对超时、限流、服务不可用和空响应进行受控处理。
- 不将模型生成结果写回知识库或当作检索证据。
- 不因生成失败伪造成功回答。
- Prompt 模板应可维护，不将大量 Prompt 字符串散落在 Controller 或 Orchestrator。

### 5.4 RagOrchestrator 编排

按固定流程协调：

1. 校验问题及请求参数。
2. 调用 RetrievalService。
3. 判断检索状态和结果数量。
4. 调用 ContextAssemblyService。
5. 判断是否存在可用证据。
6. 无可用证据时直接返回受控拒答，不调用 ChatModel。
7. 有可用证据时调用 GenerationService。
8. 汇总回答、真实来源和各阶段状态。
9. 记录必要链路日志和耗时。

每个阶段必须有明确输入、输出和异常边界。不得把所有逻辑堆在 Controller 或单个 Service 中。

### 5.5 最小 RAG HTTP 接口

按现有 API 风格新增最小接口。

请求至少包含用户问题，以及可选 Top-K、可选检索过滤条件（仅开放已验证支持的字段）。

响应至少包含回答、实际来源列表、检索状态、生成状态及必要错误信息/调试统计。

要求：

- 请求参数合法性校验。
- DTO 与内部检索/模型对象分离。
- 遵循现有统一响应和异常处理规范。
- 不暴露 API Key、数据库连接信息或内部异常堆栈。
- 不把模型超时包装成正常回答。
- 空检索与检索系统故障必须区分。
