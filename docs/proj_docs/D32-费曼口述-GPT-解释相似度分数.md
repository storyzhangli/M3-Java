# **费曼口述：解释相似度分数（Similarity Score）**

**技术基线：** JDK 21、Spring Boot 3.5.x、Spring AI 1.1.8、PostgreSQL 18.7、pgvector 0.8.7。

**应用场景：** 制造设备故障知识库 RAG 检索。

共七十道关键问题，分为七个阶段，从 Embedding 向量基础、余弦相似度、内积与欧氏距离，到不同数据库的距离度量、Embedding 模型差异、RAG 检索阈值以及生产级检索评估。

## **一、相似度分数的基本认知**

**说话人1: 问题一，什么是 Embedding 向量？文本经过 Embedding 模型处理后，为什么会变成一组浮点数？**

**说话人1: 答，** Embedding 向量就是将文本、图片等内容通过 Embedding 模型编码后得到的一组数值表示。

以文本为例，用户输入“电机无法启动”，Embedding 模型会将这段文本转换成一个固定维度的浮点数数组。

例如：

```
float[] embedding = {
    0.12f,
    -0.35f,
    0.78f,
    0.21f,
    -0.14f
};
```

这只是一个五维的示意向量，实际 Embedding 模型通常会输出数百维或者上千维的向量。

之所以转换成浮点数，是因为神经网络通过大量训练数据学习文本中的语义特征，并将这些特征编码到一个连续的高维向量空间中。

在这个空间中，语义关系相近的文本通常具有更加接近的向量表示。

例如：

- 电机无法启动。
- 电动机启动失败。
- 电机启动异常。

这些文本的表达方式不同，但是语义比较接近，因此经过合适的 Embedding 模型编码后，通常会表现出较高的向量相似度。

需要注意，每个浮点数通常不能直接解释成一个具体的中文语义，而是多个维度共同构成文本在向量空间中的表示。

**说话人1: 问题二，什么是相似度分数（Similarity Score）？它在 RAG 检索流程中承担什么作用？**

**说话人1: 答，** 相似度分数就是通过某种向量度量方法，计算查询向量和知识库文档向量之间的接近程度，并用一个数值表示两者之间的关系。

在 RAG 中，它主要用于衡量用户问题与知识库 Chunk 的向量相关程度。

例如，用户提问：

“变频器显示 E001 故障，应该如何处理？”

知识库中存在三个 Chunk：

- Chunk A：变频器 E001 故障原因及排查方法。
- Chunk B：变频器 E002 故障处理流程。
- Chunk C：设备日常保养注意事项。

系统分别计算 Query 和三个 Chunk 的向量相似度，假设得到以下示意结果：

| Chunk | 相似度分数 |
| ----- | ---------- |
| A     | 0.92       |
| B     | 0.78       |
| C     | 0.35       |

系统可以根据分数进行排序，再结合 TopK 和相似度阈值，决定哪些 Chunk 进入后续 RAG 上下文。

因此，相似度分数主要承担候选知识排序和初步相关性筛选的作用。

但它不能单独证明 Chunk 一定包含正确答案。

**说话人1: 问题三，相似度分数是如何产生的？用户 Query 和知识库 Chunk 分别经过哪些处理才能进行比较？**

**说话人1: 答，** 相似度分数通常来自两个阶段。

第一阶段是向量生成。

用户输入 Query 后，系统调用 Embedding 模型，将 Query 转换成查询向量。

知识库在入库阶段已经完成文本解析、切块和 Embedding 编码，每个 Chunk 都保存了对应的向量。

第二阶段是向量比较。

系统将 Query 向量与知识库中的 Chunk 向量进行比较，通过余弦相似度、内积或者欧氏距离等度量方式计算两者的关系。

例如：

```
用户 Query
    |
    v
Embedding Model
    |
    v
Query Vector
    |
    v
Vector Store
    |
    | 与知识库 Chunk Vector 比较
    v
相似度或距离计算
    |
    v
TopK 排序
    |
    v
阈值过滤
    |
    v
返回相关 Chunk
```

需要注意，Embedding 模型负责将文本转换成向量，而相似度计算通常由向量数据库或检索组件完成。

两者承担不同职责。

**说话人1: 问题四，为什么两个文本的向量距离或相似度可以用于衡量它们的语义接近程度？**

**说话人1: 答，** 因为 Embedding 模型在训练过程中，会学习文本之间的语义关系，并将这些关系映射到向量空间。

例如，“电机无法启动”和“电动机启动失败”虽然字面表达不同，但是它们描述的故障现象比较接近。

经过 Embedding 模型编码后，这两个文本的向量通常也会比较接近。

相反，“电机无法启动”和“员工工资结算”在语义上差异较大，对应的向量通常不会那么接近。

所以我们可以利用向量之间的距离或者相似度，对文本语义相关性进行近似衡量。

不过，这种关系是模型通过训练数据学习出来的，并不是数学上天然存在的语义定律。

Embedding 的实际效果还受到训练数据、模型架构、领域知识、文本长度和输入方式等因素影响。

**说话人1: 问题五，相似度分数越高，是否一定代表两个文本在业务含义上越接近？为什么？**

**说话人1: 答，** 不一定。

相似度分数越高，只能说明在当前 Embedding 模型和当前距离度量规则下，两个向量更加接近。

但向量接近不一定代表业务含义完全一致。

例如：

- 电机正常启动。
- 电机无法启动。

这两个句子都包含电机和启动等相同关键词，Embedding 模型可能认为它们具有一定语义相关性。

但是在设备维修业务中，它们表达的是完全不同的状态，甚至可能是相反的故障结论。

再比如：

- 变频器 E001 故障。
- 变频器 E002 故障。

两个故障描述非常接近，但是故障编码不同，实际处理方案可能也不同。

因此，设备故障知识库不能只依赖向量相似度，还应该结合设备型号、故障编码、文档类型和知识状态等结构化条件进行过滤。

**说话人1: 问题六，相似度分数与文本匹配程度、语义相关性和答案正确性之间是什么关系？**

**说话人1: 答，** 这四个概念需要区分。

第一，文本匹配程度，关注两个文本在词语、表达和内容上的匹配情况。

第二，语义相关性，关注两个文本表达的含义是否接近。

第三，相似度分数，是通过数学度量方法计算出来的向量比较结果，是对模型语义表示的一种量化。

第四，答案正确性，关注检索到的知识能否真正支持对用户问题的正确回答。

它们之间存在一定联系，但不能直接画等号。

例如，用户询问变频器 E001 故障原因，某个 Chunk 可能包含大量变频器相关内容，因此相似度较高，但实际讲的是 E002 故障。

这个 Chunk 在语义上具有相关性，却不一定能够回答用户的具体问题。

所以，RAG 的最终质量不仅取决于相似度，还取决于知识准确性、检索策略、上下文组织以及大模型生成能力。

**说话人1: 问题七，相似度分数是概率吗？为什么不能将 0.9 直接理解为模型有 90% 的把握认为文档正确？**

**说话人1: 答，** 相似度分数不是概率。

例如，余弦相似度为 0.9，只表示两个向量在方向上的接近程度比较高，并不代表知识库文档有 90% 的概率能够回答用户问题。

概率通常需要建立明确的概率模型，并且具有对应的统计解释。

而相似度分数只是根据特定数学公式计算出来的几何度量结果。

它不能直接表示：

- 文档内容有 90% 的准确率。
- 文档有 90% 的概率包含答案。
- 大模型有 90% 的把握生成正确答案。

如果业务需要评估答案置信度，还需要结合检索评估、重排序、知识验证和答案质量评估等机制。

**说话人1: 问题八，相似度分数是 Embedding 模型直接输出的吗？还是向量数据库根据两个 Embedding 计算出来的？**

**说话人1: 答，** 通常需要区分两个步骤。

Embedding 模型负责输出向量，不一定直接输出两个文本之间的相似度。

向量数据库接收到查询向量后，将它与已经保存的 Chunk 向量进行比较，再根据配置的距离度量方式计算距离或者相似度。

例如，使用 pgvector 时：

```
SELECT
    id,
    content,
    1 - (embedding <=> :query_vector) AS similarity
FROM vector_store
ORDER BY embedding <=> :query_vector
LIMIT 5;
```

这里 Embedding 模型负责提供 `query_vector`，pgvector 通过 `<=>` 计算余弦距离，SQL 再将距离转换为余弦相似度。

需要注意，有些专门的交叉编码器或者相似度模型可以直接对文本对进行评分，但这与普通 Embedding 模型输出向量后再由数据库计算相似度是不同的技术路线。

**说话人1: 问题九，为什么必须区分 Embedding 向量本身的数值与两个 Embedding 之间计算出的相似度分数？**

**说话人1: 答，** 因为它们代表完全不同的含义。

Embedding 向量是模型对一段文本进行编码后得到的多维数值表示。

例如：

```
Query Vector:
[0.12, 0.35, -0.21, 0.78]

Chunk Vector:
[0.15, 0.31, -0.18, 0.72]
```

这两组数组本身不是相似度分数。

只有将它们放在一起，根据余弦相似度、内积或者欧氏距离等公式进行计算，才能得到对应的比较结果。

例如，余弦相似度可能是 0.98，余弦距离则可能是 0.02。

因此：

- Embedding 向量：描述单个文本的向量表示。
- 相似度分数：描述两个向量之间的相似程度。
- 距离分数：描述两个向量之间的几何距离。

实际工程中还必须确认数据库返回的是哪一种数值，不能直接把原始向量和相似度分数混在一起理解。

## **二、余弦相似度（Cosine Similarity）**

**说话人1: 问题十，什么是余弦相似度？它通过什么方式衡量两个向量的方向接近程度？**

**说话人1: 答，** 余弦相似度是一种通过计算两个向量夹角的余弦值，衡量向量方向接近程度的方法。

它主要关注两个向量的方向，而不是单纯关注向量的长度。

例如：

```
向量 A = [1, 2]
向量 B = [2, 4]
```

虽然两个向量长度不同，但是它们方向完全一致，因此余弦相似度等于 1。

在文本检索中，余弦相似度常用于判断 Query 向量和 Chunk 向量在语义空间中的方向是否接近。

数值越大，通常代表方向越接近。

**说话人1: 问题十一，余弦相似度的数学公式是什么？分子和分母分别代表什么？**

**说话人1: 答，** 余弦相似度的计算公式为：

\\[ \operatorname{CosSim}(A,B)= \frac{A\cdot B}{\\|A\\|\\|B\\|} \\]

其中：

第一，分子 \\(A\cdot B\\) 表示两个向量的点积，也就是对应维度相乘后再求和。

第二，分母 \\(\\|A\\|\\|B\\|\\) 表示两个向量模长的乘积。

通过点积除以两个向量模长的乘积，就可以消除向量长度对结果的直接影响，得到两个向量方向之间的相似程度。

例如：

```
A = [1, 2]
B = [2, 4]

A · B = 1×2 + 2×4 = 10

|A| = √5
|B| = √20

Cosine Similarity = 10 / (√5 × √20) = 1
```

因此，这两个向量虽然长度不同，但是方向完全一致，余弦相似度为 1。

**说话人1: 问题十二，什么是向量点积（Dot Product）？它与余弦相似度有什么关系？**

**说话人1: 答，** 向量点积就是两个维度相同的向量，对应位置的元素分别相乘，然后将所有结果相加。

公式为：

\\[ A\cdot B=\sum\_{i=1}^{n}a_i b_i \\]

点积与余弦相似度之间具有直接关系：

\\[ \operatorname{CosSim}(A,B)= \frac{A\cdot B}{\\|A\\|\\|B\\|} \\]

也就是说，余弦相似度实际上是在点积的基础上，再除以两个向量的模长。

点积不仅受到方向影响，也受到向量长度影响。

而余弦相似度通过模长归一化，主要保留方向上的关系。

所以，两种计算方法虽然存在数学联系，但是不能在未经条件判断的情况下直接认为它们的结果相同。

**说话人1: 问题十三，为什么余弦相似度主要关注向量方向，而不是单纯比较两个向量的长度？**

**说话人1: 答，** 因为余弦相似度在计算时，会将两个向量的点积除以各自的模长。

这样可以消除向量长度对结果的直接影响。

例如：

```
A = [1, 2]
B = [2, 4]
```

B 的长度是 A 的两倍，但是两个向量的方向完全相同。

因此：

\\[ \operatorname{CosSim}(A,B)=1 \\]

在很多文本 Embedding 场景中，我们更加关注两个文本表达的语义方向是否接近，而不希望单纯因为向量模长不同就改变相似度排序。

所以余弦相似度经常用于文本语义检索。

不过，如果模型训练目标本身利用向量模长编码了有意义的信息，那么直接忽略模长也可能损失信息，需要根据模型的设计选择度量方式。

**说话人1: 问题十四，余弦相似度的理论取值范围是什么？-1、0 和 1 分别代表什么？**

**说话人1: 答，** 余弦相似度的理论取值范围是：

\\[ -1\leq \operatorname{CosSim}(A,B)\leq 1 \\]

其中：

- 等于 1：两个非零向量方向完全一致。
- 等于 0：两个向量相互正交，夹角为 90 度。
- 等于 -1：两个向量方向完全相反，夹角为 180 度。

在实际文本 Embedding 检索中，经常看到非负或者正数的相似度，但不能据此认为余弦相似度在数学上只能取 0 到 1。

不同模型输出的实际分数分布可能有所区别。

**说话人1: 问题十五，当两个向量方向完全一致、正交和完全相反时，余弦相似度分别是多少？**

**说话人1: 答，** 分别是 1、0 和 -1。

可以通过公式理解：

\\[ \operatorname{CosSim}(A,B)=\cos(\theta) \\]

其中 \\(\theta\\) 是两个向量之间的夹角。

第一，夹角为 0 度：

\\[ \cos(0^\circ)=1 \\]

第二，夹角为 90 度：

\\[ \cos(90^\circ)=0 \\]

第三，夹角为 180 度：

\\[ \cos(180^\circ)=-1 \\]

因此，两个向量的夹角越小，余弦相似度越大。

**说话人1: 问题十六，为什么两个向量的模长不同，但余弦相似度仍然可能等于 1？**

**说话人1: 答，** 因为余弦相似度主要关注两个向量的方向，而不直接比较它们的长度。

例如：

```
A = [1, 2]
B = [3, 6]
```

可以看出：

\\[ B=3A \\]

因此 B 是 A 的三倍，两个向量的长度不同，但方向完全相同。

代入余弦相似度公式：

\\[ \operatorname{CosSim}(A,B)=1 \\]

这说明两个向量的模长不同，不会妨碍它们获得相同的余弦相似度。

**说话人1: 问题十七，为什么余弦相似度适合用于很多文本语义检索场景？**

**说话人1: 答，** 主要是因为余弦相似度可以衡量向量方向之间的接近程度，并且能够减弱向量模长差异的影响。

在文本语义检索中，我们通常希望找到与用户问题表达含义相近的知识片段，而不是单纯寻找向量数值大小接近的内容。

例如：

- Query：电机无法正常启动。
- Chunk A：电动机启动失败的原因分析。
- Chunk B：设备润滑周期及维护要求。

如果 Embedding 模型能够正确学习这些文本的语义关系，那么 Query 和 Chunk A 通常会具有较高的余弦相似度。

此外，余弦相似度的计算相对简单，适合大规模向量检索系统使用。

OpenAI 的 Embedding 官方文档也推荐余弦相似度，并说明其输出向量经过 L2 归一化，因此在这种情况下可以使用点积实现等价计算。

**说话人1: 问题十八，余弦相似度与余弦距离（Cosine Distance）有什么区别？**

**说话人1: 答，** 余弦相似度和余弦距离是相关但不同的两个概念。

余弦相似度主要描述两个向量有多相似，通常是数值越大越相似。

余弦距离则通过相似度进行转换，表示两个向量之间的差异程度，通常是数值越小越接近。

对于常见定义：

\\[ \operatorname{CosineDistance}(A,B) =1-\operatorname{CosineSimilarity}(A,B) \\]

例如：

```
余弦相似度 = 0.9
余弦距离 = 1 - 0.9 = 0.1
```

需要注意，两个指标的数值方向相反。

所以在数据库检索中，使用相似度通常按照降序排列，而使用距离通常按照升序排列。

**说话人1: 问题十九，为什么余弦距离通常通过&#x20;**`1 - Cosine Similarity`**&#x20;计算？**

**说话人1: 答，** 因为余弦相似度越大，表示两个向量越接近，而我们希望距离指标能够体现数值越小越接近的特点。

因此，可以使用：

\\[ D\_{\cos}=1-S\_{\cos} \\]

其中：

- \\(D\_{\cos}\\) 表示余弦距离。
- \\(S\_{\cos}\\) 表示余弦相似度。

例如：

| 余弦相似度 | 余弦距离 |
| ---------- | -------- |
| 1.0        | 0        |
| 0.8        | 0.2      |
| 0.5        | 0.5      |
| 0.0        | 1.0      |
| -1.0       | 2.0      |

这样就可以把相似度转换成距离。

需要特别注意，余弦距离的数学取值范围是 0 到 2，而不是一定在 0 到 1 之间。

**说话人1: 问题二十，如果两个向量的余弦相似度是 0.8，那么余弦距离是多少？这是否代表文本有 80% 的语义重合？**

**说话人1: 答，** 余弦距离等于：

\\[ 1-0.8=0.2 \\]

所以余弦距离是 0.2。

但这不代表两个文本有 80% 的语义重合。

0.8 只是两个向量根据余弦公式计算出来的方向相似度，不是文本内容重合率，也不是答案正确率。

例如，两个设备故障描述的余弦相似度都是 0.8，但是一个可能是正确故障原因，另一个可能是故障现象相近但处理方案完全不同。

因此，不能把余弦相似度直接解释成业务上的百分比。

## **三、内积与欧氏距离**

**说话人1: 问题二十一，什么是内积相似度（Inner Product Similarity）？它如何衡量两个向量之间的关系？**

**说话人1: 答，** 内积相似度就是通过计算两个向量对应维度元素相乘后求和，来衡量两个向量之间的关系。

它的公式是：

\\[ A\cdot B=\sum\_{i=1}^{n}a_i b_i \\]

例如：

```
A = [1, 2]
B = [3, 4]

A · B = 1×3 + 2×4 = 11
```

内积越大，通常表示两个向量在内积度量下越接近。

但是需要注意，内积不仅受到向量方向影响，也受到向量模长影响。

因此，未经归一化的内积不能直接等同于余弦相似度。

**说话人1: 问题二十二，为什么未经归一化的内积既受到向量方向影响，也受到向量模长影响？**

**说话人1: 答，** 因为两个向量的点积公式实际上可以写成：

\\[ A\cdot B=\\|A\\|\\|B\\|\cos\theta \\]

其中：

- \\(\\|A\\|\\) 表示向量 A 的模长。
- \\(\\|B\\|\\) 表示向量 B 的模长。
- \\(\theta\\) 表示两个向量的夹角。

可以看到，内积同时受到向量模长和夹角的影响。

例如：

```
A = [1, 2]
B = [2, 4]
C = [3, 6]
```

这三个向量方向完全一致，但是长度不同。

A 和 B 的内积为 10，A 和 C 的内积为 15。

因此，即使方向完全一致，向量长度不同也会导致内积不同。

如果直接使用内积进行文本检索，就必须考虑 Embedding 模型输出向量的模长是否具有实际意义，以及是否需要进行归一化。

**说话人1: 问题二十三，什么是 L2 归一化（L2 Normalization）？为什么要将向量长度调整为 1？**

**说话人1: 答，** L2 归一化就是将一个向量的每个维度分别除以该向量的 L2 模长，使归一化之后的向量长度等于 1。

公式为：

\\[ A'=\frac{A}{\\|A\\|} \\]

假设：

```
A = [3, 4]

|A| = √(3² + 4²) = 5
```

归一化后：

```
A' = [0.6, 0.8]
```

此时：

\\[ \\|A'\\|=\sqrt{0.6^2+0.8^2}=1 \\]

为什么需要这样做？

主要是为了消除向量模长对内积结果的影响，让内积只反映两个向量方向之间的关系。

对于已经 L2 归一化的向量，直接计算内积就可以得到余弦相似度。

不过，不是所有 Embedding 模型都要求开发者手动归一化。部分模型已经输出归一化向量，实际使用时应该先确认模型的输出约定。

**说话人1: 问题二十四，当两个向量都经过 L2 归一化后，为什么内积等于余弦相似度？**

**说话人1: 答，** 因为余弦相似度公式是：

\\[ \operatorname{CosSim}(A,B) =\frac{A\cdot B}{\\|A\\|\\|B\\|} \\]

当两个向量都经过 L2 归一化后：

\\[ \\|A\\|=1,\quad \\|B\\|=1 \\]

代入公式：

\\[ \operatorname{CosSim}(A,B)=A\cdot B \\]

所以，两个单位向量之间的内积就等于余弦相似度。

这也是为什么很多向量检索系统可以通过归一化向量配合内积计算，实现余弦相似度检索。

**说话人1: 问题二十五，使用内积进行向量检索时，什么情况下必须关注 Embedding 是否已经归一化？**

**说话人1: 答，** 当我们希望内积表达的是纯粹的方向相似程度时，就必须关注 Embedding 是否已经进行了 L2 归一化。

例如，使用 pgvector 的负内积运算符 `<#>` 进行检索时，如果向量已经归一化，那么实际内积就等于余弦相似度。

但是，如果向量没有归一化，内积还会受到模长影响，排序结果可能与余弦相似度不同。

需要注意，某些模型本身使用最大内积作为检索目标，并且有意利用向量模长编码信息。这种情况下，不应该为了使用余弦相似度而擅自归一化。

所以，是否归一化应该根据 Embedding 模型的训练目标和检索方案决定，而不是所有模型统一处理。

**说话人1: 问题二十六，什么是欧氏距离（Euclidean Distance）？它与余弦距离的计算原理有什么不同？**

**说话人1: 答，** 欧氏距离又叫 L2 Distance，主要用于衡量两个向量在多维空间中的实际几何距离。

计算公式为：

\\[ D\_{L2}(A,B)= \sqrt{\sum\_{i=1}^{n}(a_i-b_i)^2} \\]

例如：

```
A = [1, 2]
B = [4, 6]
```

那么：

\\[ D\_{L2}=\sqrt{(4-1)^2+(6-2)^2}=5 \\]

余弦距离则主要根据两个向量的方向计算：

\\[ D\_{\cos}=1-\operatorname{CosSim}(A,B) \\]

两者的核心区别是：

第一，欧氏距离关注两个向量在空间中的实际距离，既受到方向影响，也受到向量位置和模长差异影响。

第二，余弦距离主要关注两个向量的方向差异，不直接比较向量长度。

因此，两种方法适用于不同的向量表示和检索需求。

**说话人1: 问题二十七，为什么欧氏距离越小，两个向量通常越接近，而余弦相似度越大，两个向量通常越接近？**

**说话人1: 答，** 因为它们本身使用了不同的数学定义。

欧氏距离衡量两个向量之间的几何距离，因此两个向量完全相同时，距离为零。距离越小，两个向量就越接近。

余弦相似度衡量两个向量的方向关系。方向完全一致时，余弦相似度为 1。相似度越大，两个向量方向就越接近。

所以：

- 欧氏距离：越小越相似。
- 余弦距离：越小越相似。
- 余弦相似度：越大越相似。
- 内积：通常越大越相似。

实际使用时，必须先明确当前数据库使用的是相似度还是距离，才能正确理解排序方向。

**说话人1: 问题二十八，两个向量已经归一化时，欧氏距离与余弦相似度之间存在什么数学关系？**

**说话人1: 答，** 对于两个经过 L2 归一化的向量：

\\[ \\|A\\|=\\|B\\|=1 \\]

根据欧氏距离平方展开公式：

\\[ \\|A-B\\|^2 =\\|A\\|^2+\\|B\\|^2-2A\cdot B \\]

又因为归一化后的内积等于余弦相似度，所以：

\\[ D\_{L2}^2=2-2\operatorname{CosSim}(A,B) \\]

因此：

\\[ D\_{L2}=\sqrt{2-2\operatorname{CosSim}(A,B)} \\]

这说明，在归一化条件下，欧氏距离与余弦相似度之间存在明确的单调关系。

余弦相似度越大，欧氏距离就越小。

**说话人1: 问题二十九，为什么同一批归一化向量使用余弦相似度和欧氏距离，可能得到完全一致的排序结果？**

**说话人1: 答，** 因为对于单位向量，欧氏距离与余弦相似度存在单调递减关系：

\\[ D\_{L2}=\sqrt{2-2S\_{\cos}} \\]

其中 \\(S\_{\cos}\\) 表示余弦相似度。

当余弦相似度越大时，欧氏距离必然越小。

因此，对于同一组归一化向量：

- 按余弦相似度降序排列。
- 按欧氏距离升序排列。

最终得到的结果顺序是一致的。

这也解释了为什么 OpenAI 官方 Embedding 文档指出，其默认输出的单位向量可以通过余弦相似度或者欧氏距离获得相同的排序结果。

但需要注意，排序一致不代表两个度量返回的具体数值相同。

**说话人1: 问题三十，为什么不同 Embedding 模型产生的向量，不应该直接混合使用同一个相似度比较结果？**

**说话人1: 答，** 因为不同 Embedding 模型通常具有不同的训练目标、模型参数和语义空间。

例如，模型 A 和模型 B 都输出 1536 维向量，但这不代表它们每个维度具有相同的语义含义。

模型 A 的第一维可能与它学习到的某类语义特征有关，而模型 B 的第一维并不一定具有相同含义。

所以，即使两个模型输出的向量维度相同，也不能直接将它们混合到同一个向量索引中进行语义检索。

实际工程中，知识库入库和用户 Query 检索应该使用兼容的 Embedding 模型及其对应的编码方式。

如果更换模型，通常需要重新生成知识库向量，并建立一致的新索引。

## **四、不同距离度量的分数方向与数值含义**

**说话人1: 问题三十一，Cosine Similarity、Cosine Distance、Inner Product 和 L2 Distance 分别属于相似度还是距离度量？**

**说话人1: 答，** 这四种指标可以分为两类。

第一，相似度或相似性度量：

- Cosine Similarity：余弦相似度，数值越大通常越相似。
- Inner Product：内积，数值越大通常越相似。

第二，距离度量：

- Cosine Distance：余弦距离，数值越小越相似。
- L2 Distance：欧氏距离，数值越小越相似。

其中，Inner Product 需要特别注意。

如果向量没有经过归一化，内积同时受到向量方向和模长影响，不能直接把它解释为余弦相似度。

**说话人1: 问题三十二，为什么不同向量数据库可能将相似度和距离以不同字段、不同方向返回？**

**说话人1: 答，** 因为不同向量数据库在底层算法、API 设计和检索实现上存在差异。

有些数据库直接返回相似度，有些数据库返回距离，还有些数据库为了方便索引排序，会返回经过符号转换的距离值。

例如：

- FAISS 使用 Inner Product 时，返回的是内积结果。
- pgvector 使用 `<=>` 时，返回的是余弦距离。
- pgvector 使用 `<#>` 时，返回的是负内积。
- Milvus 使用 COSINE 时，返回的是余弦相似度类型的度量结果。
- Milvus 使用 L2 时，返回的是平方欧氏距离。

这些结果的数值方向并不相同。

因此，在项目中不能仅仅依赖字段名称 `score` 或 `distance`，还应该明确具体的度量算法和数据库实现。

**说话人1: 问题三十三，为什么余弦相似度和内积通常是数值越大越相似，而欧氏距离和余弦距离通常是数值越小越相似？**

**说话人1: 答，** 因为相似度和距离的数学定义不同。

余弦相似度使用向量夹角的余弦值表示方向相似程度。两个向量方向越一致，余弦值越大。

内积通过向量对应维度相乘求和，通常通过最大化内积寻找更匹配的向量。

欧氏距离衡量实际空间距离，两个向量越接近，计算出的距离越小。

余弦距离则是通过：

\\[ 1-\operatorname{CosSim} \\]

转换得到的差异程度，所以数值越小越相似。

简单记忆：

**相似度通常越大越好，距离通常越小越好。**

但是使用内积时，还要确认是否归一化以及检索算法如何定义排序方向。

**说话人1: 问题三十四，为什么不能看到数据库返回一个数值，就直接假定它是 0 到 1 之间的相似度分数？**

**说话人1: 答，** 因为不同度量方式的取值范围和计算规则不同。

例如：

| 指标                       | 理论取值范围   | 趋势           |
| -------------------------- | -------------- | -------------- |
| Cosine Similarity          | [-1, 1]        | 越大越相似     |
| Cosine Distance            | [0, 2]         | 越小越相似     |
| Normalized Inner Product   | [-1, 1]        | 越大越相似     |
| Unnormalized Inner Product | 无固定范围     | 越大通常越相似 |
| L2 Distance                | [0, +∞)        | 越小越相似     |
| Negative Inner Product     | 取决于向量模长 | 越小通常越相似 |

例如，pgvector 的负内积结果可能是 -0.85，这并不代表相似度为负，而是它返回了负内积。

所以，在处理分数时必须明确：

第一，具体使用哪种度量算法。

第二，数据库返回的是原始相似度还是距离。

第三，结果是否经过归一化或符号转换。

第四，当前检索应该按照升序还是降序排序。

**说话人1: 问题三十五，pgvector 的&#x20;**`<=>`**、**`<#>`**&#x20;和&#x20;**`<->`**&#x20;分别代表什么操作？**

**说话人1: 答，** 这三个是 pgvector 最常用的向量距离操作符。

第一，`<=>` 表示余弦距离，即 Cosine Distance。

第二，`<#>` 表示负内积，即 Negative Inner Product。

第三，`<->` 表示欧氏距离，即 L2 Distance。

可以通过 SQL 理解：

```
SELECT
    embedding <=> :query_vector AS cosine_distance,
    embedding <#> :query_vector AS negative_inner_product,
    embedding <-> :query_vector AS l2_distance
FROM vector_store;
```

其中：

- `<=>`：用于余弦距离检索。
- `<#>`：用于最大内积检索，结果取负数以适配升序排序。
- `<->`：用于欧氏距离检索。

实际检索时一般会使用 `ORDER BY` 配合 `LIMIT`。

**说话人1: 问题三十六，为什么 pgvector 的&#x20;**`<=>`**&#x20;返回的是余弦距离，而不是余弦相似度？**

**说话人1: 答，** 因为 pgvector 将 `<=>` 定义为 Cosine Distance。

计算公式是：

\\[ D\_{\cos}=1-S\_{\cos} \\]

其中 \\(S\_{\cos}\\) 是余弦相似度。

pgvector 的距离运算符通常按照距离升序排列，这样可以直接使用：

```
SELECT *
FROM vector_store
ORDER BY embedding <=> :query_vector
LIMIT 5;
```

最接近的向量会排在前面。

如果直接返回余弦相似度，就需要按照降序排列。

因此，pgvector 采用余弦距离操作符，能够统一其距离检索接口的排序方向。

**说话人1: 问题三十七，为什么 pgvector 的&#x20;**`<#>`**&#x20;返回负内积？如果需要得到正向内积，应该如何转换？**

**说话人1: 答，** 因为普通内积通常是数值越大越相似，而 pgvector 的距离操作符采用升序排序。

为了让最大内积检索能够兼容距离升序排序，pgvector 将 `<#>` 定义为负内积。

假设：

```
A · B = 0.85
```

那么：

```
A <#> B = -0.85
```

这样就可以通过：

```
ORDER BY embedding <#> :query_vector ASC
```

让内积最大的向量排在前面。

如果需要得到正向内积，则乘以负一：

```
SELECT
    (embedding <#> :query_vector) * -1 AS inner_product
FROM vector_store;
```

需要记住，`<#>` 是负内积，不是负的余弦相似度。只有在向量满足 L2 归一化条件时，正向内积才等于余弦相似度。

**说话人1: 问题三十八，如何使用 SQL 将 pgvector 的余弦距离转换为余弦相似度？**

**说话人1: 答，** 可以使用：

\\[ S\_{\cos}=1-D\_{\cos} \\]

对应 SQL：

```
SELECT
    id,
    content,
    embedding <=> :query_vector AS cosine_distance,
    1 - (embedding <=> :query_vector) AS cosine_similarity
FROM vector_store
ORDER BY embedding <=> :query_vector
LIMIT 5;
```

这里有两个关键点。

第一，`1 - (embedding <=> :query_vector)` 用于将余弦距离转换为余弦相似度。

第二，`ORDER BY embedding <=> :query_vector` 仍然按照原始距离升序排列。

这样既能得到容易理解的相似度分数，也能够让查询使用对应的余弦距离索引。

在 pgvector 中，查询表达式应尽量保持符合索引操作符的形式，避免为了显示分数而改变索引使用方式。

**说话人1: 问题三十九，Milvus 的 COSINE、IP 和 L2 分别如何解释结果数值的大小方向？**

**说话人1: 答，** Milvus 支持多种向量度量方式，其中常见的三种是 COSINE、IP 和 L2。

第一，COSINE，也就是余弦相似度，数值越大通常越相似。

第二，IP，也就是内积，数值越大通常越相似。若向量经过归一化，IP 就等于余弦相似度。

第三，L2，也就是欧氏距离，数值越小越相似。

特别需要注意，Milvus 的 L2 度量计算的是平方欧氏距离，也就是省略了开平方的计算。

因此，虽然它们都可以用于向量检索，但是解释返回结果时必须结合当前配置的 Metric Type。

**说话人1: 问题四十，为什么 Milvus 的 L2 度量与部分其他工具返回的欧氏距离数值可能不同？平方欧氏距离有什么含义？**

**说话人1: 答，** 因为部分工具返回标准欧氏距离，而 Milvus 的 L2 度量采用平方欧氏距离。

标准欧氏距离的公式：

\\[ D=\sqrt{\sum\_{i=1}^{n}(a_i-b_i)^2} \\]

平方欧氏距离的公式：

\\[ D^2=\sum\_{i=1}^{n}(a_i-b_i)^2 \\]

例如：

```
A = [1, 2]
B = [4, 6]
```

标准欧氏距离：

\\[ D=\sqrt{3^2+4^2}=5 \\]

平方欧氏距离：

\\[ D^2=3^2+4^2=25 \\]

所以，同一组向量在不同工具中可能出现 5 和 25 这样的结果。

平方欧氏距离省略了开平方运算，能够减少计算开销。

由于平方函数在非负数范围内保持单调递增，所以平方欧氏距离不会改变按照 L2 距离进行的排序结果。

**说话人1: 问题四十一，为什么 FAISS、pgvector 和 Milvus 使用不同的度量接口时，必须先确认各自返回的是距离还是相似度？**

**说话人1: 答，** 因为它们的度量定义和返回值可能存在区别。

例如：

| 工具     | 度量方式             | 典型返回含义 | 排序方向 |
| -------- | -------------------- | ------------ | -------- |
| FAISS    | METRIC_INNER_PRODUCT | 正向内积     | 降序     |
| FAISS    | METRIC_L2            | 平方欧氏距离 | 升序     |
| pgvector | `<=>`                | 余弦距离     | 升序     |
| pgvector | `<#>`                | 负内积       | 升序     |
| pgvector | `<->`                | 欧氏距离     | 升序     |
| Milvus   | COSINE               | 余弦相似度   | 降序     |
| Milvus   | IP                   | 内积         | 降序     |
| Milvus   | L2                   | 平方欧氏距离 | 升序     |

因此，在做跨数据库迁移或者对比实验时，不能只比较返回数值。

必须先确认度量方式、归一化条件、返回值定义和排序方向。

否则可能出现明明使用了相同向量，却把最不相似的结果排到最前面的错误。

**说话人1: 问题四十二，如果三个数据库对同一组向量分别返回 0.85、0.15 和 -0.85，应该如何判断它们是否表达相同的检索结果？**

**说话人1: 答，** 首先必须确认它们采用的具体度量方式。

假设三个数值分别是：

- 数据库 A：余弦相似度 0.85。
- 数据库 B：余弦距离 0.15。
- 数据库 C：负内积 -0.85。

如果第三种情况使用的是经过 L2 归一化的向量，那么：

\\[ 1-0.15=0.85 \\]

同时：

\\[ -(-0.85)=0.85 \\]

因此，这三个结果在数学上可以表达相同的余弦相似度。

但是，如果向量没有归一化，就不能直接将负内积转换后的 0.85 当成余弦相似度。

所以，跨数据库对比必须确认：

第一，是否使用同一组 Embedding 向量。

第二，是否使用相同的归一化方式。

第三，是否使用相同的数学度量。

第四，是否正确转换了距离和相似度的数值方向。

只有这些条件得到确认，才能判断它们是否具有可比性。

## **五、分数与 Embedding 模型的关系**

**说话人1: 问题四十三，为什么更换 Embedding 模型后，即使使用相同的 Query 和 Chunk，得到的相似度分数也可能发生明显变化？**

**说话人1: 答，** 因为不同 Embedding 模型具有不同的训练数据、模型结构、训练目标和参数。

相同的一段文本经过不同模型编码后，可能得到完全不同的向量。

例如：

```
Query = 电机无法启动

模型 A：
[0.12, 0.35, 0.28, ...]

模型 B：
[-0.21, 0.46, 0.13, ...]
```

即使两个模型产生的向量维度完全一致，也不代表它们处于同一个语义空间。

所以，同一个 Query 和 Chunk 在模型 A 下可能得到 0.88 的余弦相似度，在模型 B 下可能只有 0.72。

这不一定说明模型 B 更差，而是因为两个模型的语义空间和分数分布不同。

因此，更换 Embedding 模型后，需要重新评估检索效果和相似度阈值。

**说话人1: 问题四十四，为什么相同模型、相同维度和相同距离度量，是比较两组向量结果的重要前提？**

**说话人1: 答，** 因为只有在向量表示空间和计算规则兼容的情况下，两个相似度结果才具有较好的可比性。

第一，相同模型可以尽量保证向量处于同一个语义空间。

第二，相同维度能够满足向量之间进行数学运算的基本要求。

第三，相同距离度量可以保证比较双方使用一致的数学定义。

此外，还需要注意模型版本、向量归一化方式、Query 和 Document 编码方式等条件。

例如，两个 1536 维向量虽然可以直接进行点积计算，但如果它们来自完全不同的 Embedding 模型，计算结果通常没有可靠的跨模型语义解释。

因此，维度相同只是数学运算的必要条件之一，不代表语义兼容。

**说话人1: 问题四十五，什么是查询向量与文档向量的非对称编码？它会如何影响相似度计算？**

**说话人1: 答，** 非对称编码就是 Embedding 模型针对查询文本和文档文本，使用不同的编码方式或者不同的提示指令生成向量。

例如：

```
Query:
电机启动失败如何处理？

Document:
设备故障排查手册中关于电机启动失败的处理方法。
```

有些 Embedding 模型会针对 Query 和 Document 使用不同的编码入口或者任务指令，让模型更好地学习查询和文档之间的匹配关系。

例如，模型可能提供：

```
query: 电机启动失败如何处理？

passage: 设备故障排查手册中的相关内容。
```

这样做的目的是提高检索任务中的查询与文档匹配效果。

但必须按照具体模型的官方要求调用对应编码方式。

如果模型要求 Query 和 Document 使用不同的前缀，而开发者却统一采用相同的编码方式，就可能降低检索效果。

**说话人1: 问题四十六，为什么有些 Embedding 模型对 Query 和 Document 使用不同的指令或编码方式？**

**说话人1: 答，** 因为查询文本和知识文档在检索任务中承担不同角色。

Query 通常比较短，表达的是用户希望找到什么信息。

Document 通常比较长，包含需要被检索的知识内容。

如果模型分别使用针对 Query 和 Document 的编码任务进行训练，就能够更好地学习查询与文档之间的相关关系。

例如：

```
Query:
query: 变频器 E001 故障如何排查？

Document:
passage: 变频器 E001 故障可能由输入电压异常、
内部保护触发或外围线路故障引起。
```

这里的 `query:` 和 `passage:` 只是示意，实际指令需要以模型官方文档为准。

所以，非对称编码不是简单的文本格式变化，而是模型针对检索任务进行优化的一种方式。

**说话人1: 问题四十七，为什么向量维度相同，不代表不同 Embedding 模型产生的向量处于同一个语义空间？**

**说话人1: 答，** 因为向量维度只代表向量包含多少个数值，并不代表每个维度具有相同的语义定义。

例如：

```
模型 A：1536 维
模型 B：1536 维
```

两个模型虽然都输出 1536 维向量，但是它们通过各自不同的训练数据和模型参数学习语义关系。

因此，模型 A 的某个维度变化与模型 B 的同一个维度变化，并不一定表达相同含义。

可以把它们理解为使用两套不同坐标体系描述语义。

即使维度数量相同，也不能直接进行跨模型相似度比较。

除非两个向量空间经过专门的对齐训练或者映射，并且经过验证，否则应该分别维护向量索引。

**说话人1: 问题四十八，为什么不能把模型 A 的 0.85 分数直接与模型 B 的 0.85 分数进行质量比较？**

**说话人1: 答，** 因为不同模型的相似度分数分布和语义表达能力可能不同。

模型 A 的 0.85 可能属于比较常见的高相关分数，而模型 B 的 0.85 可能属于相对普通的匹配结果。

这就像不同考试使用不同评分标准，即使都得到 85 分，也不代表实际能力完全相同。

所以，不能直接用相同数字判断两个 Embedding 模型的检索质量。

如果要比较模型质量，应该使用同一套带有标准答案的测试数据集，分别运行模型 A 和模型 B，再通过 Recall\@K、MRR、NDCG 等指标比较实际检索效果。

**说话人1: 问题四十九，Embedding 模型升级后，为什么旧向量和新向量可能不再适合直接混合检索？**

**说话人1: 答，** 因为新旧模型可能使用了不同的向量空间，即使向量维度没有变化，也不代表语义表示兼容。

例如，原来知识库使用模型 A 将所有 Chunk 转换成向量。

升级后，系统使用模型 B 生成新的 Query 向量。

如果直接使用模型 B 的查询向量去检索模型 A 生成的历史向量，就可能出现语义比较失真的问题。

正确做法通常是：

第一，确定新的 Embedding 模型及其参数。

第二，重新处理知识库文档。

第三，使用新模型重新生成全部 Chunk 向量。

第四，建立新的向量索引。

第五，进行检索效果验证后，再切换生产流量。

在迁移期间，可以通过双索引和版本标识实现平滑切换，但不应该把不兼容的新旧向量直接混合比较。

**说话人1: 问题五十，在设备故障知识库中，“E001 故障代码”“电机无法启动”和“电机启动异常”可能得到不同分数，应该如何理解它们之间的语义关系？**

**说话人1: 答，** 首先应该从业务语义上判断三个文本之间的关系。

第一，“E001 故障代码”是一个具体的故障标识，它可能代表某种特定设备的错误代码。

第二，“电机无法启动”描述的是一种故障现象。

第三，“电机启动异常”也是故障现象，但范围可能更加宽泛。

三个文本可能存在一定语义关联，但是它们不是完全等价的概念。

Embedding 模型计算出的相似度，只能反映其学习到的语义接近程度。

在制造设备知识库中，必须特别注意型号和故障代码这样的精确业务信息。

例如，某个 E001 代码只属于特定型号的变频器，而另一个型号的 E001 可能对应完全不同的故障。

因此，我会采用向量相似度负责语义召回，再结合设备型号、故障代码、产品系列等 Metadata Filter 进行约束。

这样能够减少仅靠语义接近造成的错误召回。

## **六、RAG 检索中的分数与阈值**

**说话人1: 问题五十一，什么是 TopK 检索？为什么 TopK 只保证返回排序靠前的结果，不保证结果一定相关？**

**说话人1: 答，** TopK 就是从候选文档中按照相似度或者距离进行排序，返回前 K 个结果。

例如：

```
Query：变频器 E001 故障如何处理？

TopK = 3

返回：
Chunk A：0.42
Chunk B：0.38
Chunk C：0.31
```

即使这三个分数都不高，数据库仍然可能返回它们，因为 TopK 只负责选出当前候选集合中排名靠前的三个结果。

它并不负责判断这些结果是否已经达到业务相关性要求。

因此，TopK 解决的是返回多少个候选结果的问题，不直接解决结果是否真正相关的问题。

**说话人1: 问题五十二，当数据库返回 TopK 文档时，为什么即使所有文档相似度都很低，也可能仍然返回结果？**

**说话人1: 答，** 因为 TopK 本质上属于排序和数量限制机制。

数据库会计算查询向量与候选向量之间的距离，然后从中选出最接近的 K 个文档。

例如，整个知识库没有与用户问题相关的内容，但是仍然存在一些距离相对较近的向量。

那么数据库依然可能返回 TopK 个结果。

例如：

```
Chunk A = 0.39
Chunk B = 0.35
Chunk C = 0.28

TopK = 3
```

这些结果只是当前候选集合中的前三名，不代表它们具有足够的业务相关性。

因此，需要结合相似度阈值或者其他相关性判断机制，过滤低质量结果。

**说话人1: 问题五十三，什么是相似度阈值（Similarity Threshold）？它与 TopK 有什么区别？**

**说话人1: 答，** 相似度阈值就是设置一个最低相似度要求，只有达到条件的文档才能进入最终检索结果。

TopK 和阈值解决的是两个不同问题。

TopK 控制最多返回多少条文档。

相似度阈值控制文档至少需要达到什么相关程度。

例如：

```
TopK = 5
Similarity Threshold = 0.75
```

假设检索结果如下：

| Chunk | 相似度 |
| ----- | ------ |
| A     | 0.92   |
| B     | 0.86   |
| C     | 0.81   |
| D     | 0.68   |
| E     | 0.51   |

最终返回 A、B、C 三个 Chunk。

因为 D 和 E 虽然在 TopK 的候选范围内，但是没有达到 0.75 的阈值。

所以，TopK 负责数量控制，阈值负责最低相关性筛选。

**说话人1: 问题五十四，为什么设置阈值可以过滤低相关性候选文档，却不能直接保证剩余文档一定包含正确答案？**

**说话人1: 答，** 因为相似度阈值只是根据向量距离进行筛选，并没有真正理解文档中的业务事实是否正确。

例如：

用户询问变频器 E001 故障处理方法。

某个 Chunk 可能介绍 E001 的产生原因，但没有提供任何维修步骤。

它的语义相似度可能很高，但是并不能完整回答用户问题。

甚至可能存在知识库内容错误、文档过期或者设备型号不匹配等问题。

因此，阈值只能过滤部分低相关性内容，不能替代业务校验、文档有效性检查和重排序。

**说话人1: 问题五十五，阈值设置过高会产生什么问题？为什么可能造成召回率下降和有效知识遗漏？**

**说话人1: 答，** 阈值设置过高，会导致很多本来具有业务价值的文档被过滤掉。

例如，用户询问：

“电机运行过程中突然停止，是什么原因？”

知识库中可能没有完全相同的表达，而是使用：

“电动机运行中断的故障诊断方法”。

两个文本虽然语义相关，但是由于表达、领域术语或者模型编码差异，得到的相似度可能只有 0.72。

如果阈值设置为 0.9，这个 Chunk 就会被过滤。

即使它实际上包含有效的故障诊断知识，也无法进入后续 RAG 流程。

因此，阈值过高可能造成召回率下降，尤其容易遗漏表达方式不同但业务上相关的知识。

**说话人1: 问题五十六，阈值设置过低会产生什么问题？为什么可能引入无关 Chunk 和上下文噪声？**

**说话人1: 答，** 阈值设置过低，会使大量相关程度较低的 Chunk 进入 RAG 上下文。

例如，用户询问变频器 E001 故障处理方法。

系统可能同时召回：

- E001 故障处理方法。
- E002 故障处理方法。
- 变频器日常维护规范。
- 电机安装注意事项。
- 其他设备的维修记录。

这些文档虽然可能存在一定语义关系，但是不一定能够回答具体问题。

如果全部放入 Prompt，会增加上下文长度，还可能让大模型混淆不同故障代码和设备型号。

因此，阈值过低容易增加上下文噪声，影响最终答案质量。

**说话人1: 问题五十七，为什么不能直接将 0.7、0.8 或 0.9 当成所有 RAG 项目的通用阈值？**

**说话人1: 答，** 因为不同 Embedding 模型和知识库的数据分布不同，相似度分数没有统一的业务解释标准。

例如：

同样是 0.8，在模型 A 中可能属于高相关性，在模型 B 中可能只是一般相关性。

另外，通用知识库与制造设备故障知识库对错误召回的容忍程度也不一样。

制造设备故障知识库需要特别关注设备型号、故障代码和维修方案的准确性。

因此，阈值不能简单照搬其他项目。

应该使用真实业务问题构建测试集，通过不同阈值下的 Precision、Recall 和答案正确性进行对照实验，最终确定合适的阈值。

**说话人1: 问题五十八，相似度分数与阈值之间应该如何建立关系？为什么需要结合真实业务数据进行阈值校准？**

**说话人1: 答，** 首先要明确当前 Embedding 模型和距离度量，然后根据真实检索结果分析分数分布。

例如，可以构建一个包含一百个真实设备故障问题的测试集。

对每个问题执行向量检索，再标注返回的 Chunk 是否相关。

然后分别尝试：

```
Threshold = 0.60
Threshold = 0.65
Threshold = 0.70
Threshold = 0.75
Threshold = 0.80
Threshold = 0.85
```

比较不同阈值对应的 Precision、Recall 和最终答案质量。

如果阈值过高，可能过滤掉相关文档，降低召回率。

如果阈值过低，可能保留大量无关文档，降低精确率。

所以，阈值校准本质上是根据实际业务数据，在召回能力和噪声控制之间寻找合理的平衡点。

**说话人1: 问题五十九，如果某个 Query 的 Top1 分数是 0.82，Top2 是 0.81，而另一个 Query 的 Top1 是 0.82，Top2 是 0.55，这两组检索结果有什么不同？**

**说话人1: 答，** 虽然两组查询的 Top1 分数都是 0.82，但是后续候选文档的分数分布不同。

第一组：

```
Top1 = 0.82
Top2 = 0.81
```

两个文档的分数非常接近，说明它们都与 Query 具有较高的向量相似度。

第二组：

```
Top1 = 0.82
Top2 = 0.55
```

Top1 明显高于 Top2，说明第一个候选文档在当前向量度量下具有更加明显的领先优势。

可以计算两者之间的差距：

第一组：

\\[ 0.82-0.81=0.01 \\]

第二组：

\\[ 0.82-0.55=0.27 \\]

这个差值可以帮助我们观察候选结果之间的分离程度。

但是，分数差距大不代表 Top1 一定正确，分数差距小也不代表结果一定错误。

还需要结合文档内容、业务条件和重排序结果进行判断。

**说话人1: 问题六十，什么是分数分布（Score Distribution）？如何通过 Top1 分数、TopK 分数、均值和分数差距分析检索质量？**

**说话人1: 答，** 分数分布就是一次检索过程中，所有候选文档相似度分数的整体分布情况。

除了观察 Top1 分数，还可以分析其他统计信息。

第一，Top1 分数，表示当前最接近 Query 的候选文档分数。

第二，TopK 分数，表示前 K 个候选文档的分数情况。

第三，平均分数，可以了解整体候选集合的相关程度。

第四，分数差距，可以观察 Top1 与 Top2 之间是否存在明显差异。

例如：

```
0.92
0.88
0.84
0.52
0.31
```

这组结果说明前三个候选文档相对集中，而后两个分数明显降低。

可以结合这个现象分析是否存在一个相对明确的相关文档集合。

但必须注意，相似度分数分布只能作为检索诊断的参考，不能直接代替相关性标签。

尤其不能只根据 Top1 分数或者 Top1 与 Top2 的差值判断答案是否正确。

## **七、分数的工程应用与评估**

**说话人1: 问题六十一，为什么相似度分数高，不代表 Chunk 中的内容一定能回答用户问题？**

**说话人1: 答，** 因为相似度分数主要反映 Query 与 Chunk 在向量空间中的接近程度，而不是直接判断 Chunk 是否包含问题的答案。

例如：

用户提问：

“变频器 E001 故障应该如何处理？”

知识库中存在一个 Chunk：

“变频器常见故障包括 E001、E002 和 E003，设备出现故障时应该及时检查运行状态。”

这个 Chunk 与用户问题在语义上比较接近，可能得到较高的相似度分数。

但是它没有具体说明 E001 故障的原因和处理步骤。

所以，相似度高不等于答案完整，也不等于答案正确。

在实际 RAG 工程中，可以通过向量召回、Rerank 重排序、知识内容校验和答案依据约束等方式，提高最终回答的准确性。

**说话人1: 问题六十二，为什么设备型号、故障编码、零件编号等精确条件不能只依赖向量相似度？**

**说话人1: 答，** 因为 Embedding 模型主要学习语义关系，并不能保证所有精确标识都能得到严格区分。

例如：

```
设备型号：INV-3000
故障代码：E001

设备型号：INV-3000
故障代码：E002
```

虽然两个故障代码只相差一个数字，但是它们可能对应不同的故障原因和维修方案。

再比如：

```
设备型号：MOTOR-A100
设备型号：MOTOR-A101
```

这两个型号非常接近，但实际设备规格可能存在差异。

如果只依赖向量相似度，可能召回相似型号或者相似故障代码的错误知识。

所以，我会将这些精确业务条件作为结构化 Metadata，使用精确匹配或者范围过滤，再结合向量相似度执行语义检索。

对于故障代码，还可以使用关键词检索或者数据库精确查询进行补充。

**说话人1: 问题六十三，什么是 Metadata Filter？为什么应该先通过设备型号、文档版本和知识状态缩小检索范围？**

**说话人1: 答，** Metadata Filter 就是元数据过滤，也就是利用文档附带的结构化信息，对向量检索的候选范围进行约束。

例如，一个设备故障 Chunk 除了保存文本和 Embedding 向量，还可以保存：

```
{
  "equipmentModel": "INV-3000",
  "faultCode": "E001",
  "documentVersion": "V2.1",
  "knowledgeStatus": "PUBLISHED",
  "deviceCategory": "INVERTER"
}
```

用户查询时，可以先限定设备型号、知识状态和有效版本，再在符合条件的数据范围内进行向量检索。

这样有几个好处。

第一，减少不同设备型号之间的错误召回。

第二，避免已经废弃或者过期的维修方案进入上下文。

第三，降低候选集合中的无关内容。

第四，提高检索结果的业务准确性。

在 PostgreSQL + pgvector 中，可以结合普通 SQL 条件和向量距离运算符实现这一过程。

不过需要注意，Metadata Filter 也不能设置得过于严格。如果结构化信息缺失或者用户没有提供足够条件，过度过滤反而可能造成有效知识遗漏。

**说话人1: 问题六十四，什么是混合检索（Hybrid Search）？BM25 分数与向量相似度为什么不能不加处理地直接比较？**

**说话人1: 答，** 混合检索就是同时利用关键词检索和向量语义检索，综合两种检索方式的优势。

关键词检索通常使用 BM25 等算法，主要考虑：

- Query 中的关键词是否出现在文档中。
- 关键词在文档中出现的频率。
- 关键词在整个文档集合中的重要程度。
- 文档长度等因素。

向量检索则通过 Embedding 向量之间的距离或者相似度，寻找语义相关的文档。

两者的计算基础和分数分布不同。

例如：

```
BM25 Score = 12.6
Vector Similarity = 0.85
```

不能直接认为 BM25 的 12.6 比向量相似度 0.85 更重要。

因为 BM25 分数通常没有固定的统一上界，而余弦相似度通常位于 -1 到 1 之间。

常见的混合检索方案包括加权分数融合和 RRF，也就是 Reciprocal Rank Fusion，倒数排名融合。

RRF 主要根据不同检索结果的排名进行融合，而不是直接比较两种算法的原始分数。

例如，一个 Chunk 在关键词检索中排名第一，在向量检索中排名第三，综合排名时就可以考虑它在两个检索通道中的表现。

这样能够兼顾精确关键词匹配和语义召回。

**说话人1: 问题六十五，什么是 Rerank？为什么重排序模型的相关性分数与 Embedding 相似度分数不是同一种指标？**

**说话人1: 答，** Rerank 就是重排序，主要用于对初步召回的候选文档进行第二阶段相关性评估。

向量检索通常采用 Bi-Encoder，也就是双编码器。

它分别将 Query 和 Document 编码成向量，然后通过向量距离计算两者的相似程度。

Rerank 常见的实现方式是 Cross-Encoder，也就是交叉编码器。

它会将 Query 和 Document 作为一个文本对输入模型，让模型联合分析两者之间的关系，再输出相关性分数。

例如：

```
Query:
变频器 E001 故障如何处理？

Candidate A:
变频器 E001 故障原因、检查步骤和维修方案。

Candidate B:
变频器 E002 故障原因和维修方案。
```

向量召回可能认为 A、B 都有一定相关性。

但是 Rerank 可以进一步分析故障代码和问题内容，通常能够将真正匹配的 A 排在前面。

两种分数不能直接等同：

- Embedding 相似度：衡量两个独立编码向量的几何关系。
- Rerank 分数：衡量模型联合分析文本对后得到的相关性判断。

Rerank 的原始输出还可能是 Logit 或模型特定的相关性分数，不一定是经过校准的概率。

所以，不能直接将 Embedding 的 0.85 与 Rerank 的 0.85 当成相同含义。

**说话人1: 问题六十六，如何通过 Recall\@K、Precision\@K、MRR 和 NDCG 评估相似度排序是否真正有效？**

**说话人1: 答，** 这四个指标主要用于评估检索系统的召回能力、结果精确程度以及排序质量。

第一，Recall\@K，也就是 K 个结果的召回率。

它衡量前 K 个检索结果中，找回了多少相关文档。

公式：

\\[ Recall\@K= \frac{K个结果中相关文档数量} {全部相关文档数量} \\]

例如，某个故障问题一共存在 10 个相关 Chunk，Top5 检索到了其中 4 个。

那么：

\\[ Recall\@5=\frac{4}{10}=0.4 \\]

说明召回率为 40%。

第二，Precision\@K，也就是 K 个结果的精确率。

它衡量返回的 K 个文档中，有多少是真正相关的。

公式：

\\[ Precision\@K= \frac{K个结果中相关文档数量}{K} \\]

例如，Top5 中有 4 个相关 Chunk：

\\[ Precision\@5=\frac{4}{5}=0.8 \\]

说明精确率为 80%。

第三，MRR，也就是 Mean Reciprocal Rank，平均倒数排名。

它主要关注第一个相关文档出现的位置。

公式：

\\[ MRR=\frac{1}{N} \sum\_{i=1}^{N}\frac{1}{rank_i} \\]

其中 \\(rank_i\\) 表示第 i 个查询中第一个相关结果的排名。如果没有相关结果，倒数排名记为零。

例如：

```
问题 A：第一个相关结果排名第 1
问题 B：第一个相关结果排名第 2
问题 C：第一个相关结果排名第 4
```

那么：

\\[ MRR=\frac{1}{3} \left(1+\frac12+\frac14\right) \\]

MRR 越高，说明第一个有用结果通常越靠前。

第四，NDCG，也就是 Normalized Discounted Cumulative Gain，归一化折损累计增益。

它主要考虑两个因素：

- 检索结果的相关性等级。
- 相关文档在结果列表中的位置。

与简单的 Precision 和 Recall 不同，NDCG 可以使用 0、1、2、3 等不同等级表示文档相关程度，并对排名靠后的结果给予折损。

它的计算核心是：

\\[ DCG\@K= \sum\_{i=1}^{K} \frac{2^{rel_i}-1}{\log_2(i+1)} \\]

然后：

\\[ NDCG\@K=\frac{DCG\@K}{IDCG\@K} \\]

其中 IDCG 是理想排序情况下的 DCG。

NDCG 越接近 1，表示检索排序越接近理想排序。

在制造设备故障知识库中，我会综合使用这四个指标：

- Recall\@K：检查是否漏掉重要故障知识。
- Precision\@K：检查是否召回大量无关维修内容。
- MRR：检查最重要的故障解决方案能否排在前面。
- NDCG：检查不同相关等级的知识是否按照合理顺序排列。

不能只使用一个指标评价整个检索系统。

**说话人1: 问题六十七，如何设计真实问题与相关 Chunk 的标注数据集，对不同相似度阈值进行对照实验？**

**说话人1: 答，** 我会建立一套包含真实设备故障问题、标准相关知识以及相关性等级的测试数据集。

第一，准备真实 Query。

**说话人1: 问题六十八，Spring AI 1.1.8 中的&#x20;**`Document.getScore()`**&#x20;和&#x20;**`SearchRequest.similarityThreshold()`**&#x20;分别有什么作用？使用 pgvector 时应该如何结合实际距离类型理解它们？**

**说话人1: 答，** 这两个 API 分别负责获取检索结果分数和设置最低相似度阈值。

第一，`Document.getScore()`。

它用于获取检索结果对应的分数，返回类型是 `Double`，并且允许为 null。

在 Spring AI 1.1.8 的 PgVectorStore 实现中，返回 Document 时会执行：

```
.score(1.0 - distance)
```

也就是说：

\\[ score=1-distance \\]

同时，计算得到的原始距离会保存到 Document 的 `distance` 元数据中。

对于默认的 `COSINE_DISTANCE`：

\\[ score=1-\text{cosine distance} \\]

也就是余弦相似度。

因此，在当前项目默认采用余弦距离时，可以直接通过：

```
Double score = document.getScore();
```

获取对应的余弦相似度分数。

第二，`SearchRequest.similarityThreshold()`。

它用于设置检索结果最低相似度分数。

例如：

```
SearchRequest request = SearchRequest.builder()
        .query("变频器 E001 故障如何处理")
        .topK(10)
        .similarityThreshold(0.75)
        .build();

List<Document> documents =
        vectorStore.similaritySearch(request);
```

这里表示最多检索 10 条，并设置最低分数阈值为 0.75。

在 Spring AI 1.1.8 的 PgVectorStore 源码中，查询时会计算：

```
double distance = 1 - request.getSimilarityThreshold();
```

然后将距离条件放入 SQL 查询中。

对于默认余弦距离，这实际上就是：

```
WHERE embedding <=> :query_vector < 0.25
```

也就相当于要求余弦相似度大于 0.75。

这里有一个工程上非常重要的区别：

`Document.getScore()`**&#x20;和&#x20;**`similarityThreshold()`**&#x20;的字段名称虽然是通用的，但具体数值含义取决于 VectorStore 的实现和距离类型。**

对于 Spring AI 1.1.8 的 PgVectorStore：

- COSINE_DISTANCE：Score 等于余弦相似度。
- EUCLIDEAN_DISTANCE：Score 等于 1 减去欧氏距离，可能出现负数。
- NEGATIVE_INNER_PRODUCT：Score 等于正向内积；只有向量归一化后，才等于余弦相似度。

所以，不能在更换距离类型后，依然把 `getScore()` 一律理解成 0 到 1 的余弦相似度。

另外，Spring AI 1.1.8 的 PgVectorStore 实际将阈值转换成 SQL 距离条件，而通用 Builder API 的文档描述了客户端过滤语义。项目开发时应该以实际使用的 VectorStore 实现为准。

对于当前制造设备 RAG 项目，我建议优先采用一致的 Embedding 模型和默认余弦距离，在明确分数语义后，再进行阈值校准。

public record RetrievalTrace(

**说话人1: 问题七十，在制造设备故障知识库中，如何建立一套从向量相似度计算、分数解释、阈值校准、混合检索到 RAG 答案评估的完整机制？**

**说话人1: 答，** 我会从知识入库、向量检索、候选筛选、重排序、答案生成和效果评估六个方面设计完整机制。

第一，知识入库阶段。

对制造设备故障文档进行解析、清洗和切块。

每个 Chunk 保存：

- Chunk ID。
- Document ID。
- 设备型号。
- 故障代码。
- 文档版本。
- 知识状态。
- Chunk 正文。
- Embedding 向量。

所有知识文档统一使用同一个 Embedding 模型和兼容的编码方式，保证 Query 向量与 Document 向量处于兼容的语义空间。

第二，向量检索阶段。

用户输入问题后，系统通过 Embedding 模型生成 Query Vector。

然后使用 PostgreSQL + pgvector 执行向量检索。

在当前技术基线下，可以优先使用余弦距离：

```
SELECT
    id,
    content,
    metadata,
    embedding <=> :query_vector AS distance,
    1 - (embedding <=> :query_vector) AS similarity
FROM vector_store
WHERE metadata->>'knowledgeStatus' = 'PUBLISHED'
ORDER BY embedding <=> :query_vector
LIMIT 20;
```

这里通过余弦距离升序排列，取前 20 条候选知识。

同时，可以增加设备型号、故障代码、产品系列等 Metadata Filter。

第三，候选筛选阶段。

结合 TopK 和相似度阈值进行初步筛选。

阈值必须根据真实的设备故障问题进行校准，而不是直接照搬其他项目的 0.7 或 0.8。

如果没有达到最低相关性要求的结果，就不应该强行向大模型提供无关知识。

第四，混合检索和 Rerank 阶段。

对于设备型号、故障编码、零件编号等精确内容，可以增加 BM25 关键词检索。

再通过 RRF 融合关键词检索与向量检索的结果。

随后使用 Rerank 模型对候选 Chunk 进行二次相关性判断，重点关注设备型号、故障代码、故障现象和维修方案是否匹配。

第五，RAG 答案生成阶段。

将经过筛选和重排序的 Chunk 作为上下文传递给大模型。

要求大模型：

- 优先根据知识库内容回答。
- 明确区分故障现象、故障原因和维修方案。
- 不得混淆不同设备型号和故障代码。
- 对缺失的信息主动提出澄清问题。
- 找不到可靠知识依据时明确说明，不能编造维修方案。
- 尽可能提供对应的 Document ID 和 Chunk 来源。

第六，检索与答案评估阶段。

建立人工标注的真实故障问题数据集。

使用 Recall\@K、Precision\@K、MRR 和 NDCG 评估检索质量。

使用 RAGAS 等评估方法分析 Context Precision、Context Recall、Faithfulness 和 Answer Relevancy 等指标。

同时，通过 TraceId 记录 Query、Embedding 模型、距离度量、相似度分数、阈值、过滤条件、Rerank 结果和最终答案。

最终形成一个可追踪、可评估、可调优的 RAG 检索闭环。

我的核心设计思想是：

**Embedding 负责语义表示，向量数据库负责相似度计算，Metadata Filter 负责业务约束，Hybrid Search 负责补充精确关键词召回，Rerank 负责二次相关性判断，RAG 负责基于可靠知识生成答案，评估系统负责持续验证检索和生成质量。**

这样才能将相似度分数从一个简单的数学数值，真正转化为生产级 RAG 系统中的可解释、可评估和可优化的工程指标。

## **九、本主题必须掌握的核心知识**

**1. 四种常见度量的区别**

| 度量              | 趋势     | 关键含义         |
| ----------------- | -------- | ---------------- |
| Cosine Similarity | 越大越好 | 方向相似         |
| Cosine Distance   | 越小越好 | 方向差异         |
| Inner Product     | 越大越好 | 点积，受模长影响 |
| L2 Distance       | 越小越好 | 几何距离         |

**2. 三个 pgvector 运算符**

```
<=>  -- Cosine Distance
<#>  -- Negative Inner Product
<->  -- Euclidean Distance
```

**3. 两个 Spring AI 1.1.8 API**

```
document.getScore();

SearchRequest.builder()
    .topK(10)
    .similarityThreshold(0.75)
    .build();
```

**4. 四个检索评估指标**

- Recall\@K：有没有漏掉相关知识。
- Precision\@K：返回的知识有多少真正相关。
- MRR：第一个相关结果排得是否靠前。
- NDCG：整体排序是否合理。
