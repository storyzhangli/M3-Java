# 费曼口述：数据变更如何映射到向量库
说话人1: 费曼口述，数据变更如何映射到向量库，共七十道关键问题，由浅入深分六个阶段，从数据变更与向量库的基本关系、新增数据如何映射到向量库、更新数据如何映射到向量库、删除数据如何映射到向量库、数据一致性事务与可靠性，到生产级数据同步与工程实践，技术基线为 JDK 21、Spring Boot 3.5.x、Spring AI 1.1.8、PostgreSQL 18.6、pgvector，以制造设备故障知识库为应用场景。

## 一、数据变更与向量库的基本关系
说话人1: 问题一，为什么 RAG 知识库中的向量数据不是一次性写入后就永远不变？
说话人1: 答，因为原始文档会变。设备手册会更新，故障案例会新增，过期的会删除。向量是派生的，源变了，向量也要跟着变。

说话人1: 问题二，什么是数据源、文档、Chunk 和 Embedding？它们之间是什么关系？
说话人1: 答，数据源：原始文件，比如 PDF。文档：解析后的文档对象。Chunk：文档切出来的小块。Embedding：Chunk 转成的向量。一个数据源 → 一个文档 → 多个 Chunk → 多个向量。

说话人1: 问题三，原始文档发生新增、修改、删除时，为什么必须考虑向量库中的数据同步？
说话人1: 答，因为向量是基于原始文档生成的。原始文档变了，旧的向量就不对了。要同步更新或者删除。

说话人1: 问题四，为什么向量库中的数据应该被视为原始知识数据的派生数据，而不是唯一事实来源？
说话人1: 答，因为向量是从原始文档算出来的。真正的事实是原始文档。向量只是为了检索方便的派生数据。

说话人1: 问题五，什么是数据变更映射（Change Mapping）？它要解决什么问题？
说话人1: 答，就是原始文档变了，怎么对应到向量库的变化。解决：新增要写哪些，更新要改哪些，删除要清哪些。

说话人1: 问题六，为什么业务数据变更不能简单地等同于向量库新增一条记录？
说话人1: 答，因为一条业务记录，可能切成好几个 Chunk，对应好几个向量。不是一对一。

说话人1: 问题七，数据库中的一条业务记录，经过文档转换和切块后，为什么可能对应多个向量记录？
说话人1: 答，因为一条记录内容多，要切成好几块。每块一个向量。

说话人1: 问题八，如何建立业务主键、文档 ID、Chunk ID 和向量记录 ID 之间的映射关系？
说话人1: 答，每个 Chunk 都存业务主键、文档 ID、Chunk ID。向量记录也关联这些 ID。能从向量回溯到原始业务记录。

说话人1: 问题九，为什么每个 Chunk 都应该保留稳定的来源标识和必要的业务元数据？
说话人1: 答，为了追溯。检索到了 Chunk，要知道来自哪份文档、哪个业务记录、哪一页。

说话人1: 问题十，什么是知识库数据的生命周期？新增、更新、删除和重建分别处于什么阶段？
说话人1: 答，生命周期就是文档从进库到出库的过程。新增：第一次进库。更新：内容改了。删除：不要了。重建：换 Embedding 模型，重新算。

## 二、新增数据如何映射到向量库
说话人1: 问题十一，当一份新的设备维修手册进入知识库时，应该经过哪些处理步骤才能写入向量库？
说话人1: 答，步骤：上传 → 解析 → 清洗 → 质量检测 → 生成文档 ID → 切 Chunk → 批量 Embedding → 写入向量库。

说话人1: 问题十二，为什么新增文档需要先进行格式解析、内容清洗和质量检测？
说话人1: 答，因为脏文档不能进库。先清洗，先检测，合格了再向量化。

说话人1: 问题十三，为什么必须先确定文档 ID，再执行 Chunk 切分和向量化？
说话人1: 答，因为每个 Chunk 都要带文档 ID。先有文档 ID，后面切分和向量化的时候才能关联上。

说话人1: 问题十四，如何为同一份文档生成稳定且可追溯的 Chunk ID？
说话人1: 答，Chunk ID = 文档 ID + Chunk 序号。稳定，而且能知道是哪份文档的第几个块。

说话人1: 问题十五，文档切分后，为什么每个 Chunk 都需要保存所属文档 ID？
说话人1: 答，为了追溯。后面要删文档或者更新文档，按文档 ID 找到所有 Chunk。

说话人1: 问题十六，EmbeddingModel 如何将 Chunk 文本转换为向量？
说话人1: 答，调 EmbeddingModel，输入 Chunk 文本，输出向量数组。

说话人1: 问题十七，为什么向量维度必须与向量库中的字段定义保持一致？
说话人1: 答，因为 pgvector 建表的时候指定了 vector(n)。维度不对，存不进去。

说话人1: 问题十八，如何将 Chunk 文本、Embedding 向量和 Metadata 一起写入 pgvector？
说话人1: 答，插入一行。字段包括：chunk_id、doc_id、content、embedding、metadata。

说话人1: 问题十九，如果一份文档包含多个 Chunk，如何保证这些 Chunk 全部成功入库？
说话人1: 答，用事务。要么全部成功，要么全部回滚。

说话人1: 问题二十，如果文档向量化过程中部分 Chunk 写入失败，应该如何处理？
说话人1: 答，失败重试。或者整份文档标记为失败，后面重新处理。

说话人1: 问题二十一，如何避免同一份文档重复导入，产生重复 Chunk 和重复向量？
说话人1: 答，入库前检查文档哈希。已经存在的，不重复导入。

说话人1: 问题二十二，什么是 Upsert？它与普通 Insert 有什么区别？
说话人1: 答，Upsert 就是有就更新，没有就插入。普通 Insert 是直接插，重复了报错。

说话人1: 问题二十三，使用 Upsert 实现新增数据写入时，应该选择什么业务唯一键？
说话人1: 答，用 Chunk ID 作为唯一键。或者用文档 ID + Chunk 序号。

说话人1: 问题二十四，为什么不能直接使用随机生成的向量记录 ID 作为重复入库判断依据？
说话人1: 答，因为每次随机生成的都不一样。重复导入的时候，判断不出来是重复的。

## 三、更新数据如何映射到向量库
说话人1: 问题二十五，当设备维修手册内容发生修改时，为什么不能只更新原始文档而不处理旧向量？
说话人1: 答，因为旧的向量是基于旧内容生成的。内容改了，旧向量就不对了。检索出来的还是旧的内容。

说话人1: 问题二十六，为什么原文修改后，原有 Chunk 的文本内容和 Embedding 可能已经失效？
说话人1: 答，因为内容变了。Chunk 文本变了，向量也要重新算。旧的就失效了。

说话人1: 问题二十七，什么是增量更新？它与全量重建有什么区别？
说话人1: 答，增量更新：只改变了的部分。全量重建：所有文档重新向量化一遍。增量快，全量慢但彻底。

说话人1: 问题二十八，如何判断一份文档是否真正发生了内容变更？
说话人1: 答，对比内容哈希。哈希变了，就是内容变了。

说话人1: 问题二十九，什么是内容哈希？如何利用 SHA-256 判断文档内容是否变化？
说话人1: 答，就是文档内容的哈希值。每次算一遍，和之前的对比。一样就是没变，不一样就是变了。

说话人1: 问题三十，为什么应该区分文件元数据变化、文档内容变化和 Embedding 模型变化？
说话人1: 答，因为影响不一样。元数据变了，不用重新向量化。内容变了，要重新切分。Embedding 模型变了，全部都要重新算。

说话人1: 问题三十一，如果只修改文档标题、来源地址或业务标签，是否一定需要重新生成 Embedding？
说话人1: 答，不用。因为正文没变。只改元数据，更新 Metadata 就行。

说话人1: 问题三十二，如果只修改文档中的一个段落，应该重新处理整份文档还是只处理受影响的 Chunk？
说话人1: 答，最好只处理受影响的 Chunk。但因为切分可能变，有时候要整份文档重新切。

说话人1: 问题三十三，如何判断修改后的 Chunk 与旧 Chunk 是否属于同一份知识内容？
说话人1: 答，看文档 ID 和位置。位置差不多，就是同一块。

说话人1: 问题三十四，当新版本文档重新切块后，旧 Chunk 的 ID 是否应该继续沿用？为什么？
说话人1: 答，不应该。因为切分变了，Chunk 对应关系变了。用新的 Chunk ID。

说话人1: 问题三十五，为什么更新文档时需要先生成新版本 Chunk，再处理旧版本 Chunk？
说话人1: 答，为了保证服务不中断。先生成新的，验证好了，再删旧的。中间有个并行期。

说话人1: 问题三十六，如何避免更新过程中出现新旧 Chunk 同时可检索或全部不可检索的状态？
说话人1: 答，用版本号控制。检索的时候，只取最新版本。旧的标记为过期，过滤掉。

说话人1: 问题三十七，什么是版本化更新？如何通过 document_version 管理文档的多个版本？
说话人1: 答，每个文档有版本号。新版本来了，旧版本标记为过期。检索的时候，只查最新版本。

说话人1: 问题三十八，当文档更新失败时，如何保证旧版本知识仍然可用？
说话人1: 答，新版本失败了，旧版本还在。不会影响线上服务。

说话人1: 问题三十九，如何设计文档更新的状态机，例如待处理、处理中、已发布和失败？
说话人1: 答，状态流转：待处理 → 处理中 → 已发布。失败了就标记失败，回滚。

说话人1: 问题四十，为什么文档更新应该具备幂等性？如何保证同一个变更事件重复执行不会产生错误？
说话人1: 答，因为消息可能重复消费。幂等就是重复执行结果一样。用事件 ID 判断，已经处理过的就不重复处理。

## 四、删除数据如何映射到向量库
说话人1: 问题四十一，当原始文档被删除时，为什么必须同时考虑其全部 Chunk 和向量记录？
说话人1: 答，因为文档删了，它的 Chunk 和向量也没用了。不删，就成了孤儿数据。

说话人1: 问题四十二，如何通过 document_id 找到一份文档对应的全部向量记录？
说话人1: 答，按 document_id 查向量表。把所有这个文档的 Chunk 都找出来。

说话人1: 问题四十三，什么是级联删除？为什么不应该默认认为删除 PostgreSQL 业务记录就会自动删除 pgvector 中的向量？
说话人1: 答，级联删除就是删主记录，关联的也自动删。但 pgvector 是扩展，不一定有外键级联。要手动删。

说话人1: 问题四十四，如何区分逻辑删除和物理删除？
说话人1: 答，逻辑删除：标记为删除，不真删。物理删除：真的从表里删掉。

说话人1: 问题四十五，什么是软删除？如何通过 deleted_at 或状态字段控制知识是否参与检索？
说话人1: 答，软删除就是加个删除标记。检索的时候，过滤掉 deleted_at 不为空的。

说话人1: 问题四十六，为什么软删除的向量必须在检索阶段被过滤？
说话人1: 答，因为数据还在表里。不过滤的话，还是会被检索出来。

说话人1: 问题四十七，如果文档删除成功，但向量删除失败，会造成什么数据一致性问题？
说话人1: 答，业务记录没了，向量还在。检索的时候，会召回到已经删除的文档。数据不一致。

说话人1: 问题四十八，如何通过删除事件和重试机制，最终清理已经失效的向量记录？
说话人1: 答，发删除事件。消费失败了，重试。死信队列里的，人工处理。

说话人1: 问题四十九，当文档被误删除时，如何利用原始文件、版本记录和备份恢复知识？
说话人1: 答，从备份恢复原始文件。重新入库。版本记录可以回溯到之前的版本。

说话人1: 问题五十，如果一份文档被多个知识库或业务场景引用，删除时应该如何处理引用关系？
说话人1: 答，引用计数。只有所有引用都没了，才真正删除。不然只是标记为不可见。

## 五、数据一致性、事务与可靠性
说话人1: 问题五十一，为什么 PostgreSQL 业务表与向量表之间的更新可能出现部分成功？
说话人1: 答，因为中间要调外部 Embedding API。API 调用失败，就可能业务表更新了，向量没更新。

说话人1: 问题五十二，如果业务数据和向量数据存储在同一个 PostgreSQL 实例中，能否利用数据库事务保证两者一致？
说话人1: 答，能。但前提是 Embedding 已经算好了。如果 Embedding 要调外部 API，不能放在事务里。

说话人1: 问题五十三，当向量化调用外部 Embedding API 时，为什么不应该长时间占用数据库事务？
说话人1: 答，因为外部 API 可能很慢。事务开太久，会锁表，影响性能。

说话人1: 问题五十四，什么是双写问题？为什么同时写业务数据库和独立向量数据库容易出现数据不一致？
说话人1: 答，双写就是同时写两个地方。容易一个成功一个失败。数据不一致。

说话人1: 问题五十五，什么是 Transactional Outbox Pattern？它如何保证业务数据变更事件不会轻易丢失？
说话人1: 答，就是在同一个事务里，既写业务数据，又写事件表。然后异步把事件发出去。保证事件不丢。

说话人1: 问题五十六，什么是最终一致性？为什么 RAG 知识库可以采用最终一致性，但必须定义可接受的同步延迟？
说话人1: 答，最终一致性就是数据慢慢会一致，不是马上。RAG 可以接受。但要定好，比如最多延迟几分钟。

说话人1: 问题五十七，如何使用消息队列实现文档变更事件的异步处理？
说话人1: 答，文档变了，发个消息到 MQ。消费者收到消息，去更新向量库。异步处理。

说话人1: 问题五十八，如何设计事件 ID、幂等键、重试次数和死信队列，避免重复消费与永久丢失？
说话人1: 答，每个事件有唯一 ID。消费者判断是不是处理过。失败了重试。重试多次还失败，进死信队列。

说话人1: 问题五十九，如何处理乱序事件？例如旧版本更新事件晚于新版本更新事件到达？
说话人1: 答，用版本号。事件里带版本号。旧版本的事件，直接丢掉。

说话人1: 问题六十，如何通过版本号或更新时间戳阻止旧事件覆盖新版本向量？
说话人1: 答，处理事件的时候，对比版本号。事件的版本比当前的旧，就不处理。

## 六、生产级数据同步与工程实践
说话人1: 问题六十一，如何设计一张文档主表，记录文档 ID、版本号、内容哈希、处理状态和更新时间？
说话人1: 答，字段：doc_id、version、content_hash、status、created_at、updated_at、deleted_at。

说话人1: 问题六十二，如何设计 Chunk 元数据，使其能够追溯到原始文档、文档版本和具体位置？
说话人1: 答，Metadata 里加：doc_id、doc_version、page_number、chunk_index、source。

说话人1: 问题六十三，如何设计文档变更事件，使新增、更新和删除都能够被统一处理？
说话人1: 答，事件类型：CREATE、UPDATE、DELETE。带 doc_id、version、content_hash。消费者根据类型处理。

说话人1: 问题六十四，为什么需要定期执行原始数据与向量库之间的一致性对账？
说话人1: 答，因为可能有不一致。定期对账，发现问题，修复。

说话人1: 问题六十五，如何发现原文存在但向量缺失、原文已删除但向量残留、Chunk 数量不一致等问题？
说话人1: 答，对比两边的数量。按文档 ID 对账。找不一致的地方。

说话人1: 问题六十六，当 Embedding 模型或向量维度发生变化时，为什么需要考虑全量重新向量化？
说话人1: 答，因为换模型了，向量空间不一样。旧向量和新的不兼容。要全部重新算。

说话人1: 问题六十七，如何通过双版本向量库或新旧索引并行方案完成 Embedding 模型迁移？
说话人1: 答，新模型先建一套新向量库。并行跑。验证好了，切流量。旧的慢慢停。

说话人1: 问题六十八，如何设计向量数据重建任务，保证重建过程中线上 RAG 检索仍然可用？
说话人1: 答，重建在新索引上跑。线上还是用旧索引。建好了，切换。不影响线上。

说话人1: 问题六十九，如何监控文档变更处理成功率、同步延迟、失败重试次数和孤儿向量数量？
说话人1: 答，埋点。统计这些指标。看板看趋势。异常告警。

说话人1: 问题七十，在制造设备故障知识库中，如何设计一套从原始文档变更到 pgvector 更新、删除、重试和一致性对账的完整数据同步机制？
说话人1: 答，完整设计分几步。
说话人1：第一步：文档主表。记录每个文档的版本、哈希、状态。
说话人1：第二步：变更事件。文档新增、修改、删除，发事件到 MQ。
说话人1：第三步：消费者。收到事件，处理向量库。新增就写，更新就删旧的写新的，删除就清向量。
说话人1：第四步：幂等和重试。事件 ID 幂等。失败重试，死信队列。
说话人1：第五步：版本控制。新版本来了，旧版本标记过期。检索只取最新版本。
说话人1：第六步：一致性对账。定期对比原始数据和向量库。发现不一致，修复。
说话人1：第七步：监控。同步延迟、成功率、孤儿向量，都监控。
说话人1：这样，文档变了，向量库能跟着变。数据保持一致。
