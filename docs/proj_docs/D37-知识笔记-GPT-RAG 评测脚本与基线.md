围绕一个核心问题展开：**一项 RAG 评测结果究竟证明了检索质量、生成质量，还是系统性能？**

先明确三个边界：

1. **检索指标**可以通过固定问题集、人工相关性标注和实际检索结果离线计算，不需要调用生成模型。
2. **生成与拒答指标**必须有真实生成结果才能验证真实模型表现；人工评判和 LLM-as-a-Judge 可以辅助评价，但不能用模拟回答代替真实模型结果。
3. **性能指标**必须基于实际运行链路测量。没有真实模型时，可以测本地检索耗时，但不能把它称为生产环境的 RAG 端到端延迟。

# M3 知识笔记：RAG 核心评测指标与指标分层

> **技术基线**：JDK 21 / Spring Boot 3.5.16 / Spring AI 1.1.8 / PostgreSQL 18.7 / pgvector 0.8.7\
> **学习目标**：能够区分检索质量、生成质量和系统性能，明确哪些指标可以离线验证，哪些必须调用真实模型。\
> **核心原则**：没有真实模型调用，不得声称完成了真实生成质量、拒答质量和生产级端到端延迟评测。

---

## 一、先建立 RAG 评测的整体认知

RAG 不只是一个检索算法，也不只是一次大模型调用，而是一条由多个环节组成的处理链路：

```
用户问题
   |
   v
查询处理
   |
   v
检索（关键词 / 向量 / 混合）
   |
   v
候选 Chunk 与证据
   |
   v
上下文组装
   |
   v
生成模型
   |
   v
回答与引用
   |
   v
返回用户
```

因此，评测也必须分层。

| 评测层级 | 主要回答的问题                         | 典型指标                                   | 是否必须调用真实生成模型 |
| -------- | -------------------------------------- | ------------------------------------------ | ------------------------ |
| 检索层   | 有没有找到正确证据？                   | Recall\@K、HitRate\@K、Precision\@K        | 否                       |
| 引用层   | 引用是否真实、可追溯、能支持回答？     | 引用真实性、可追溯性、支持性、完整性       | 部分需要                 |
| 生成层   | 模型是否正确回答，证据不足时是否拒答？ | 答案正确性、拒答质量                       | 是                       |
| 系统层   | 系统是否足够快、稳定？                 | 检索耗时、生成耗时、端到端延迟、TTFT、TPOT | 部分需要                 |

### 1.1 三个不能混淆的结论

**结论 A：Recall\@K 高，不代表 RAG 回答正确。**

检索阶段找到正确的设备故障手册，只能证明系统有机会获得正确证据。模型仍可能误解手册、遗漏关键条件，或者生成手册没有说明的维修步骤。

**结论 B：引用 ID 存在，不代表引用正确。**

`[S1]` 对应的 Chunk 可能真实存在，但它可能与回答中的结论无关，甚至与结论相反。

**结论 C：检索耗时低，不代表端到端响应快。**

检索只占整条链路的一部分。模型排队、网络请求、生成大量 Token、上下文组装等都可能增加总耗时。

## 二、检索层指标：Recall\@K、HitRate\@K、Precision\@K

检索层的核心问题是：

> 对于一个用户问题，系统返回的 Top-K 结果中，有没有找到应该找到的相关证据？

首先需要理解一个前提：**必须先建立 Ground Truth（真实标注集），才能计算这些指标。**

### 2.1 Ground Truth 是什么？

Ground Truth 是经过人工核验的评测标准，用于判断某个问题应该检索到哪些文档或 Chunk。

例如，设备故障知识库中有以下资料：

| Chunk ID | 内容                        | 是否与问题相关 |
| -------- | --------------------------- | -------------- |
| C001     | E101 故障码的定义和触发条件 | 是             |
| C002     | E101 故障码的检查流程       | 是             |
| C003     | E101 故障码的维修处理步骤   | 是             |
| C004     | GL-200 设备的日常保养说明   | 否             |
| C005     | 设备电机振动异常排查        | 否             |

问题：

> 设备出现 E101 故障码，应该如何处理？

经过人工核验，确定 C001、C002、C003 是相关证据。

那么：

```
Ground Truth = {C001, C002, C003}
```

Ground Truth 不是模型自己生成的检索结果，而是评测人员提前建立的参考答案。

### 2.2 Recall\@K：召回率

**定义：Top-K 检索结果中找回的相关文档数 / 全部已标注相关文档数。**

公式：

[\
Recall\@K =\
\frac{|Retrieved\@K \cap Relevant|}\
{|Relevant|}\
]

其中：

- `Retrieved@K`：系统实际返回的 Top-K 结果。
- `Relevant`：人工标注的全部相关结果。
- 分母是该问题所有已标注的相关结果数量。

假设系统返回 Top-5：

```
Retrieved@5 = {C001, C002, C004, C005, C006}
Ground Truth = {C001, C002, C003}
```

实际命中的相关 Chunk：

```
Retrieved@5 ∩ Ground Truth = {C001, C002}
```

因此：

[\
Recall\@5 = \frac{2}{3} \approx 66.67%\
]

\*\*含义：\*\*系统找回了全部已知相关证据中的约 66.67%。

注意：Recall\@K 关注的是有没有尽可能找全相关证据，不直接衡量返回结果中噪声有多少，也不单独衡量相关结果的排序是否足够靠前。

### 2.3 HitRate\@K：命中率

**定义：Top-K 是否至少命中一个相关结果。**

对单个问题：

[\
HitRate\@K(q) =\
\begin{cases}\
1 & Retrieved\@K \cap Relevant \neq \varnothing \\\
0 & Retrieved\@K \cap Relevant = \varnothing\
\end{cases}\
]

对于整个问题集：

[\
HitRate\@K =\
\frac{\text{至少命中一个相关结果的问题数}}\
{\text{总问题数}}\
]

假设有 4 个问题：

| 问题                | Top-5 是否命中相关 Chunk | HitRate |
| ------------------- | ------------------------ | ------- |
| Q1：E101 故障码     | 是                       | 1       |
| Q2：GL-200 无法启动 | 是                       | 1       |
| Q3：电机异常振动    | 否                       | 0       |
| Q4：泵运行噪声      | 是                       | 1       |

那么：

[\
HitRate\@5 = \frac{3}{4}=75%\
]

\*\*含义：\*\*75% 的问题至少找到了一个相关证据。

HitRate\@K 的特点：

- 计算简单。
- 适合衡量系统是否经常完全检索失败。
- 不关心命中了 1 个相关 Chunk 还是 5 个相关 Chunk。
- 不直接反映相关结果的数量和排序质量。

### 2.4 Precision\@K：精确率

**定义：Top-K 检索结果中，相关结果占全部返回结果的比例。**

[\
Precision\@K =\
\frac{|Retrieved\@K \cap Relevant|}\
{K}\
]

继续使用前面的例子：

```
Retrieved@5 = {C001, C002, C004, C005, C006}
Ground Truth = {C001, C002, C003}
```

命中 2 个相关 Chunk，实际返回 5 个结果：

[\
Precision\@5 = \frac{2}{5}=40%\
]

\*\*含义：\*\*Top-5 中只有 40% 的结果被标注为相关。

注意：如果系统实际只返回 3 条结果，而评测定义要求固定 K=5，那么需要提前约定分母口径。常见做法是将未返回的位置视为未命中，仍以 K 作为分母。不能在不同实验中随意改变计算规则。

### 2.5 三个指标的区别

| 指标         | 核心问题                     | 主要关注点       | 典型问题                     |
| ------------ | ---------------------------- | ---------------- | ---------------------------- |
| Recall\@K    | 找回了多少应该找到的证据？   | 相关结果覆盖程度 | 是否漏掉关键故障处理步骤？   |
| HitRate\@K   | 是否至少找到了一个相关证据？ | 问题级检索成功率 | 有多少问题完全没有命中？     |
| Precision\@K | 返回结果中有多少是相关的？   | 检索结果纯度     | Top-5 是否塞入太多无关资料？ |

可以用一句话记忆：

- Recall：**找全没有？**
- HitRate：**至少找到一个没有？**
- Precision：**找到的结果准不准？**

三者不能互相替代。

例如，一个系统每道题都能命中一个相关 Chunk，HitRate\@5 可能很高，但如果其他 4 个结果全是噪声，Precision\@5 仍然很低。

### 2.6 Chunk 级评测与 Document 级评测

RAG 通常先把原始文档切分成多个 Chunk，再进行检索。因此，必须明确 Ground Truth 的评测单位。

**Chunk 级评测**

例如：

```
设备维修手册 V2
 ├── C001：E101 故障定义
 ├── C002：E101 触发条件
 ├── C003：E101 检查步骤
 └── C004：E101 维修步骤
```

问题是：

> E101 的触发条件是什么？

Ground Truth 可能只有 C002。

如果检索返回 C001、C002、C003，Chunk 级 Recall\@3 = 1/1 = 100%。

**Document 级评测**

如果 C001～C004 都来自同一份设备维修手册，那么 Document 级评测只关心是否检索到这份手册。

| 评测单位    | 评测重点                   | 适用场景             |
| ----------- | -------------------------- | -------------------- |
| Chunk 级    | 是否找到具体支持问题的段落 | 检查证据定位是否准确 |
| Document 级 | 是否找到正确的原始文档     | 检查文档召回范围     |

两种评测结果可能不同：

- Document 级命中了正确手册。
- Chunk 级却没有找到包含 E101 触发条件的具体段落。

这说明：**找到正确文档，不等于找到了正确证据。**

建议 M3 评测优先采用 Chunk 级 Ground Truth，同时保留 Document ID，用于追溯原始文档。

## 三、Ground Truth 数据集：评测的基础

没有标注集，就无法可靠判断检索结果是否相关，也无法判断证据是否足以回答问题。

### 3.1 建议的数据结构

每道评测题至少记录：

| 字段                  | 含义                   | 示例                           |
| --------------------- | ---------------------- | ------------------------------ |
| question_id           | 问题唯一 ID            | Q001                           |
| question              | 用户问题               | 设备出现 E101 应该怎么办？     |
| relevant_chunk_ids    | 标注的相关 Chunk       | C001、C002、C003               |
| relevant_document_ids | 相关原始文档           | DOC001                         |
| answerability         | 证据充分程度           | SUFFICIENT                     |
| expected_action       | 预期行为               | ANSWER                         |
| expected_answer       | 参考答案或关键事实     | 检查 E101 触发条件并按手册排查 |
| required_evidence_ids | 必须支持关键结论的证据 | C002、C003                     |
| annotation_note       | 标注说明               | C003 包含维修步骤              |

### 3.2 可回答性不能只分成有答案和无答案

建议至少分为三类：

| 可回答性     | 含义                                 | 设备故障示例                     | 预期行为                            |
| ------------ | ------------------------------------ | -------------------------------- | ----------------------------------- |
| SUFFICIENT   | 知识库证据充分，可以回答             | 手册明确记录 E101 定义和处理步骤 | ANSWER                              |
| PARTIAL      | 有部分相关证据，但不足以支持完整结论 | 找到 E101 定义，但没有维修步骤   | PARTIAL_ANSWER 或 CLARIFY / ABSTAIN |
| INSUFFICIENT | 知识库没有足够证据                   | 用户询问未收录设备的特殊故障     | ABSTAIN                             |

其中 `PARTIAL` 需要在标注规范中明确处理规则：

- 如果已有证据能支持部分结论，可以明确回答已知部分，并说明未知部分。
- 如果问题要求的是一个必须完整、确定的结论，而证据不足，则应拒答或请求补充信息。

不能简单地把所有 PARTIAL 都标为回答或拒答，否则评测口径容易混乱。

### 3.3 标注质量控制

建议：

1. 先制定相关性标准，明确什么叫“相关 Chunk”。
2. 关键故障问题由熟悉设备知识的人员核验。
3. 对争议样本保留标注说明。
4. 重要数据集可由两名标注人员独立标注，再处理分歧。
5. Ground Truth 必须记录文档版本，避免文档更新后仍使用旧标签。

**注意：Ground Truth 也可能有错误。** 如果标注本身不准确，Recall\@K 等指标即使计算正确，也无法证明系统真实能力。

## 四、生成与引用层指标

检索阶段解决的是“找到证据”，生成阶段解决的是“正确使用证据”。

两者必须分开评测。

### 4.1 引用正确性：四个维度

引用正确性不能只验证引用 ID 是否存在。建议拆成四个维度。

#### 维度一：引用真实性（Citation Authenticity）

回答中的引用是否对应真实存在的资料？

需要检查：

- Source ID 是否存在。
- Document ID 是否存在。
- Document Version 是否存在。
- Chunk ID 是否存在。
- Chunk 是否属于对应 Document。
- Chunk 是否属于对应版本。
- 引用映射是否被篡改或指向错误记录。

示例：

```
回答：
E101 表示设备启动阶段异常，建议检查电源模块。[S1]
```

系统需要验证：

```
S1
  -> Source ID
  -> Document ID
  -> Document Version
  -> Chunk ID
```

如果 `[S1]` 根本不存在，引用真实性不通过。

但即使 `[S1]` 存在，也只能证明引用对象真实存在。

#### 维度二：引用可追溯性（Citation Traceability）

引用是否可以定位到原始资料和具体内容？

例如：

```
Source ID: SRC001
Document ID: DOC001
Version: V2
Chunk ID: C003
Page: 12
Section: 4.2 故障处理
```

理想情况下，用户或审查人员可以通过这些信息找到：

- 原始文档。
- 文档版本。
- 具体页码或章节。
- 对应 Chunk 内容。

可追溯性强调的是**证据定位能力**，不等于证据一定支持回答。

#### 维度三：引用支持性（Citation Support）

引用原文是否真正支持回答中的对应事实？

例如：

```
回答：
E101 表示电机过载，需要更换电机。[S1]
```

引用原文：

```
E101：设备启动异常，请检查供电状态。
```

`[S1]` 真实存在，也可以追溯到原文，但原文并没有说明“电机过载”或“需要更换电机”。

因此：

- 引用真实性：通过。
- 引用可追溯性：通过。
- 引用支持性：不通过。

这是引用评测中非常重要的区别。

引用支持性需要判断：

1. 引用是否支持回答中的事实？
2. 是否存在引用与结论相矛盾的情况？
3. 是否把相关性错误地当成因果关系？
4. 是否把建议、可能性表述成确定事实？
5. 是否超出原文证据范围？

#### 维度四：引用完整性（Citation Completeness）

回答中所有需要证据支持的关键事实，是否都具有必要引用？

例如：

```
E101 表示启动异常。[S1]
建议先检查电源状态。[S2]
如果仍无法启动，应检查控制线路。[无引用]
```

即使 `[S1]` 和 `[S2]` 都正确，也不能说明整个回答的引用完整。

第三个关键建议没有引用，需要进一步核验。

引用完整性关注的是：

- 关键事实是否都有证据。
- 重要操作建议是否有来源。
- 是否存在没有引用支撑的关键结论。

### 4.2 引用四维度对照

| 维度     | 核心问题                         | 是否能只靠数据库验证 |
| -------- | -------------------------------- | -------------------- |
| 真实性   | 引用的 ID 和资料是否真实存在？   | 大部分可以           |
| 可追溯性 | 是否能定位到原文、版本和 Chunk？ | 大部分可以           |
| 支持性   | 原文是否真正支持回答？           | 需要语义核验         |
| 完整性   | 关键事实是否都有必要引用？       | 需要结合回答内容核验 |

**必须记住：验证 `[S1]` 存在，不代表 `[S1]` 内容正确，更不代表 `[S1]` 支持模型回答。**

### 4.3 引用评测的实现思路

可以把引用校验拆成两步。

**第一步：程序化结构校验**

```
输入：模型回答 + 引用映射

1. 提取回答中的引用 ID
2. 查询引用 ID 对应的 Source
3. 校验 Document ID
4. 校验 Document Version
5. 校验 Chunk ID
6. 校验 Chunk 与 Document 的归属关系
7. 校验引用内容是否仍然存在
8. 输出真实性、可追溯性结果
```

这一步可以不调用生成模型。

**第二步：语义校验**

```
输入：
- 回答中的某一条事实
- 对应引用原文

判断：
- 支持
- 部分支持
- 不支持
- 与原文矛盾
```

这一步可以通过人工核验，也可以使用真实模型辅助评判，但重要结果应保留人工复核机制。

## 五、拒答质量：必须双向评测

拒答不是简单地判断模型有没有说“不知道”。

RAG 系统需要同时做到：

1. 证据充分时，尽可能正确回答。
2. 证据不足时，不编造、不误导。

因此，拒答质量必须双向评测。

### 5.1 四种情况

以“系统是否应该回答”为判断标准：

| 实际证据情况 | 模型行为 | 评测结论              | 示例                                         |
| ------------ | -------- | --------------------- | -------------------------------------------- |
| 证据不足     | 拒答     | 正确拒答              | 知识库没有该设备的维修资料，模型说明无法确认 |
| 证据充分     | 拒答     | 误拒答                | 手册明确记录 E101 处理流程，模型仍回答不知道 |
| 证据充分     | 回答     | 正确回答候选          | 模型依据手册给出有依据的处理步骤             |
| 证据不足     | 回答     | 错误回答 / 无依据回答 | 模型编造 E999 的故障含义和维修步骤           |

注意：证据充分时给出回答，只能说明它做出了正确的回答决策。是否真正回答正确，还需要单独检查答案事实。

### 5.2 拒答决策混淆矩阵

将实际证据是否充分作为真实标签，将模型是否回答作为预测结果。

| 实际情况 \ 模型决策 | 模型回答         | 模型拒答     |
| ------------------- | ---------------- | ------------ |
| 证据充分（应回答）  | TP：正确回答决策 | FN：误拒答   |
| 证据不足（应拒答）  | FP：无依据回答   | TN：正确拒答 |

其中：

- TP：证据充分，模型选择回答。
- FN：证据充分，模型错误拒答。
- FP：证据不足，模型仍然回答。
- TN：证据不足，模型正确拒答。

这里的 TP 只代表回答决策正确，不代表回答内容事实正确。

### 5.3 正确拒答率

[\
CorrectAbstentionRate =\
\frac{TN}{TN+FP}\
]

含义：

> 在所有实际证据不足的问题中，模型有多少比例正确选择了拒答？

例如：

- 证据不足问题：20 道。
- 正确拒答：18 道。
- 错误回答：2 道。

[\
CorrectAbstentionRate = \frac{18}{20}=90%\
]

### 5.4 误拒答率

[\
FalseAbstentionRate =\
\frac{FN}{TP+FN}\
]

含义：

> 在所有证据充分、应该回答的问题中，模型有多少比例错误拒答？

例如：

- 证据充分问题：30 道。
- 正确选择回答：24 道。
- 错误拒答：6 道。

[\
FalseAbstentionRate = \frac{6}{30}=20%\
]

误拒答率越低越好。

### 5.5 可回答问题正确回答率

首先计算回答决策成功率：

[\
AnswerDecisionRate =\
\frac{TP}{TP+FN}\
]

但这个指标只表示模型是否选择回答，不表示回答内容是否正确。

还需要单独计算：

[\
AnswerAccuracy =\
\frac{\text{事实正确的回答数}}\
{\text{证据充分且模型实际回答的问题数}}\
]

例如：

- 30 道证据充分的问题。
- 模型回答了 24 道。
- 其中 21 道事实正确。

那么：

[\
AnswerAccuracy = \frac{21}{24}=87.5%\
]

因此，不能把 AnswerDecisionRate 和 AnswerAccuracy 当成同一个指标。

### 5.6 为什么不能只看正确拒答率？

假设评测集有 100 道题：

- 90 道证据不足。
- 10 道证据充分。

如果模型对所有问题都拒答：

- 正确拒答 90 道。
- 误拒答 10 道。
- 正确拒答率 = 90 / 90 = 100%。
- 误拒答率 = 10 / 10 = 100%。

如果只报告正确拒答率，就会出现一个非常荒谬的结论：

> 模型拒答质量达到 100%。

实际上，模型完全没有回答能力。

因此必须同时报告：

- 正确拒答率。
- 误拒答率。
- 可回答问题回答决策率。
- 可回答问题答案正确率。
- 证据不足时无依据回答率。

### 5.7 类别不平衡问题

如果评测集中 95% 的问题都没有答案，那么模型全部拒答，也可能获得很高的总体准确率。

例如：

| 类别     | 数量 |
| -------- | ---- |
| 证据充分 | 5    |
| 证据不足 | 95   |

全部拒答时，决策准确率为：

[\
Accuracy = \frac{95}{100}=95%\
]

但模型没有回答任何一道可回答问题。

所以拒答评测必须分组统计，不能只报告总体 Accuracy。

建议至少分别统计：

- 证据充分问题。
- 证据部分充分问题。
- 证据不足问题。
- 故障码问题。
- 设备型号问题。
- 日常口语问题。

## 六、系统层指标：检索耗时与端到端延迟

系统性能评测主要回答：

> 用户从发出问题到收到回答，究竟需要等待多久？

### 6.1 一条 RAG 请求的耗时组成

可以把请求拆分成以下阶段：

```
请求进入
   |
   v
网关 / 网络 / 排队
   |
   v
查询预处理
   |
   v
Embedding
   |
   v
关键词检索 + 向量检索
   |
   v
结果融合 / 去重
   |
   v
上下文组装
   |
   v
模型请求与排队
   |
   v
模型生成
   |
   v
响应处理 / 网络返回
   |
   v
请求完成
```

每个阶段都可能产生耗时。

### 6.2 检索耗时（Retrieval Latency）

检索耗时不是只有 PostgreSQL 执行 SQL 的时间。

建议记录：

| 阶段            | 具体内容                          |
| --------------- | --------------------------------- |
| 查询处理        | 清洗、规范化、查询改写（如果有）  |
| Query Embedding | 将用户问题转换为向量              |
| 关键词检索      | PostgreSQL 全文检索或外部搜索服务 |
| 向量检索        | pgvector 相似度查询               |
| 结果融合        | 合并候选结果、去重、排序          |
| 权限过滤        | 按租户、设备、用户权限过滤        |
| 上下文组装      | 拼接最终交给模型的证据            |

如果关键词检索和向量检索并行执行，那么：

[\
T\_{parallel} \approx \max(T\_{keyword},T\_{vector})\
]

而不是：

[\
T\_{parallel} = T\_{keyword}+T\_{vector}\
]

如果两者串行执行，则需要累加各阶段耗时。

因此，计算检索总耗时时，必须明确阶段是并行还是串行。

### 6.3 生成耗时（Generation Latency）

生成耗时包括：

- 应用向模型服务发起请求。
- 网络传输。
- 模型服务排队。
- 模型处理 Prompt。
- 模型生成输出 Token。
- 响应传输回应用。

如果使用非流式调用，应用通常需要等到完整响应返回才能拿到最终答案。

如果使用流式调用，模型可能先返回第一个 Token，再持续返回后续 Token。

这就引出了 TTFT 和 TPOT。

### 6.4 TTFT：首 Token 延迟

TTFT = Time To First Token。

**定义：从请求开始到应用收到第一个输出 Token 的时间。**

[\
TTFT = t\_{firstToken}-t\_{requestStart}\
]

TTFT 越低，用户越早看到模型开始回答。

注意：

- 它不是完整回答耗时。
- 它受到网络、排队、Prompt 长度、模型推理等因素影响。
- 如果应用在模型开始输出前还执行了检索和上下文组装，那么必须明确 TTFT 的起点是“整个 RAG 请求开始”还是“模型请求发出”。

建议同时记录：

- RAG 请求到首 Token 的时间。
- 模型请求发出到首 Token 的时间。

这样才能区分检索阶段与模型阶段的等待。

### 6.5 TPOT：平均输出 Token 间隔

TPOT = Time Per Output Token。

通常用于描述首 Token 之后，模型持续输出 Token 的平均间隔。

一种常见计算口径：

[\
TPOT =\
\frac{T\_{lastToken}-T\_{firstToken}}\
{N\_{outputTokens}-1}\
]

其中：

- (T\_{firstToken})：首 Token 到达时间。
- (T\_{lastToken})：最后一个 Token 到达时间。
- (N\_{outputTokens})：输出 Token 数量。

例如：

- 第一个 Token 到达：1.0 秒。
- 最后一个 Token 到达：5.0 秒。
- 输出 Token 数量：101。

[\
TPOT = \frac{5.0-1.0}{101-1}=0.04s\
]

平均每个后续 Token 间隔约 40ms。

注意：不同模型服务商、监控系统可能采用不同的 TPOT 统计口径。实际项目必须明确计算定义，不能直接比较口径不同的 TPOT。

### 6.6 P50、P95、P99 延迟

平均延迟不能完整反映用户体验。

假设 100 次请求耗时：

- 大多数请求 1～2 秒。
- 少数请求需要 10～20 秒。

平均值可能掩盖慢请求。

因此需要看分位数。

| 指标 | 含义                   | 关注点             |
| ---- | ---------------------- | ------------------ |
| P50  | 50% 请求耗时不超过该值 | 典型用户体验       |
| P95  | 95% 请求耗时不超过该值 | 较慢请求体验       |
| P99  | 99% 请求耗时不超过该值 | 极端慢请求与尾延迟 |

例如：

```
RAG 端到端延迟：

P50 = 2.1s
P95 = 7.8s
P99 = 13.5s
```

说明：

- 一半请求在 2.1 秒内完成。
- 95% 请求在 7.8 秒内完成。
- 最慢的 1% 请求可能超过 13.5 秒。

P95 和 P99 对生产系统尤其重要，因为少量慢请求可能影响用户体验和服务稳定性。

### 6.7 端到端延迟为什么不能简单相加？

最基本的定义是：

[\
E2E = t\_{responseComplete}-t\_{requestStart}\
]

其中：

- `requestStart`：请求进入系统的时间。
- `responseComplete`：完整响应返回应用或客户端的时间，必须明确选用哪一个边界。

不能简单认为：

[\
E2E = 检索耗时 + 生成耗时\
]

因为还可能存在：

- 网关和应用排队。
- 网络传输。
- 线程调度。
- 数据库连接池等待。
- 模型服务排队。
- 上下文组装。
- 响应序列化。
- 流式传输与客户端接收。
- 其他中间件处理。

更准确的做法是：以统一请求 Trace ID 关联各阶段 Span，记录每个阶段的开始、结束时间，同时保留完整请求的总耗时。

如果多个阶段并行执行，也不能简单把所有 Span 时长相加，否则会重复计算并行等待时间。

### 6.8 流式响应与非流式响应的统计区别

| 统计维度     | 非流式响应                     | 流式响应                       |
| ------------ | ------------------------------ | ------------------------------ |
| 首次可见内容 | 通常等完整响应返回             | 收到首 Token 后即可展示        |
| TTFT         | 可测，但用户通常看不到中间输出 | 是重要体验指标                 |
| 完整响应时间 | 可直接测量                     | 需要等最后一个 Token 或流结束  |
| TPOT         | 通常没有逐 Token 到达记录      | 可以统计                       |
| 主要体验指标 | 完整响应延迟                   | TTFT + 输出速度 + 完整响应时间 |

不要因为流式响应更早返回首 Token，就认为它的完整响应时间一定更短。

**流式改善的是首屏体验和输出过程的可感知性，不等于模型完成全部生成所需的时间必然减少。**

### 6.9 影响延迟的主要因素

| 因素            | 可能产生的影响                                        |
| --------------- | ----------------------------------------------------- |
| 并发量          | 线程池、连接池、模型服务排队增加                      |
| 网络状况        | 请求和响应传输变慢                                    |
| 模型服务负载    | 模型排队、推理速度下降                                |
| Prompt Token 数 | 输入越长，处理成本通常越高                            |
| 输出 Token 数   | 输出越长，完整生成时间通常越长                        |
| 检索 Top-K      | 候选数量增加，可能增加数据库和上下文处理成本          |
| Embedding 调用  | 远程 Embedding 服务会增加网络与模型耗时               |
| 数据库索引      | 索引、数据规模和查询计划影响检索性能                  |
| 冷启动          | JVM、连接池、缓存、模型服务预热等因素可能影响首批请求 |

性能测试应同时记录输入 Token、输出 Token、并发量和模型配置，否则不同实验之间的延迟不具备可比性。

## 七、指标分层表：哪些能离线测，哪些必须调用真实模型？

这是本次学习的重点交付。

### 7.1 完整指标分层表

| 层级   | 评测指标     | 无 API Key 能否评测    | 评测依据                                  | 成本与局限                                       |
| ------ | ------------ | ---------------------- | ----------------------------------------- | ------------------------------------------------ |
| 检索层 | Recall\@K    | 可以                   | 固定问题集、检索结果、人工相关性标注      | 无生成模型调用成本，但依赖标注质量               |
| 检索层 | HitRate\@K   | 可以                   | 检索结果与相关性标注                      | 计算成本低，无法体现命中数量和排序质量           |
| 检索层 | Precision\@K | 可以                   | Top-K 结果与相关性标注                    | 无生成模型调用成本                               |
| 引用层 | 引用真实性   | 可以                   | Source、Document、Version、Chunk 实际记录 | 可以验证结构真实性，不能证明语义支持性           |
| 引用层 | 引用可追溯性 | 可以                   | 引用映射与原始文档定位信息                | 可程序化验证定位链路，但不能证明内容支持回答     |
| 引用层 | 引用支持性   | 有条件                 | 原文与回答的人工核验，或真实模型辅助评判  | 需要回答样本；人工或模型评判有成本               |
| 引用层 | 引用完整性   | 有条件                 | 回答关键事实与引用证据的对应关系          | 需要先识别关键事实，不能只检查引用 ID            |
| 生成层 | 答案正确性   | 不能评测真实模型表现   | 真实模型回答与标准答案、证据核验          | 必须有真实生成结果；人工复核提高可信度           |
| 生成层 | 拒答质量     | 不能完整评测           | 真实模型回答与可回答性标注                | 需要真实模型决策结果，不能用模拟回答代替         |
| 系统层 | 检索耗时     | 可以                   | 本地实际检索链路计时                      | 无生成模型调用成本                               |
| 系统层 | 端到端延迟   | 有条件                 | 完整请求链路实际运行记录                  | 没有真实生成模型时，不能代表生产模型端到端延迟   |
| 系统层 | TTFT         | 有条件                 | 支持流式输出的实际请求                    | 需要真实流式生成环境才能评测真实模型 TTFT        |
| 系统层 | TPOT         | 有条件                 | 实际逐 Token 到达时间                     | 需要真实流式输出和明确统计口径                   |
| 系统层 | P50/P95/P99  | 可以，但要明确测量对象 | 多次实际运行的延迟样本                    | 可以统计本地检索分位数；不能把它当作真实生成延迟 |

### 7.2 四种评测方式必须区分

| 方式           | 怎么做                                                       | 优点                           | 局限                                             |
| -------------- | ------------------------------------------------------------ | ------------------------------ | ------------------------------------------------ |
| 人工标注       | 人工确认相关 Chunk、答案是否有证据、引用是否支持事实         | 对业务语义判断更可靠           | 人力成本高，标注标准必须统一                     |
| 程序自动计算   | 根据 Ground Truth 和实际结果计算 Recall、HitRate、Precision；校验引用 ID | 低成本、可重复、适合自动化回归 | 只能验证规则明确、可结构化的内容                 |
| 真实模型调用   | 使用实际模型执行生成，记录回答、引用、Token 和耗时           | 能反映真实生成链路             | 需要 API Key、模型额度和真实运行环境             |
| LLM-as-a-Judge | 使用模型判断答案正确性、引用支持性等                         | 可扩大评测规模、减少人工工作   | 裁判模型也会出错，存在偏差，不能直接视为绝对真值 |

### 7.3 无 API Key 不等于无法评测 RAG

没有 API Key，仍然可以完成大量有价值的工作：

**可以完成：**

- 使用固定问题集运行本地检索。
- 统计 Recall\@K。
- 统计 HitRate\@K。
- 统计 Precision\@K。
- 检查 Chunk ID、Document ID、Source ID 是否真实存在。
- 检查文档版本和 Chunk 归属关系。
- 测量关键词检索、向量检索和结果融合耗时。
- 统计本地检索链路的 P50、P95、P99。
- 分析漏召回、召回噪声、权限过滤等问题。

**不能据此宣称已经完成：**

- 真实模型答案正确性评测。
- 真实模型拒答质量评测。
- 真实模型引用支持性评测。
- 真实模型 TTFT、TPOT 评测。
- 真实生成链路的生产级端到端延迟评测。

如果没有真实模型，可以使用已经保存的真实历史回答做离线引用和答案分析，但必须标注这些回答的模型版本、生成时间和来源；不能把人工编写或模拟生成的答案伪装成真实模型输出。

## 八、检索与生成的因果边界

Recall\@K 只证明检索阶段找到了多少相关证据，不代表模型正确理解和使用了证据。

### 8.1 例子：检索正确，回答仍然错误

用户问题：

> GL-200 设备出现 E101，应该怎么处理？

Ground Truth：

```
C001：E101 的故障定义
C002：E101 的触发条件
C003：E101 的检查步骤
```

检索结果：

```
Top-5：
C001
C002
C003
C006
C007
```

假设相关 Chunk 全部找回：

[\
Recall\@5=100%\
]

但模型生成：

> E101 表示电机损坏，必须立即更换电机。

原始证据只说明启动异常和检查供电状态，并没有要求更换电机。

那么：

- 检索 Recall\@5：100%。
- 生成答案正确性：不通过。
- 引用支持性：不通过。
- 如果模型把无依据结论说成确定事实：属于生成幻觉。

这说明：

**检索质量和生成质量是因果链路上的不同环节，不能用一个指标代替另一个指标。**

### 8.2 常见失败类型

| 失败类型   | 所属环节      | 表现                             |
| ---------- | ------------- | -------------------------------- |
| 漏召回     | 检索          | 没有检索到正确故障手册           |
| 召回噪声   | 检索          | Top-K 返回大量无关设备资料       |
| 证据不足   | 知识库 / 检索 | 找到部分信息，但无法支持完整结论 |
| 引用错误   | 引用          | 引用 ID 指向错误 Chunk           |
| 引用不支持 | 引用 / 生成   | 原文存在，但无法支持回答事实     |
| 生成幻觉   | 生成          | 模型编造故障原因或维修步骤       |
| 错误拒答   | 生成          | 明明证据充分，却回答不知道       |
| 性能超时   | 系统          | 检索或模型响应超过预期时间       |

定位问题时，先判断失败发生在哪个环节，再决定应该优化什么。不能看到最终回答错误，就直接认定是检索出了问题。

## 九、评测集划分：避免测试集污染

评测集不能全部用于调参。

如果反复根据同一批测试问题修改检索参数、Prompt 和模型配置，最终指标会越来越贴合这批问题，却不一定代表真实泛化能力。

建议分为三部分：

| 数据集                        | 作用                                 | 是否用于反复调参     |
| ----------------------------- | ------------------------------------ | -------------------- |
| 开发集（Train / Development） | 设计评测脚本、检查标注规则、发现问题 | 可以                 |
| 验证集（Validation）          | 比较检索参数、Prompt 版本和系统配置  | 可以，但需要记录实验 |
| 测试集（Test）                | 最终独立评估，检验方案效果           | 不应该反复用于调参   |

对于当前规模不大的 M3 项目，可以先建立一个固定问题集，再从中划分开发集、验证集和测试集。

如果样本很少，必须如实说明统计结论的局限，不要把少量问题上的高分解释成普遍能力。

特别注意：

- 同一故障案例的改写版本不要随意分散到不同集合，否则可能造成信息泄漏。
- 同一设备、同一文档版本的高度相似问题，需要考虑分组划分。
- 测试集标注应在参数调优前固定。
- 测试集发生修改时，应记录数据集版本。

## 十、Java RAG 工程实现思路

技术基线：

```
JDK 21
Spring Boot 3.5.16
Spring AI 1.1.8
PostgreSQL 18.7
pgvector 0.8.7
```

这里关注的是评测数据采集和计时边界，不扩展到其他 RAG 功能实现。

### 10.1 统一评测记录

建议为每次 RAG 请求生成唯一 `traceId`，把检索、生成、引用校验和最终评测结果关联起来。

可以设计如下记录：

| 字段                  | 含义                   |
| --------------------- | ---------------------- |
| trace_id              | 请求追踪 ID            |
| question_id           | 评测问题 ID            |
| dataset_version       | 问题集版本             |
| retrieval_config      | 检索参数配置           |
| retrieved_chunk_ids   | 实际检索结果           |
| retrieval_latency_ms  | 检索耗时               |
| model_name            | 实际模型名称           |
| model_version         | 模型版本或服务标识     |
| prompt_version        | Prompt 版本            |
| input_tokens          | 输入 Token 数          |
| output_tokens         | 输出 Token 数          |
| answer                | 实际模型回答           |
| citation_ids          | 回答中的引用 ID        |
| generation_latency_ms | 生成阶段耗时           |
| ttft_ms               | 首 Token 延迟          |
| tpot_ms               | 平均输出 Token 间隔    |
| end_to_end_latency_ms | 端到端耗时             |
| citation_check_result | 引用结构校验结果       |
| answer_evaluation     | 答案评测结果           |
| abstention_evaluation | 拒答评测结果           |
| evaluation_status     | 已验证、待验证、未执行 |

不一定要把所有字段放在同一张数据库表中。可以根据实际项目采用请求主表、检索明细表、引用明细表和评测结果表。

关键是保证它们可以通过 `traceId`、`questionId` 和数据集版本关联起来。

### 10.2 Java 计时：使用 System.nanoTime()

测量代码运行耗时，应使用单调时间源，而不是直接用系统日期时间计算时间差。

示例：

```
long start = System.nanoTime();

try {
    List<Document> documents = vectorStore.similaritySearch(searchRequest);
    return documents;
} finally {
    long elapsedNanos = System.nanoTime() - start;
    long elapsedMillis = elapsedNanos / 1_000_000;

    log.info("retrieval_latency_ms={}", elapsedMillis);
}
```

说明：

- `System.nanoTime()` 适合测量时间间隔。
- `System.currentTimeMillis()` 适合记录墙上时钟时间，例如事件发生时间。
- 不要用两个 `currentTimeMillis()` 的差值替代高精度耗时测量。
- 计时范围应覆盖你定义的完整检索阶段。

实际项目还应分别记录关键词检索、向量检索、结果融合和上下文组装耗时。

### 10.3 检索计时与生成计时分开

推荐采用如下结构：

```
traceId
  |
  +-- query_process_ms
  |
  +-- embedding_ms
  |
  +-- keyword_search_ms
  |
  +-- vector_search_ms
  |
  +-- fusion_ms
  |
  +-- context_assembly_ms
  |
  +-- model_request_ms
  |
  +-- generation_ms
  |
  +-- citation_validation_ms
  |
  +-- end_to_end_ms
```

这里的阶段名称是建议的业务计时项，不意味着 Spring AI 会自动为每一个自定义业务阶段生成对应指标。

### 10.4 Spring AI 1.1.8 的观测能力

Spring AI 提供基于 Spring 生态观测体系的 Metrics 和 Tracing 能力，覆盖 ChatClient、ChatModel、EmbeddingModel、VectorStore 等核心组件。

其中：

- ChatClient 可以观测 `call()` 和 `stream()` 操作。
- ChatModel 可以观测模型执行耗时。
- EmbeddingModel 可以观测 Embedding 操作。
- VectorStore 可以观测向量存储操作。
- ChatModel 的响应元数据在提供商支持时可以包含模型信息和 Token 使用量。

但需要注意：

**框架组件观测数据不等于整个业务 RAG 请求的端到端指标。**

例如，ChatClient 的调用耗时不一定包含此前的检索、上下文组装和网关等待。因此，仍然需要在业务入口建立自己的完整计时和 Trace 关联。

### 10.5 引用校验的数据关系

可以用以下关系理解引用真实性检查：

```
Citation
   |
   v
Source
   |
   v
Document
   |
   v
Document Version
   |
   v
Chunk
```

程序应校验：

1. 引用记录是否存在。
2. Source 是否存在。
3. Document 是否存在。
4. Version 是否存在。
5. Chunk 是否存在。
6. Chunk 是否属于对应 Document 和 Version。
7. Chunk 内容是否与实际引用内容一致。

如果某个引用记录指向已经删除或失效的 Chunk，不能只因为 Citation ID 存在就判定通过。

### 10.6 指标采集与监控

Spring Boot 3.5 的 Actuator 和 Micrometer 可以用于指标采集。

建议关注：

```
rag.retrieval.duration
rag.generation.duration
rag.request.duration
rag.citation.validation.duration
rag.retrieval.result.count
rag.generation.input.tokens
rag.generation.output.tokens
rag.request.error
```

这些是建议的业务指标命名，不代表框架自动提供了所有这些指标。

对于耗时指标，应使用 Timer 或直方图等适合统计延迟分布的方式，按统一时间窗口统计 P50、P95、P99。

注意：

- 不要把 `questionId`、`traceId`、用户 ID 等高基数值直接作为 Prometheus 指标标签。
- 这类信息更适合保存在日志、Trace 或评测明细中。
- 指标标签优先使用低基数维度，例如环境、模型类型、检索策略。

## 十一、最小可执行 RAG 评测方案

本阶段建议先完成离线评测闭环，再接入真实生成模型验证生成层。

### 11.1 第一步：建立固定问题集

建议先覆盖四类设备故障问题：

| 类型     | 问题示例                     | 评测关注点                 |
| -------- | ---------------------------- | -------------------------- |
| 故障码   | E101 是什么意思？            | 精确故障证据是否召回       |
| 设备型号 | GL-200 无法启动怎么办？      | 是否检索到正确型号资料     |
| 技术术语 | 电机运行时出现异常振动       | 专业术语证据是否召回       |
| 口语表达 | 机器一开机就哆嗦，声音特别大 | 非标准表达是否找到对应知识 |

同时增加证据不足问题：

| 问题类型     | 问题示例                     | 预期行为             |
| ------------ | ---------------------------- | -------------------- |
| 未收录故障码 | E999 是什么原因？            | 证据不足时拒答       |
| 未收录设备   | 某未知型号设备如何维修？     | 拒答或请求补充资料   |
| 部分证据     | 找到故障定义，但没有维修步骤 | 仅回答证据支持的部分 |

每道题都要标注：

- 问题 ID。
- 相关 Chunk ID。
- 相关 Document ID。
- 可回答性。
- 预期回答或拒答行为。
- 必须引用的证据。

### 11.2 第二步：执行离线检索评测

对固定问题集执行真实检索链路。

保存：

```
question_id
query
retrieved_chunk_ids
retrieved_document_ids
retrieval_config
retrieval_latency_ms
```

根据 Ground Truth 自动计算：

```
Recall@K
HitRate@K
Precision@K
```

要求：

- 所有实验使用相同问题集。
- Ground Truth 版本固定。
- K 值固定。
- 检索结果完整保存。
- 不要只保存最后的平均分。

### 11.3 第三步：验证引用真实性和可追溯性

不需要生成模型，也可以针对已有引用映射或历史回答中的引用执行结构校验。

检查：

```
Source ID 是否存在
Document ID 是否存在
Document Version 是否存在
Chunk ID 是否存在
Chunk 是否属于对应 Document
Chunk 是否属于对应 Version
```

输出：

```
citation_authenticity_pass
citation_traceability_pass
citation_invalid_count
citation_missing_count
```

这一步只能证明引用结构和定位关系，不证明引用支持回答。

### 11.4 第四步：有真实模型时评测生成质量

调用真实模型，保存原始生成结果：

```
question_id
trace_id
model_name
model_version
prompt_version
retrieved_chunk_ids
answer
citation_ids
input_tokens
output_tokens
```

再执行：

- 答案事实正确性核验。
- 引用支持性核验。
- 引用完整性核验。
- 正确拒答率。
- 误拒答率。
- 可回答问题回答决策率。
- 可回答问题答案正确率。
- 证据不足时无依据回答率。

如果模型没有调用成功，应标记为未执行或调用失败，不能把空结果当成拒答。

### 11.5 第五步：测量性能

至少记录：

```
retrieval_latency_ms
generation_latency_ms
end_to_end_latency_ms
ttft_ms
tpot_ms
input_tokens
output_tokens
```

根据多次实际运行统计：

```
P50
P95
P99
```

建议分别记录：

- 冷启动阶段。
- 稳定运行阶段。
- 不同并发量。
- 不同输入 Token 数量。
- 不同输出长度。

流式与非流式请求应分开统计，避免混在同一组数据中。

### 11.6 第六步：失败案例分类

每个失败问题都应归类，而不是只记录“评测不通过”。

| 失败标签              | 说明                 | 优先排查方向             |
| --------------------- | -------------------- | ------------------------ |
| MISS_RECALL           | 相关证据没有召回     | 检索策略、索引、查询表达 |
| NOISE_RETRIEVAL       | 返回大量无关证据     | 检索精度、过滤条件       |
| INSUFFICIENT_EVIDENCE | 知识库证据不足       | 知识库覆盖与标注         |
| INVALID_CITATION      | 引用 ID 或映射错误   | 引用数据结构             |
| UNSUPPORTED_CITATION  | 引用不能支持回答     | 证据与回答对应关系       |
| INCOMPLETE_CITATION   | 关键事实缺少必要引用 | 引用完整性               |
| HALLUCINATION         | 模型给出无依据结论   | 生成与证据约束           |
| FALSE_ABSTENTION      | 证据充分却错误拒答   | 拒答决策                 |
| LATENCY_TIMEOUT       | 请求耗时超出限制     | 检索、模型、网络与并发   |

### 11.7 第七步：输出评测报告

报告必须区分三种结论：

**A. 已验证结论**

例如：

```
已完成固定问题集的离线检索评测。
已根据人工标注计算 Recall@K、HitRate@K、Precision@K。
已完成引用 ID 和 Chunk 归属关系校验。
已记录本地检索链路耗时。
```

**B. 尚未验证结论**

例如：

```
尚未验证模型生成的答案是否正确。
尚未验证模型是否会在证据不足时正确拒答。
尚未验证回答中的引用是否真正支持关键事实。
```

**C. 需要真实模型才能验证的结论**

例如：

```
真实模型答案正确性。
真实模型拒答质量。
真实模型 TTFT 和 TPOT。
真实模型生成链路端到端延迟。
```

没有真实模型调用时，只能输出离线评测结果，不得使用模拟生成结果冒充真实模型测试。

## 十二、评测结果的可追溯性

一份合格的评测报告，不应该只有几项百分比。

至少要能回答：

- 哪一道题失败？
- 使用了哪一版问题集？
- 使用了什么检索参数？
- 实际返回了哪些 Chunk？
- 当时的模型和 Prompt 版本是什么？
- 模型实际生成了什么回答？
- 引用了哪些证据？
- 每个阶段耗时是多少？
- 最终评测结论是什么？
- 结论由人工、程序还是模型裁判得出？

建议每次实验保存以下信息：

```
experiment:
  experiment_id: M3-EVAL-001
  dataset_version: v1
  corpus_version: kb-v1
  test_date: "实际执行日期"

retrieval:
  strategy: "实际检索策略"
  top_k: 5
  config_version: "实际配置版本"

generation:
  model_name: "实际模型名称或 null"
  model_version: "实际模型版本或 null"
  prompt_version: "实际 Prompt 版本或 null"

metrics:
  recall_at_k: "实际计算值或 null"
  hit_rate_at_k: "实际计算值或 null"
  precision_at_k: "实际计算值或 null"
  citation_authenticity: "实际校验结果或 null"
  citation_support: "实际核验结果或 null"
  answer_accuracy: "实际评测值或 null"
  correct_abstention_rate: "实际评测值或 null"
  false_abstention_rate: "实际评测值或 null"
  retrieval_p50_ms: "实际测量值或 null"
  retrieval_p95_ms: "实际测量值或 null"
  e2e_p50_ms: "实际测量值或 null"
  e2e_p95_ms: "实际测量值或 null"

evaluation:
  status: "OFFLINE_ONLY / REAL_MODEL_TESTED / PARTIALLY_TESTED"
  limitations:
    - "填写尚未验证的指标"
```

以上只是记录结构示例，不代表已经执行过实验。没有测量的数据必须填写 `null` 或明确标记为未执行，不得编造数字。

## 十三、三个重点思考题

### 思考题 1：为什么不能只用 Recall\@K 衡量 RAG 好坏？检索命中了相关文档，为什么生成模型仍可能给出错误答案？

**第一，Recall\@K 只衡量检索覆盖程度。**

例如：

用户询问：

> E101 故障码应该如何处理？

Ground Truth 有三个相关 Chunk：

```
C001：故障码定义
C002：故障触发条件
C003：故障处理步骤
```

检索 Top-5 找回了全部三个 Chunk：

[\
Recall\@5=100%\
]

这只能证明相关证据被检索出来。

**第二，模型可能没有正确理解证据。**

例如，C002 说明 E101 可能由供电异常引起，模型却将其解释成电机损坏。

检索正确，但语义理解错误。

**第三，模型可能遗漏关键证据。**

即使三个 Chunk 都进入上下文，模型也可能只使用 C001 的故障定义，忽略 C003 的处理限制。

**第四，模型可能产生证据之外的结论。**

例如，手册只要求检查电源状态，模型却建议直接更换电机。

这属于无依据生成。

**第五，引用也可能不正确。**

模型可能引用了真实存在的 C001，但 C001 并不能支持“更换电机”这一结论。

因此，完整评测至少需要分开检查：

| 层级 | 评测问题                         |
| ---- | -------------------------------- |
| 检索 | 是否找到相关证据？               |
| 引用 | 引用是否真实、可追溯、支持回答？ |
| 生成 | 最终事实是否正确？               |
| 拒答 | 证据不足时是否避免编造？         |
| 系统 | 请求是否足够快、稳定？           |

**结论：Recall\@K 是检索质量指标，不是完整 RAG 质量指标。**

### 思考题 2：没有 API Key、不能调用真实模型时，哪些评测可以完成？哪些不能完成？如何设计低成本离线评测方案？

可以完成的工作比很多人想象的多。

**第一，建立固定问题集和 Ground Truth。**

由人工标注：

- 相关 Chunk。
- 相关 Document。
- 证据是否充分。
- 预期回答或拒答行为。

这一步不需要 API Key。

**第二，运行真实的本地检索链路。**

使用现有 PostgreSQL 和 pgvector 环境执行检索，保存 Top-K 结果。

然后计算：

[\
Recall\@K,\quad HitRate\@K,\quad Precision\@K\
]

这是真实检索结果，不是模拟结果。

**第三，执行引用结构校验。**

查询实际数据库记录，检查：

- Source ID。
- Document ID。
- Document Version。
- Chunk ID。
- 归属关系。

可以完成引用真实性和可追溯性检查。

**第四，执行本地性能测试。**

可以测量：

- 查询处理耗时。
- Embedding 耗时（如果使用本地 Embedding 模型）。
- PostgreSQL 检索耗时。
- 向量检索耗时。
- 结果融合耗时。
- 上下文组装耗时。

如果没有真实生成模型，不能把本地检索耗时当作完整 RAG 端到端耗时。

**第五，明确不能完成的评测。**

没有真实生成模型结果，就不能验证：

- 真实模型答案正确性。
- 真实模型拒答质量。
- 真实模型引用支持性。
- 真实模型 TTFT、TPOT。
- 真实模型完整生成链路延迟。

低成本方案可以总结为：

```
固定问题集
   |
   v
人工标注 Ground Truth
   |
   v
本地真实检索
   |
   v
自动计算 Recall / HitRate / Precision
   |
   v
程序校验引用 ID 和映射关系
   |
   v
测量本地检索耗时
   |
   v
输出离线评测报告
```

**结论：没有 API Key，仍然能够完成可靠的检索层和引用结构层离线评测；但不能声称完成真实生成质量和真实模型性能评测。**

### 思考题 3：为什么拒答质量必须双向统计？如果只统计“该拒的拒了”，为什么可能出现所有问题都拒答、指标却看起来很好的情况？

因为 RAG 不只是要避免幻觉，还必须在证据充分时正常回答。

假设有 100 道问题：

```
证据充分：40 道
证据不足：60 道
```

模型对 100 道问题全部拒答。

那么：

```
正确拒答：60 道
错误拒答：40 道
```

正确拒答率：

[\
\frac{60}{60}=100%\
]

但误拒答率：

[\
\frac{40}{40}=100%\
]

如果只统计正确拒答率，模型看起来达到 100%，实际上它没有回答任何一道有充分证据的问题。

所以必须双向统计：

- 证据不足时，模型是否正确拒答？
- 证据充分时，模型是否错误拒答？
- 证据充分且模型回答时，答案是否事实正确？
- 证据不足但模型回答时，是否出现无依据结论？

**结论：正确拒答和正确回答是两个方向的能力，拒答评测必须同时检查它们。**

## 十四、常见误区与纠正

| 常见误区                               | 正确理解                                   |
| -------------------------------------- | ------------------------------------------ |
| Recall\@K 高，说明 RAG 效果好          | 只说明检索覆盖较好，不代表生成正确         |
| HitRate\@K 高，说明检索结果都相关      | HitRate 只要求至少命中一个相关结果         |
| Precision\@K 和 Recall\@K 一样         | 一个关注结果纯度，一个关注相关证据覆盖     |
| 找到正确 Document 就代表找到了正确证据 | Document 级命中不代表 Chunk 级命中         |
| 引用 ID 存在就代表引用正确             | 还需要可追溯、支持性和完整性检查           |
| 模型拒答越多越安全                     | 过度拒答会损害可回答问题的服务能力         |
| 正确拒答率高就代表拒答质量好           | 还必须检查误拒答率和答案正确性             |
| 平均延迟低就代表用户体验好             | 还需要看 P95、P99 和流式首 Token 体验      |
| TTFT 就是完整响应时间                  | TTFT 只衡量首 Token 到达时间               |
| 检索耗时就是端到端耗时                 | 端到端还包括模型、网络、排队和其他环节     |
| 没有 API Key 就无法评测 RAG            | 检索、引用结构和本地性能仍然可以离线评测   |
| LLM-as-a-Judge 就是真实标签            | 模型裁判只能辅助判断，重要结论需要人工核验 |

## 十五、本阶段最终掌握标准

完成本主题后，应该能够独立回答：

1. Recall\@K、HitRate\@K、Precision\@K 分别衡量什么？
2. 为什么 Chunk 级评测和 Document 级评测可能得出不同结果？
3. 为什么引用 ID 存在不能证明引用支持回答？
4. 引用真实性、可追溯性、支持性、完整性分别如何验证？
5. 为什么拒答质量必须同时统计正确拒答率和误拒答率？
6. 为什么正确回答决策不等于答案事实正确？
7. TTFT、TPOT、P50、P95、P99 分别是什么？
8. 为什么端到端延迟不能简单等于检索耗时加生成耗时？
9. 没有 API Key 时，哪些指标可以通过真实本地检索完成？
10. 为什么没有真实生成模型，不能声称完成真实拒答质量和生成质量评测？

最终应形成以下认知：

```
检索质量：
Recall@K / HitRate@K / Precision@K

引用质量：
真实性 / 可追溯性 / 支持性 / 完整性

生成质量：
答案正确性 / 正确拒答 / 误拒答 / 无依据回答

系统性能：
检索耗时 / 生成耗时 / E2E / TTFT / TPOT / P50 / P95 / P99
```

**最终验收原则：任何评测结论都必须明确它验证的是哪个层级、基于什么数据、使用什么评测方式，以及还有哪些能力没有被验证。**
