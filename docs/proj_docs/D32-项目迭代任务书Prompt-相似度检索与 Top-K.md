## 4. 核心实施需求

### 4.1 Query Embedding

实现用户问题的向量化：

1. 接收用户输入的自然语言问题。
2. 使用与 D31 入库阶段一致的 Embedding 模型及配置。
3. 生成 384 维 Query Embedding。
4. 对空问题、超长问题、Embedding 调用失败、返回向量为空或维度不符等情况进行必要校验和错误处理。
5. 确保 Query Embedding 与入库向量处于同一模型及向量空间。

必须从实际配置和代码确认模型一致性，不能仅因维度相同就认定模型兼容。不得在 D32 擅自切换模型、模型版本或向量维度。

### 4.2 Spring AI VectorStore 相似度检索

基于现有 Spring AI 1.1.8 和 PgVectorStore 实现相似度检索。

要求：

- 默认返回 Top-5。
- Top-K 参数如需开放，设置合理边界，避免任意大值造成资源消耗；默认值必须为 5。
- 复用已有 VectorStore Bean 和数据库配置。
- 明确实际使用的距离度量和排序方向。
- 只检索允许参与检索的有效文档版本，具体过滤方式必须以现有数据结构和实现能力为依据。
- 返回结果按实际相似度检索顺序排列。
- 对无结果、输入异常、Embedding 服务异常、数据库异常等情况提供清晰处理。
- 不重复实现 D31 的向量入库、更新、删除和幂等逻辑。

核实 Spring AI 1.1.8 当前依赖版本下 VectorStore.similaritySearch 的真实调用方式、SearchRequest 参数和返回对象语义。不得照搬其他版本 API。

### 4.3 检索结果与来源信息

检索结果至少应能表达：

- Chunk 内容或检索片段。
- 来源文档标识。
- Chunk 标识（若现有结构提供）。
- 文档版本（若现有结构提供）。
- 实际存在且有用的来源信息。
- 相似度分数或距离信息（仅在底层适配器实际支持并能准确解释时返回）。

关于分数：

1. 检查 Spring AI 1.1.8 与当前 PgVectorStore 适配器的真实返回字段和语义。
2. 明确区分 similarity score、distance 和其他内部数值。
3. 不得将 distance 直接标记为 similarity。
4. 不得自行构造、归一化或编造分数。
5. 如果适配器未暴露可用分数，结果中明确说明当前能力限制，不返回虚假分数。

来源字段必须来自真实 Chunk 元数据或现有业务关联关系。不存在的字段不得臆造；如确实缺少关键来源信息，先报告最小数据结构改造建议，经现有架构评估后实施。

### 4.4 元数据过滤

根据 D31 已有元数据结构验证过滤能力。

执行要求：

1. 先检查实际写入向量记录的 metadata 内容和字段类型。
2. 选择真实存在、具有业务意义的字段进行过滤验证。
3. 使用 Spring AI 1.1.8 支持的 FilterExpression/API 形式。
4. 验证过滤条件是否真正下推并生效，不能只验证代码能够编译。
5. 对过滤前后的结果数量、来源和文档版本进行核对。
6. 如果当前元数据不足以支持目标过滤，明确记录缺失字段和最小改造方案，不得虚构字段或伪造过滤成功。

不得在本次任务中无边界扩展元数据体系。

### 4.5 检索接口与工程实现

根据 D32 现有工程结构，设计最小可用的检索入口，可以是现有业务接口的扩展或独立检索接口。

至少明确：

- 请求参数：用户问题及可选 Top-K、过滤条件（仅开放已验证支持的字段）。
- 响应结构：问题、检索结果列表、来源信息、可用的真实分数及必要的执行信息。
- 参数校验和异常处理。
- 不将数据库实体或框架内部对象无约束地直接暴露为 API DTO。

## 5. 十个真实业务问题与人工相关性评估

至少准备 10 个真实业务问题，问题应来自当前知识库实际覆盖的业务领域，优先选择设备故障、设备型号、故障代码、维修处理、工单分类等真实主题。

不得编造知识库中不存在的设备、故障代码、维修结论或文档内容。

每个问题执行实际 Top-5 检索，并保存完整结果。对每条返回片段逐条人工标注：

- 相关：片段能够直接或实质性帮助回答该问题。
- 不相关：片段与问题主题无关，或不能提供有效证据。
- 如有必要，可增加“部分相关”作为分析备注，但统计口径必须明确，不能混淆相关/不相关计数。

建议建立检索评估记录：

| 问题 | Top-5 结果 | 相关片段 | 噪声 | 漏召回 | 备注 |
|---|---|---|---|---|---|
| Q1 | 记录实际返回的 Chunk ID、来源及内容摘要 | 人工标注相关项 | 记录不相关项 | 记录已知应召回但未出现的内容 | 分析原因 |
| Q2–Q10 | 按 Q1 格式逐条记录 | 同上 | 同上 | 同上 | 同上 |

评估要求：

1. 至少 10 个问题，每个问题保存实际 Top-5 结果。
2. 每条结果必须保留可追溯 Chunk ID 或现有等价标识。
3. 人工标注不得由模型自动生成后冒充人工结论。
4. 对漏召回，必须先有可核对的相关目标片段或业务依据；无法确认时标记“待确认”，不得随意声称漏召回。
5. 记录检索噪声、漏召回及可能原因，例如问题表达与原文差异、切块边界、Embedding 表达能力、元数据过滤、知识库覆盖不足等。
6. 评估结果必须保留在 `docs\evidence\D32`，并在技术文档中总结。

如果当前知识库内容不足以形成 10 个有意义的真实业务问题，必须报告覆盖不足及影响，不得用虚构数据凑数。
