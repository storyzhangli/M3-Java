# M3 知识笔记：关键词检索、向量检索、混合检索与查询改写

> **学习目标**：理解不同检索方式的能力边界，掌握 RRF 融合与查询改写的基本原理，能够针对设备故障问答场景设计对照实验，并通过数据判断优化方案是否值得引入。
>
> **技术基线**：JDK 21 / Spring Boot 3.5.16 / Spring AI 1.1.8 / PostgreSQL 18.7 / pgvector 0.8.7  
> **范围约束**：本文不展开 Rerank、Agent、Tool Calling、MCP 等后续主题。

---

## 一、先建立整体认识：不同检索方式解决不同问题

假设设备工程师向知识库提问：

> GL-200 设备运行一段时间后，电机附近出现明显异响和振动，应该怎么排查？

知识库中可能存在以下内容：

1. `GL-200 电机异常振动故障排查手册`
2. `E101 故障码处理说明`
3. `电机轴承磨损与振动异常分析`
4. `泵体运行噪声诊断规范`
5. `GL-200 设备维护保养手册`

不同检索方式的侧重点不同：

| 检索方式   | 主要解决的问题                             |
| ---------- | ------------------------------------------ |
| 关键词检索 | 用户输入的词语、编号、型号是否出现在文档中 |
| 向量检索   | 用户问题与文档内容在语义上是否接近         |
| 混合检索   | 同时利用精确词项匹配和语义相似性           |
| 查询改写   | 将不利于检索的口语表达转成更适合检索的查询 |

核心原则：

- 故障码、设备型号、零件编号：先保证精确匹配。
- 专业术语、同义表达：根据词项匹配情况选择关键词或向量检索。
- 口语化、描述不完整的问题：重点评估查询改写与向量检索。
- 混合检索：只有在两路检索能够互补、并且实验结果证明有收益时才引入。

**不存在适用于所有问题的最优检索方式。**

## 二、关键词检索：Sparse Retrieval

### 2.1 倒排索引是什么

关键词检索通常依赖倒排索引（Inverted Index）。

传统方式是逐篇文档检查是否包含查询词；倒排索引则反过来记录：

> 某个词出现在哪些文档中，以及出现的位置、次数等信息。

三个基础概念：

| 概念         | 含义                     | 示例                        |
| ------------ | ------------------------ | --------------------------- |
| Term         | 被索引的词项             | 电机、振动、E101            |
| Document     | 被检索的文档单元         | Chunk-001、Chunk-002        |
| Posting List | 某个词对应的文档记录列表 | 电机 → Chunk-001、Chunk-005 |

例如，知识库有三个 Chunk：

```text
Chunk-001：GL-200 电机出现异常振动，需要检查轴承。
Chunk-002：E101 表示电机过载，请检查负载和供电。
Chunk-003：设备运行时出现明显噪声，可能与轴承磨损有关。
```

构建倒排索引后，可以得到简化结构：

```text
电机
  ├── Chunk-001
  └── Chunk-002

振动
  └── Chunk-001

E101
  └── Chunk-002

轴承
  ├── Chunk-001
  └── Chunk-003

噪声
  └── Chunk-003
```

当用户搜索 `E101` 时，系统可以直接定位包含该词项的文档，而不必逐篇扫描全部文档。

### 2.2 BM25 的基本评分逻辑

BM25 是经典的词项相关性排序算法。

它不是简单地统计查询词出现了多少次，而是综合考虑：

1. 词频 TF（Term Frequency）
2. 逆文档频率 IDF（Inverse Document Frequency）
3. 文档长度归一化
4. 算法参数对词频饱和程度和长度影响的控制

**① TF：词频**

某个查询词在文档中出现得越多，通常意味着该文档与查询越相关。

例如搜索：

```text
电机 振动
```

文档 A：

```text
电机振动故障排查。
```

文档 B：

```text
电机振动异常时，应检查电机底座、电机轴承和电机固定螺栓。
```

文档 B 对查询词的覆盖更多，可能获得更高的相关性得分。

但词频不是无限增长就无限增加分数。BM25 使用词频饱和机制，避免重复堆积同一个词导致分数不合理地增长。

**② IDF：逆文档频率**

一个词在整个知识库中越少见，通常越有区分价值。

例如：

- “设备”：大量文档都有。
- “电机”：部分文档有。
- “E101”：可能只有少数文档有。

`E101` 的区分能力通常更强。

BM25 会利用词项在整个文档集合中的分布情况计算 IDF。

**③ 文档长度归一化**

较长的文档天然更容易包含查询词。

如果不考虑文档长度，长文档可能仅仅因为包含更多词，就获得不合理的高分。

BM25 通过文档长度归一化，降低这种偏差。

**④ BM25 的参数**

常见实现中会有：

- `k1`：控制词频饱和程度。
- `b`：控制文档长度归一化程度。

不同搜索引擎和实现可能有各自的默认值与配置方式，不应把某个组件的默认值当成 BM25 的统一标准。

### 2.3 BM25 适合什么场景

特别适合：

- 故障码：E101、F203、P001。
- 设备型号：GL-200、MX-500。
- 零件编号：MTR-001、BRG-6204。
- 专业术语：变频器过流、轴承磨损、液压压力异常。
- 手册标题、规范名称、明确的技术词汇。

例如：

用户：

```text
E101 故障码怎么处理？
```

知识库：

```text
E101：电机过载保护触发。
处理步骤：
1. 检查设备负载。
2. 检查电机供电。
3. 检查电机运行电流。
```

关键词检索能够利用 `E101` 直接定位对应内容。

### 2.4 BM25 的局限

关键词检索依赖词项匹配。

假设用户输入：

```text
机器运行的时候一直抖。
```

知识库内容：

```text
设备运行过程中发生异常振动，建议检查电机底座、轴承和联轴器。
```

用户没有输入“异常振动”，文档也未必出现“抖”这个词。

如果分词和词项没有建立有效关联，BM25 可能无法充分召回这段内容。

因此：

**关键词检索擅长回答“有没有出现这些词”，但不擅长独立理解“这些话是不是表达了同一个意思”。**

## 三、向量检索：Dense Retrieval

### 3.1 Query Embedding 与 Document Embedding

向量检索通过 Embedding 模型将文本转换为向量。

例如：

```text
用户问题：
设备运行时出现异常振动
```

经过 Embedding 模型：

```text
Query Embedding：
[0.12, -0.35, 0.78, ...]
```

知识库中的 Chunk：

```text
电机运行过程中出现明显抖动，应检查轴承磨损。
```

经过相同或兼容的 Embedding 模型：

```text
Document Embedding：
[0.11, -0.31, 0.75, ...]
```

然后计算两个向量之间的相似程度或距离。

一般流程：

```text
用户问题
   │
   ▼
Embedding 模型
   │
   ▼
Query Vector
   │
   ▼
向量索引 / 向量数据库
   │
   ▼
相似度或距离计算
   │
   ▼
Top-K 候选 Chunk
```

知识库构建阶段：

```text
原始文档
   │
   ▼
文档解析
   │
   ▼
Chunk 切分
   │
   ▼
Embedding 模型
   │
   ▼
Document Vector
   │
   ▼
pgvector 存储和索引
```

### 3.2 为什么向量检索能理解同义表达

Embedding 模型会根据训练过程中学习到的语言表示，将语义相近的文本映射到相近的向量区域。

例如：

```text
设备运行时出现异常振动
机器运行时一直抖动
设备工作时产生明显震动
```

三句话虽然词语不同，但语义可能比较接近。

因此，向量检索有机会召回包含以下内容的 Chunk：

```text
电机运行时出现异常振动，需检查轴承磨损和底座固定情况。
```

这正是向量检索相对关键词检索的重要优势。

### 3.3 为什么向量距离接近不等于业务语义完全匹配

向量相似度只是模型对文本语义表示的近似结果，不是业务规则验证。

例如：

```text
GL-200 电机故障
GL-200 电机正常维护
```

两句话包含相同设备和相似主题，Embedding 可能认为它们比较接近。

但用户要查询的是故障处理，正常维护内容未必能解决问题。

再例如：

```text
E101：电机过载
E102：电机欠压
```

它们都是电机故障码，语义接近，但故障原因和处理流程可能完全不同。

所以：

- 向量相似度高，不代表故障码相同。
- 向量距离近，不代表设备型号匹配。
- 语义相关，不代表内容可以直接作为答案依据。

**对于故障码和设备型号，不能只依赖 Embedding。**

### 3.4 pgvector 的距离方向必须注意

pgvector 常见操作符：

| 操作符 | 含义                   | 排序方向             |
| ------ | ---------------------- | -------------------- |
| `<->`  | L2 欧氏距离            | 越小越近             |
| `<=>`  | Cosine Distance        | 越小越近             |
| `<#>`  | Negative Inner Product | 越小通常表示内积越大 |

以余弦距离为例：

```sql
SELECT
    id,
    content,
    embedding <=> :query_vector AS distance
FROM vector_store
ORDER BY embedding <=> :query_vector
LIMIT 5;
```

这里排序是 `ASC`，因为距离越小越近。

如果应用层想表达余弦相似度，可以根据所采用的定义转换，例如：

```text
cosine_similarity = 1 - cosine_distance
```

但必须确认当前使用的距离定义和数据类型。

不要把所有向量检索接口返回的 `score` 都理解为“越大越相关”。不同后端可能返回相似度，也可能返回距离。

## 四、关键词检索与向量检索对比

| 对比维度   | 关键词检索（BM25）   | 向量检索               |
| ---------- | -------------------- | ---------------------- |
| 核心依据   | 词项匹配与统计评分   | 语义向量相似度         |
| 故障码     | 擅长精确匹配         | 可能漏召回或语义误匹配 |
| 设备型号   | 擅长精确匹配         | 对字母数字组合不稳定   |
| 零件编号   | 擅长精确匹配         | 不适合单独承担精确匹配 |
| 技术术语   | 擅长精确术语         | 擅长同义和语义表达     |
| 口语化问题 | 字面不匹配时效果有限 | 通常更有优势           |
| 同义表达   | 依赖词项重合         | 通常更有优势           |
| 主要局限   | 语义理解不足         | 精确字符匹配不稳定     |

### 4.1 四个典型案例

**案例一：搜索故障码 E101**

用户：

```text
E101 故障码怎么处理？
```

优先方案：

1. 从问题中提取故障码 `E101`。
2. 查询故障码结构化字段。
3. 同时可以执行关键词检索。
4. 必要时再用向量检索补充相关说明。

原因：

故障码属于精确业务标识，不能把 E101 和 E102 当成相近故障处理。

**案例二：搜索设备型号 GL-200**

用户：

```text
GL-200 设备电机怎么维护？
```

优先方案：

1. 提取型号 `GL-200`。
2. 通过结构化字段过滤或精确匹配锁定设备。
3. 在该设备范围内进行关键词或向量检索。

原因：

不能仅仅因为 GL-200 和 GL-300 都是设备型号，就认为它们的维修资料可以互换。

**案例三：搜索技术术语**

用户：

```text
变频器过流怎么排查？
```

如果知识库明确使用“变频器过流保护”，关键词检索可能已经足够。

如果知识库还使用“驱动器输出电流异常”“逆变单元过电流”等表达，向量检索或混合检索可能更有价值。

**案例四：口语化故障描述**

用户：

```text
机器运行一会儿就开始抖，还伴随着异响。
```

优先考虑：

- 保留原始问题。
- 将“抖”转换为“异常振动”等检索表达。
- 将“异响”转换为“异常噪声”等检索表达。
- 结合已知设备型号进行检索。
- 不确定故障原因时，不要直接补充“轴承损坏”等结论。

## 五、中文关键词检索的特殊问题

### 5.1 中文分词

英文天然以空格区分大多数单词：

```text
motor vibration fault
```

中文没有天然空格：

```text
电机运行过程中出现异常振动
```

系统需要通过分词或其他分析方式提取可检索词项。

例如：

```text
电机 / 运行 / 过程 / 异常 / 振动
```

分词质量会直接影响关键词检索效果。

如果专业词汇被错误切分：

```text
变频器
```

可能被拆成不合理的词项，导致检索质量下降。

### 5.2 专业词典

设备故障知识库可以维护专业词汇表：

| 标准术语     | 同义表达             |
| ------------ | -------------------- |
| 异常振动     | 抖动、震动异常       |
| 轴承磨损     | 轴承损坏、轴承异响   |
| 变频器过流   | 驱动器过流、电流异常 |
| 液压压力不足 | 液压压力低、压力不够 |

注意：同义词映射需要业务审核，不能把语义相近但含义不同的故障合并。

### 5.3 英文缩写和数字字母混合编码

例如：

```text
GL-200
E101
MTR-001
BRG-6204
```

需要关注：

- 连字符是否保留。
- 大小写是否统一。
- 字母和数字是否被错误切分。
- 前导零是否保留。
- 标点符号是否影响查询。
- 型号是否发生错误归一化。

对于设备型号和故障码，建议使用独立字段保存标准化后的值，并建立精确查询路径。

### 5.4 结构化字段检索与全文检索不是一回事

假设设备数据表：

```text
device_id
device_model
fault_code
device_type
```

查询：

```text
GL-200 + E101
```

可以直接使用字段过滤：

```sql
SELECT *
FROM fault_knowledge
WHERE device_model = 'GL-200'
  AND fault_code = 'E101';
```

它和全文检索有本质区别：

| 检索方式       | 主要作用                           |
| -------------- | ---------------------------------- |
| 结构化字段过滤 | 判断型号、故障码等字段是否精确匹配 |
| 关键词全文检索 | 根据文本中的词项寻找相关内容       |
| 向量检索       | 根据语义相似度寻找相关内容         |

工程上可以组合使用，但不能把结构化精确匹配完全交给 BM25 或 Embedding。

## 六、混合检索：Hybrid Retrieval

### 6.1 什么是混合检索

混合检索是同时执行关键词检索和向量检索，再将两路结果融合。

```text
                  用户问题
                     │
          ┌──────────┴──────────┐
          │                     │
          ▼                     ▼
     关键词检索              向量检索
       BM25                Embedding
          │                     │
          ▼                     ▼
     关键词结果              向量结果
          │                     │
          └──────────┬──────────┘
                     │
                     ▼
                  结果融合
                     │
                     ▼
                 去重与排序
                     │
                     ▼
                最终候选 Chunk
```

例如用户搜索：

```text
GL-200 设备运行时一直抖动
```

关键词检索可能找到：

```text
R1：GL-200 设备维护手册
R2：GL-200 电机振动故障说明
R3：GL-200 电机结构介绍
```

向量检索可能找到：

```text
V1：电机异常振动排查流程
V2：轴承磨损与设备抖动分析
V3：泵体运行噪声诊断
```

两路结果有交集，也有各自独有的结果。

混合检索希望利用两种检索方式的互补性，提高最终候选结果的质量。

### 6.2 为什么不能简单拼接两路结果

假设：

关键词结果：

```text
1. Chunk-A
2. Chunk-B
3. Chunk-C
```

向量结果：

```text
1. Chunk-B
2. Chunk-D
3. Chunk-E
```

直接拼接：

```text
A、B、C、B、D、E
```

问题：

1. Chunk-B 重复出现。
2. 两路排名没有统一处理。
3. 可能让某一路结果因为拼接顺序而天然占优。
4. 不能正确表达两路检索对同一文档的共同认可程度。

因此需要融合算法。

### 6.3 为什么不能直接相加原始分数

假设关键词检索返回：

```text
Chunk-A：BM25 = 12.5
Chunk-B：BM25 = 8.2
```

向量检索返回：

```text
Chunk-B：Similarity = 0.89
Chunk-C：Similarity = 0.85
```

如果直接相加：

```text
Chunk-A：12.5
Chunk-B：8.2 + 0.89 = 9.09
Chunk-C：0.85
```

结果会严重偏向 BM25。

原因：

- BM25 分数和向量相似度的量纲不同。
- 分数范围不同。
- 分数分布不同。
- 不同查询下分数尺度可能变化。

因此，不能认为：

```text
BM25 = 10
```

一定比：

```text
Vector Similarity = 0.9
```

更相关。

### 6.4 RRF：倒数秩融合

RRF（Reciprocal Rank Fusion）根据文档在不同检索结果中的排名计算融合分数。

标准公式：

\[
RRF(d)=\sum_{r \in R}\frac{1}{k+rank_r(d)}
\]

其中：

- \(d\)：候选文档或 Chunk。
- \(R\)：参与融合的检索结果列表。
- \(rank_r(d)\)：文档在某一路检索中的排名。
- \(k\)：排名平滑常数，经典示例中经常使用 60。
- 未出现在某一路结果中的文档，该路不贡献分数。

**注意：RRF 中的 k 不是 Top-K。**

| 参数     | 含义                         |
| -------- | ---------------------------- |
| Top-K    | 每一路检索返回多少个候选结果 |
| RRF 的 k | 控制排名倒数得分的平滑程度   |

### 6.5 RRF 手算示例

假设关键词检索和向量检索各返回三个文档。

关键词检索：

| 文档 | 排名 |
| ---- | ---: |
| A    |    1 |
| B    |    2 |
| C    |    3 |

向量检索：

| 文档 | 排名 |
| ---- | ---: |
| B    |    1 |
| C    |    2 |
| D    |    3 |

使用：

\[
k=60
\]

计算过程：

**文档 A**

只出现在关键词检索中：

\[
RRF(A)=\frac{1}{60+1}
\]

\[
RRF(A)\approx0.016393
\]

**文档 B**

出现在两路结果中：

\[
RRF(B)=\frac{1}{60+2}+\frac{1}{60+1}
\]

\[
RRF(B)\approx0.016129+0.016393
\]

\[
RRF(B)\approx0.032522
\]

**文档 C**

出现在两路结果中：

\[
RRF(C)=\frac{1}{60+3}+\frac{1}{60+2}
\]

\[
RRF(C)\approx0.015873+0.016129
\]

\[
RRF(C)\approx0.032002
\]

**文档 D**

只出现在向量检索中：

\[
RRF(D)=\frac{1}{60+3}
\]

\[
RRF(D)\approx0.015873
\]

最终结果：

| 文档 | 关键词排名 | 向量排名 | RRF 得分 |
| ---- | ---------: | -------: | -------: |
| B    |          2 |        1 | 0.032522 |
| C    |          3 |        2 | 0.032002 |
| A    |          1 |       无 | 0.016393 |
| D    |         无 |        3 | 0.015873 |

<font color="inherit">最终排序：</font>

```text
B → C → A → D
```

可以看到：

- B 在两路检索中都表现较好，因此融合排名第一。
- C 同样被两路检索召回，因此排名靠前。
- A 虽然在关键词检索中排名第一，但只被一路检索发现。
- D 只被向量检索召回，也仍然保留了进入最终结果的机会。

RRF 不要求两路原始分数处于相同范围。

### 6.6 结果去重与融合粒度

需要明确融合对象是 Chunk 还是 Document。

**情况一：两路命中同一个 Chunk**

```text
BM25：Chunk-A
Vector：Chunk-A
```

应该把它识别为同一个 Chunk，再合并排名贡献。

**情况二：两路命中同一 Document 的不同 Chunk**

```text
BM25：Document-A / Chunk-001
Vector：Document-A / Chunk-008
```

不能直接当成同一个 Chunk。

这两个 Chunk 可能包含不同的故障步骤和技术信息。

建议：

- 检索阶段先以 Chunk 为单位保留证据。
- 如果需要限制同一 Document 的结果数量，可以在融合后增加文档级去重策略。
- 不要为了减少重复文档，直接丢弃可能有价值的不同 Chunk。
- 使用稳定的 Chunk ID 去重，不要仅凭文本相似就认定是同一个 Chunk。

融合粒度必须与评测粒度保持一致。

## 七、线性加权与 RRF 的区别

### 7.1 线性加权

线性加权的基本形式：

\[
Score(d)=\alpha \cdot Score_{keyword}(d)
+(1-\alpha)\cdot Score_{vector}(d)
\]

其中：

- \(\alpha\)：关键词检索权重。
- \(1-\alpha\)：向量检索权重。

例如：

```text
关键词权重：0.6
向量权重：0.4
```

但如果两路分数尺度不同，直接加权仍然可能失衡。

因此，通常需要先考虑分数归一化，例如 Min-Max 或其他校准方法。

归一化也不是没有问题：

- 每次查询的分数分布可能不同。
- 极端值可能影响归一化结果。
- 归一化后的数值不一定代表真实相关性概率。

### 7.2 RRF 与线性加权对比

| 对比维度         | 线性加权             | RRF                        |
| ---------------- | -------------------- | -------------------------- |
| 使用信息         | 原始分数或归一化分数 | 排名位置                   |
| 是否依赖分数尺度 | 是                   | 相对较低                   |
| 参数             | 权重、归一化方法     | 排名平滑常数 k             |
| 调优重点         | 分数校准、权重       | 排名质量、k                |
| 主要优势         | 能利用分数差距       | 降低不同分数尺度的直接冲突 |
| 主要局限         | 分数校准复杂         | 可能忽略原始分数差距       |

RRF 不是永远优于线性加权。

如果某个检索系统的分数经过充分校准，且分数本身具有可靠的相关性意义，线性加权可能同样有效。

RRF 的价值在于：当两路检索分数尺度难以直接比较时，排名融合通常更容易建立一个稳健的初始方案。

### 7.3 RRF 与 Rerank 的区别

| 对比维度         | RRF                  | Rerank                   |
| ---------------- | -------------------- | ------------------------ |
| 输入             | 多路检索结果及其排名 | 查询和候选文档           |
| 主要依据         | 原始排名位置         | 额外相关性评分模型       |
| 是否重新理解文本 | 不需要               | 通常需要                 |
| 主要作用         | 融合多路排名         | 对候选结果进行相关性重评 |

RRF 只是排名融合，不是一个理解用户问题和文档语义的模型。

本阶段掌握 RRF 即可，不需要实现 Rerank。

## 八、查询改写：Query Rewriting

### 8.1 为什么需要查询改写

用户原始问题通常不是最适合检索的表达。

例如：

```text
机器运行的时候一直抖。
```

知识库可能使用：

```text
设备运行过程中发生异常振动。
```

原始查询：

```text
机器运行的时候一直抖
```

改写查询：

```text
设备运行异常振动
```

查询改写的目标是：

> 在不改变用户原意的前提下，将自然语言问题转换成更适合检索的表达。

查询改写不是生成故障答案，也不是推测故障原因。

### 8.2 查询改写流程

```text
用户原始问题
      │
      ▼
实体与约束提取
      │
      ├── 设备型号
      ├── 故障码
      ├── 设备类型
      └── 故障现象
      │
      ▼
查询改写
      │
      ▼
原始查询 + 改写查询
      │
      ▼
关键词检索 / 向量检索
      │
      ▼
结果合并与去重
      │
      ▼
最终检索结果
```

### 8.3 三个设备故障改写案例

**案例一：口语化振动描述**

原始问题：

```text
机器运行的时候一直抖。
```

改写查询：

```text
设备运行异常振动
电机运行振动异常
设备运行稳定性异常
```

说明：

这些是检索表达，不代表已经确定电机或设备稳定性存在故障。

**案例二：口语化异响描述**

原始问题：

```text
设备开机后有很大的声音。
```

改写查询：

```text
设备启动后异常噪声
设备运行异响
电机运行噪声异常
```

说明：

不能直接改写成“轴承损坏”，因为原始问题没有提供足够证据。

**案例三：已知型号和故障现象**

原始问题：

```text
GL-200 用一会儿就会发热，而且有点抖。
```

实体提取：

```json
{
  "deviceModel": "GL-200",
  "faultCode": null,
  "symptoms": [
    "运行一段时间后发热",
    "运行振动异常"
  ]
}
```

改写查询：

```text
GL-200 设备运行温度异常
GL-200 设备运行异常振动
GL-200 电机发热与振动问题
```

说明：

设备型号必须保留；不能凭空增加故障码。

### 8.4 原始查询与改写查询的关系

建议保留两者：

```text
originalQuery
rewrittenQueries
```

原始查询是用户真实表达，改写查询是检索辅助表达。

不要只保存改写结果，否则后续无法分析：

- 改写是否改变原意？
- 哪个改写查询带来了有效召回？
- 改写是否导致错误召回？
- 原始查询是否本来就能检索到正确结果？

可以采用两种策略：

**策略 A：只检索改写查询**

优点：

- 检索调用少。
- 实现简单。
- 适合改写质量已经稳定的场景。

风险：

- 改写错误可能直接导致漏召回。

**策略 B：原始查询和改写查询都检索**

优点：

- 保留原始查询召回能力。
- 可以降低单次改写错误造成的影响。

代价：

- 检索次数增加。
- 结果需要合并去重。
- 可能增加延迟。

### 8.5 查询改写风险控制

| 风险         | 示例                            | 控制方式                             |
| ------------ | ------------------------------- | ------------------------------------ |
| 改变原意     | “设备发热”改成“电机过载”        | 保留原始查询，限制改写范围           |
| 猜测型号     | 用户未提供型号，模型补成 GL-200 | 型号必须来自用户输入或可信业务上下文 |
| 编造故障码   | 自动补充 E101                   | 故障码必须提取并校验                 |
| 丢失关键约束 | 丢失 GL-200                     | 对关键实体做保留校验                 |
| 过度扩展     | 加入轴承损坏、转子偏心等推测    | 区分现象和原因，不将推测当事实       |

建议将实体提取与查询改写分开：

1. 先提取型号、故障码等关键实体。
2. 校验实体来源和格式。
3. 再生成检索表达。
4. 校验改写是否保留关键实体。
5. 未通过校验时，回退到原始查询。

**查询改写不能替代业务实体校验。**

## 九、混合检索与查询改写的 ROI 对比

### 9.1 方案成本与收益

| 方案                | 开发成本 | 运行成本                 | 运维成本 | 主要收益                 | 适用场景                     |
| ------------------- | -------- | ------------------------ | -------- | ------------------------ | ---------------------------- |
| 纯关键词检索        | 低至中   | 低                       | 低至中   | 精确词项匹配             | 故障码、型号、编号、规范名称 |
| 纯向量检索          | 中       | Embedding 与向量检索成本 | 中       | 语义相似、同义表达       | 自然语言描述、语义模糊问题   |
| 混合检索 + RRF      | 中至高   | 两路检索成本             | 中至高   | 利用两种检索的互补性     | 精确术语与自然语言混合问题   |
| 查询改写            | 中       | 可能增加模型调用和 Token | 中       | 提高口语化问题的可检索性 | 用户描述模糊、术语不规范     |
| 混合检索 + 查询改写 | 高       | 改写模型 + 两路检索      | 高       | 覆盖多种表达形式         | 问题类型复杂且基线已证明需要 |

这里的成本是相对工程估计，不是固定市场报价。

### 9.2 不同业务场景的方案选择

**故障码查询**

例如：

```text
E101 怎么处理？
```

建议优先顺序：

1. 故障码结构化字段精确查询。
2. 关键词检索。
3. 必要时使用向量检索补充背景说明。

不建议一开始就引入查询改写模型。

**设备型号查询**

例如：

```text
GL-200 的电机怎么维护？
```

建议：

1. 提取并校验设备型号。
2. 先通过型号字段过滤。
3. 在设备范围内执行关键词或向量检索。

型号过滤应该是可靠的业务约束，而不是交给语义相似度决定。

**技术术语查询**

例如：

```text
变频器过流保护如何排查？
```

如果知识库术语标准化程度高，关键词检索可能已经足够。

如果存在大量不同表达，混合检索可能更有收益。

**口语化故障描述**

例如：

```text
设备运行一段时间就抖，还会发出奇怪的声音。
```

建议重点评估：

- 查询改写。
- 向量检索。
- 原始查询与改写查询的并行检索。

如果口语化问题在业务问题中占比很高，查询改写可能带来更明显的收益。

### 9.3 查询改写与混合检索，哪个 ROI 更高？

不能脱离数据分布直接判断。

假设知识库有大量设备故障码查询：

```text
E101、E102、E103、F201
```

查询改写的收益可能很有限，因为这些查询本身已经非常明确。

此时优先完善故障码精确匹配可能更划算。

假设用户大多是维修人员口语描述：

```text
设备一开机就抖
运行一段时间声音变大
机器转起来不太稳定
```

查询改写可能更有价值，因为它能够将口语表达转换成知识库常见术语。

如果系统同时存在：

- 大量精确故障码。
- 大量设备型号。
- 多种技术术语。
- 大量口语化描述。

那么混合检索可能带来更广泛的覆盖，但必须测量实际增益。

**建议采用增量建设顺序：**

1. 先建立纯关键词与纯向量基线。
2. 检查错误案例，确认是否存在两路互补。
3. 再增加 RRF。
4. 独立评估查询改写。
5. 最后评估 RRF 与查询改写组合是否有额外收益。

不要一次性把所有能力全部加上，否则很难判断哪项优化真正有效。

## 十、Spring AI 1.1.8 与 PostgreSQL / pgvector 的工程落点

### 10.1 各组件职责

| 组件                       | 职责                               | 不应误认为                   |
| -------------------------- | ---------------------------------- | ---------------------------- |
| Spring AI `EmbeddingModel` | 将文本转换为向量                   | 自动完成关键词检索           |
| Spring AI `Document`       | 承载文本、ID 和 Metadata           | 自动提供完整业务文档解析能力 |
| Spring AI `VectorStore`    | 向量数据存储和相似度检索抽象       | 同时提供标准 BM25 实现       |
| Spring AI `SearchRequest`  | 配置向量检索请求                   | 通用 BM25 查询对象           |
| PostgreSQL 18              | 关系数据、字段过滤、全文检索等     | 默认内置 BM25                |
| pgvector 0.8.7             | 向量数据类型、距离运算符和向量索引 | BM25 全文检索引擎            |
| 自定义 Service             | 组织双路检索、RRF、去重、权限过滤  | Spring AI 自动完成的业务逻辑 |

### 10.2 Spring AI 1.1.8 的向量检索入口

Spring AI 1.1.8 提供 `SearchRequest` 用于构建向量检索请求。

概念示例：

```java
SearchRequest searchRequest = SearchRequest.builder()
        .query(query)
        .topK(5)
        .similarityThreshold(0.7)
        .build();

List<Document> documents =
        vectorStore.similaritySearch(searchRequest);
```

需要理解：

- `query`：待检索文本。
- `topK`：返回候选数量。
- `similarityThreshold`：相似度阈值。
- `filterExpression`：可用于 Metadata 过滤。

1.1.8 的 `SearchRequest` 文档明确说明：

- 阈值为 `0.0` 时接受所有检索分数，即不进行阈值过滤。
- 阈值为 `1.0` 时要求精确匹配。

但要注意：这属于 Spring AI `SearchRequest` 的相似度阈值语义，具体 VectorStore 实现还需要结合后端的相似度计算和分数映射确认。不要把它直接等同于 pgvector 的原始距离阈值。

另外，`SearchRequest` 的默认 Top-K 应以 1.1.8 对应常量和实际配置为准，不要把其他版本或其他向量数据库的默认值直接套用。

### 10.3 Spring AI Document 的职责

Spring AI 1.1.8 的 `Document` 主要包含：

```text
id
text
metadata
score
```

其中：

- `id`：Document 唯一标识。
- `text`：文本内容。
- `metadata`：应用定义的元数据。
- `score`：检索结果分数信息。

例如：

```java
Document document = Document.builder()
        .text("GL-200 电机运行过程中出现异常振动")
        .metadata("deviceModel", "GL-200")
        .metadata("faultCode", "E101")
        .metadata("chunkId", "chunk-001")
        .build();
```

注意：

这只是展示 Metadata 的承载方式，不代表当前项目已经具有这些字段，也不代表所有向量存储后端都会以相同方式持久化和返回所有 Metadata。

### 10.4 PostgreSQL 全文检索不等于 BM25

PostgreSQL 18 自带全文检索能力：

- `tsvector`：文档词项表示。
- `tsquery`：查询表达式。
- `to_tsvector`：文本转换。
- `to_tsquery` / `websearch_to_tsquery`：查询解析。
- `ts_rank` / `ts_rank_cd`：相关性排序。
- GIN：常见的全文检索索引。

PostgreSQL 内置的 `ts_rank` 和 `ts_rank_cd` 不是 BM25。

如果项目明确要求 BM25，可以评估：

- 专门的搜索引擎。
- 支持 BM25 的 PostgreSQL 扩展，例如 ParadeDB `pg_search`。
- 其他经过验证的关键词检索实现。

但引入扩展前必须检查：

1. PostgreSQL 18.7 兼容性。
2. 扩展版本与部署方式。
3. 中文分词和专业词典能力。
4. 维护成本与许可证。
5. 与现有 pgvector 表和查询链路的集成方式。

不要因为项目已经使用 PostgreSQL 和 pgvector，就认为 BM25 已经可用。

### 10.5 Java 工程中的检索编排

推荐将两路检索分别封装，再在 Service 层融合。

```text
RetrievalService
   │
   ├── KeywordRetrievalService
   │       └── BM25 / PostgreSQL FTS / 外部搜索组件
   │
   ├── VectorRetrievalService
   │       └── Spring AI VectorStore
   │
   └── FusionService
           ├── Chunk ID 去重
           ├── RRF 得分计算
           ├── 排序
           └── 返回最终候选结果
```

RRF 的核心计算可以用纯 Java 表达：

```java
double rrfScore = 0.0;

for (Integer rank : ranks) {
    if (rank != null) {
        rrfScore += 1.0 / (rrfK + rank);
    }
}
```

这里的 `ranks` 是同一个 Chunk 在不同检索列表中的排名。

工程实现时还要处理：

- 两路检索异常。
- 空结果。
- Chunk ID 去重。
- 租户和设备权限过滤。
- 检索结果数量限制。
- 超时与降级。
- TraceId、耗时和融合结果记录。

### 10.6 权限过滤不能在融合后才考虑

假设：

```text
用户 A 只能访问 GL-200 设备知识库。
用户 B 可以访问 GL-300 设备知识库。
```

如果先检索出所有数据，再在最终结果阶段过滤，可能产生：

- 越权数据进入应用内存。
- 日志记录敏感内容。
- 不必要的检索资源消耗。
- 某一路检索绕过权限条件。

建议：

1. 在关键词检索和向量检索两路都执行相同的租户、设备和用户权限约束。
2. 对无法下推到数据库的过滤条件，在服务端进行严格校验。
3. RRF 只融合已经通过权限约束的结果。
4. 不信任模型生成的设备型号或权限范围。

## 十一、失败与降级策略

| 场景             | 推荐处理                                       |
| ---------------- | ---------------------------------------------- |
| 关键词检索失败   | 记录异常；如果向量检索可用，可按降级策略继续   |
| 向量检索失败     | 记录异常；如果关键词检索可用，可返回关键词结果 |
| 一路无结果       | 另一路结果仍可参与融合                         |
| 两路都无结果     | 返回无可用知识的状态，不要编造答案             |
| 两路结果高度重复 | 按 Chunk ID 去重，保留融合排名                 |
| 查询改写失败     | 回退原始查询                                   |
| 改写丢失故障码   | 拒绝该改写结果，使用原始查询                   |
| 权限过滤后无结果 | 按无权限或无可用知识策略处理，不得绕过权限     |
| 某一路超时       | 设置合理超时与降级策略，记录该次实验的降级状态 |

注意：

如果一次实验中关键词检索失败，系统实际只执行了向量检索，那么这次结果不能被当成完整混合检索结果。

### 12.5 指标计算

设：

- \(Q\)：全部问题集合。
- \(R_q\)：问题 q 的标准相关结果集合。
- \(S_q^K\)：检索系统为问题 q 返回的 Top-K 结果。
- \(rel(q,d)\)：文档 d 对问题 q 的相关性标注。

**Recall@K**

\[
Recall@K=
\frac{|S_q^K \cap R_q|}{|R_q|}
\]

回答：

> 已知相关内容中，系统找回了多少？

**Precision@K**

\[
Precision@K=
\frac{|S_q^K \cap R_q|}{K}
\]

回答：

> 返回的 K 个结果中，有多少是相关的？

如果实际返回数量小于 K，实验必须统一约定未返回位置是否按不相关处理。常见评测会将分母仍固定为 K，以体现结果列表的填充不足。

**HitRate@K**

\[
HitRate@K=
\frac{
\text{至少命中一个相关结果的问题数}
}{
\text{总问题数}
}
\]

回答：

> 有多少问题至少找到了一个可用结果？

**MRR**

\[
MRR=
\frac{1}{|Q|}
\sum_{q\in Q}
\frac{1}{rank_q}
\]

其中 \(rank_q\) 是第一个相关结果的位置；如果没有相关结果，则该问题的倒数排名记为 0。

回答：

> 第一个相关结果通常排在多靠前的位置？

**nDCG@K**

\[
DCG@K=
\sum_{i=1}^{K}
\frac{2^{rel_i}-1}{\log_2(i+1)}
\]

\[
nDCG@K=
\frac{DCG@K}{IDCG@K}
\]

其中：

- \(rel_i\)：第 i 个结果的相关性等级。
- \(IDCG@K\)：理想排序下的 DCG。

回答：

> 高相关结果是否排在更靠前的位置？

## 十三、三个重点思考题

### 问题一：为什么纯向量检索在搜索“故障码 E101”“型号 GL-200”时经常漏召回？

**第一，Embedding 的目标不是精确字符匹配。**

Embedding 模型主要学习文本的语义表示。

```text
E101 电机过载
E102 电机欠压
```

这两段内容在主题上非常接近。

但是用户查询 E101 时，真正需要的是 E101 的精确处理说明，而不是另一个相似故障码。

**第二，数字和字母组合的语义信息有限。**

```text
GL-200
GL-300
```

两个型号的字符结构相似，但对应的设备可能完全不同。

模型未必能够可靠地把这些编码当作必须严格相等的业务标识。

**第三，向量检索是近邻搜索，不是精确查询。**

向量检索寻找的是距离最近的候选项。

如果正确的 E101 Chunk 没有排进 Top-K，就可能被漏掉，即使它确实存在于知识库中。

**工程解决办法：**

```text
提取故障码 / 设备型号
          │
          ▼
    精确字段过滤
          │
          ▼
    关键词检索
          │
          ▼
  必要时补充向量检索
```

结论：

故障码和设备型号应该优先使用结构化字段或精确关键词匹配，不能完全依赖向量语义相似度。

### 问题二：为什么混合检索不能简单拼接两路结果？为什么 RRF 通常比直接相加原始分数更稳健？RRF 又有哪些局限？

**不能简单拼接的原因：**

- 两路结果可能包含相同 Chunk。
- 两路排序可能存在冲突。
- 拼接顺序会影响最终结果。
- 无法体现两路检索对同一 Chunk 的共同认可。

**不能直接相加原始分数的原因：**

BM25 和向量相似度的分数范围、分布及计算含义不同。

```text
BM25：12.5
Vector Similarity：0.89
```

这两个值不能直接比较大小。

**RRF 的优势：**

RRF 只使用排名位置，不直接比较两路原始分数。

如果一个 Chunk 在关键词和向量两路结果中都排名靠前，它通常会得到更高的融合分数。

**RRF 的局限：**

1. 主要依赖排名，不充分利用原始分数差距。
2. 如果某一路检索本身排序质量差，可能带来噪声。
3. 排名平滑常数 k 会影响融合行为。
4. 两路结果高度重复时，融合收益可能有限。
5. 如果两路检索召回的都是错误内容，RRF 不能凭空创造正确结果。

结论：

RRF 是一种方便的排名融合方法，不是自动提升检索质量的保证。必须通过固定问题集上的对照实验验证。

### 问题三：查询改写和混合检索，哪个在设备故障问答场景的 ROI 更高？

需要先分析用户问题分布。

**场景 A：大量故障码和设备型号查询**

例如：

```text
E101 怎么处理？
GL-200 的维护流程是什么？
```

更高优先级：

- 结构化字段过滤。
- 精确关键词检索。

查询改写可能没有明显收益。

**场景 B：大量口语化描述**

例如：

```text
机器转起来有点抖。
运行一会儿声音就特别大。
```

查询改写可能更有收益，因为它能把用户表达转成知识库中常见的标准术语。

**场景 C：问题类型复杂且多样**

例如同时存在：

- 故障码。
- 型号。
- 专业术语。
- 同义表达。
- 口语化描述。

混合检索可能带来更全面的召回能力。

**成本比较：**

| 比较项     | 查询改写                        | 混合检索                                     |
| ---------- | ------------------------------- | -------------------------------------------- |
| 开发成本   | 需要模型调用、Prompt 和实体校验 | 需要两路检索、融合和去重                     |
| 运行成本   | 可能增加 LLM Token              | 增加一条检索链路                             |
| 运维复杂度 | 需要关注改写质量和模型版本      | 需要关注两路检索与融合质量                   |
| 延迟       | 可能增加一次模型调用            | 两路并行时可降低串行等待，但仍有额外资源消耗 |
| 效果上限   | 受改写质量和模型能力影响        | 受两路检索召回能力影响                       |
| 更适合     | 口语化和表达不规范的问题        | 精确术语与语义问题混合存在                   |

**最终判断：**

不要直接选择更复杂的方案。

先分析真实问题集：

- 故障码占比高：优先做好精确匹配。
- 口语化问题占比高：重点测试查询改写。
- 两种检索方式明显互补：测试 RRF。
- 两项优化分别有效：再测试组合方案。

最终应该比较的是：

\[
ROI \approx
\frac{\text{检索质量提升带来的业务收益}}
{\text{开发成本 + 运行成本 + 运维成本}}
\]

这是决策思路，不是可以直接计算的统一财务公式。

## 十四、常见实验错误与排查方法

| 常见错误                 | 为什么错误                 | 排查方法                       |
| ------------------------ | -------------------------- | ------------------------------ |
| 只看 Recall              | 可能引入大量无关结果       | 同时看 Precision 和 HitRate    |
| 只看总体指标             | 掩盖故障码和口语问题的差异 | 按问题类型分组                 |
| 直接相加 BM25 和向量分数 | 分数尺度不同               | 使用 RRF 或经过校准的融合      |
| 两路结果直接拼接         | 重复且排序不合理           | 使用统一 ID 去重和融合         |
| 将 RRF 的 k 当作 Top-K   | 两者含义不同               | 明确排名平滑常数和返回数量     |
| 认为 pgvector 自带 BM25  | 技术组件职责混淆           | 区分全文检索与向量检索         |
| 认为向量距离越大越相关   | 距离和相似度方向可能相反   | 核对操作符和后端定义           |
| 查询改写丢失型号         | 可能召回其他设备资料       | 校验关键实体是否保留           |
| 查询改写猜测故障码       | 可能引入错误知识           | 故障码只允许来自可信输入或数据 |
| 只比较最终回答           | 生成模型可能掩盖检索退化   | 独立评测检索结果               |
| 不固定 Embedding 版本    | 多个变量同时变化           | 固定模型名称、版本和维度       |
| 混合检索未统一权限条件   | 可能造成越权召回           | 两路检索都执行权限过滤         |
| 只统计一次实验           | 容易受偶然波动影响         | 固定环境，必要时重复执行       |

## 十五、最终知识总结

需要建立以下完整认知：

```text
                  设备故障问题
                        │
                        ▼
                  问题类型识别
                        │
          ┌─────────────┼──────────────┐
          │             │              │
          ▼             ▼              ▼
        故障码         设备型号        自然语言描述
          │             │              │
          ▼             ▼              ▼
       精确匹配       精确过滤       查询改写评估
          │             │              │
          ▼             ▼              ▼
       关键词检索     关键词检索      向量检索
          │             │              │
          └─────────────┼──────────────┘
                        │
                        ▼
                 根据实验决定是否
                   增加 RRF 融合
                        │
                        ▼
                  去重与结果排序
                        │
                        ▼
                   检索结果评估
                        │
                        ▼
                 记录收益、成本和退化
```

必须记住：

1. **关键词检索**：擅长精确词项匹配，特别适合故障码、型号和专业术语。
2. **向量检索**：擅长语义相似和同义表达，但不保证精确字符匹配。
3. **混合检索**：利用两路检索互补性，RRF 根据排名融合，而不是直接相加原始分数。
4. **查询改写**：改善用户表达与知识库术语之间的差异，但必须防止改变原意和猜测实体。
5. **工程选型**：不能以技术复杂度判断优劣，必须以固定评测集上的检索效果、延迟、成本和维护负担判断。

## 十七、最终验收清单

完成学习后，应能独立完成以下任务：

- [ ] 能解释倒排索引、Term、Document、Posting List。
- [ ] 能解释 BM25 的 TF、IDF 和文档长度归一化。
- [ ] 能解释 Query Embedding 和 Document Embedding。
- [ ] 能说明故障码和设备型号为什么不应该只依赖向量检索。
- [ ] 能说明 PostgreSQL 全文检索、BM25 与 pgvector 的职责区别。
- [ ] 能手工计算 RRF 三个以上候选文档的融合分数。
- [ ] 能解释 RRF 的 k 和 Top-K 的区别。
- [ ] 能解释线性加权为什么需要考虑分数归一化。
- [ ] 能设计查询改写流程并防止型号、故障码被模型猜测。
- [ ] 能分别评测关键词检索、向量检索、RRF 和查询改写。
- [ ] 能使用 Recall@K、Precision@K、HitRate@K 评价检索结果。
- [ ] 能记录 P95、模型调用次数、Token 成本和资源开销。
- [ ] 能根据四类设备问题选择合理的检索策略。
- [ ] 能根据真实实验结果决定是否引入额外复杂度。

**最终验收标准：** 面对一个新的设备故障检索问题，能够判断应该优先采用精确字段匹配、关键词检索、向量检索、RRF 还是查询改写，并通过固定评测集验证选择，而不是凭直觉认为技术越复杂越好。
