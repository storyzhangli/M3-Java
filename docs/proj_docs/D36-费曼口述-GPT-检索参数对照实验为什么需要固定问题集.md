# **费曼口述：检索参数对照实验为什么需要固定问题集**

先建立一个核心认识：

**固定问题集的目的，不是让 RAG 永远只回答这批问题，而是让我们能够在相同测试条件下，判断检索参数调整是否真的带来了改善。**

例如，你要比较三组配置：

| 配置 | Top-K | Chunk Size | Overlap |
| ---- | ----- | ---------- | ------- |
| A    | 3     | 500        | 50      |
| B    | 5     | 500        | 50      |
| C    | 10    | 500        | 50      |

三组配置必须使用相同的问题、相同的文档版本、相同的相关性标注。否则，最终 Recall\@K 的变化，可能不是参数带来的，而是测试问题本身变了。

经典信息检索评估通常需要三类基础材料：**文档集合、查询集合、查询与文档之间的相关性判断**。这也是固定问题集的理论基础。

## **第一阶段：理解固定问题集的基本概念**

### **1. 什么是 RAG 检索参数对照实验？它主要想解决什么问题？**

RAG 检索参数对照实验，是在尽可能保持其他条件不变的情况下，调整一个或多个检索参数，观察检索质量如何变化。

例如：

- A：Top-K = 3
- B：Top-K = 5
- C：Top-K = 10

三个配置处理同一批问题，再比较 Recall\@K、Precision\@K、MRR 等指标。

它要解决的核心问题是：

**当前检索效果的变化，到底是参数调整造成的，还是其他因素造成的？**

没有对照实验，很容易陷入凭感觉调参：感觉 Top-K 越大越好，Chunk 越大越好，Threshold 越低越好。但这些参数之间存在取舍，不存在对所有场景都最优的固定值。

### **2. 什么是固定问题集（Fixed Query Set）？它与日常用户随机提问有什么区别？**

固定问题集是一批提前整理、具有稳定 ID、经过分类和标注，并在多轮实验中重复使用的问题集合。

例如：

| Query ID | 问题                                         | 类型     |
| -------- | -------------------------------------------- | -------- |
| Q001     | E1002 故障代码代表什么？                     | 故障代码 |
| Q002     | MODEL-A 设备主轴温度过高怎么办？             | 自然语言 |
| Q003     | 设备运行 30 分钟后出现振动，可能是什么原因？ | 模糊描述 |
| Q004     | 更换主轴轴承需要哪些工具？                   | 维修步骤 |

它与生产环境随机问题的区别：

- 固定问题集：主要用于可重复、可比较的实验。
- 随机用户问题：主要反映真实用户不断变化的查询分布。

固定问题集是基准测试工具，不是生产环境问题的替代品。

### **3. 为什么评估 RAG 检索效果时，不能每次随意更换测试问题？**

因为问题难度、表达方式、知识类型都会影响检索结果。

例如：

问题 A：

> E1002 代表什么故障？

问题 B：

> 设备运行一段时间后主轴温度逐渐升高，同时伴随异常振动，应该优先检查什么？

问题 A 有明确故障代码，容易通过关键词匹配找到目标文档；问题 B 需要理解多种故障现象之间的关系，通常更难。

如果第一次使用简单问题，第二次改用复杂问题，即使第二次 Recall 下降，也不能证明参数变差了。

因为实验条件已经发生变化。

### **4. 固定问题集在一次检索实验中扮演什么角色？**

它相当于实验中的统一测试样本。

例如，准备 50 道问题：

```
Q001
Q002
Q003
...
Q050
```

每组参数都运行这 50 道问题：

```
配置 A -> Q001~Q050
配置 B -> Q001~Q050
配置 C -> Q001~Q050
```

这样可以逐题比较：

- Q001 在 A、B、C 中的检索结果有什么变化？
- 哪些问题因 Top-K 增大而找到了更多证据？
- 哪些问题增加了无关 Chunk？
- 哪些问题始终无法召回正确证据？

### **5. 为什么对照实验要求不同参数配置使用同一批问题？**

这是为了控制查询样本差异。

例如：

| 问题 | 配置 A Recall\@5 | 配置 B Recall\@5 |
| ---- | ---------------- | ---------------- |
| Q001 | 1.0              | 1.0              |
| Q002 | 0.5              | 1.0              |
| Q003 | 0.0              | 0.5              |

因为问题相同，才有条件分析 B 相比 A 的逐题变化。

如果两组问题不同，就无法区分参数变化和查询样本变化的贡献。

### **6. 如果两组参数使用不同的问题集，即使最终 Recall\@K 不同，为什么也不能直接认为其中一组更好？**

因为两个 Recall 数值可能来自不同难度、不同知识类别、不同相关证据数量的样本。

例如：

- A 组：20 道简单问题，Recall\@5 = 0.90。
- B 组：20 道复杂问题，Recall\@5 = 0.75。

不能据此判断 A 的检索算法一定更好。

可能只是 A 组的问题更容易。

需要让两组参数在同一批测试问题和同一套 Ground Truth 上评估。

### **7. 固定问题集究竟控制了实验中的什么变量？它又不能控制什么变量？**

固定问题集主要控制的是：

**查询样本及其问题分布。**

但它不能单独控制：

- 文档内容和文档版本；
- Embedding 模型及版本；
- Chunk 切分方式；
- 向量索引及索引参数；
- 检索算法；
- 数据库状态；
- 相似度阈值；
- Reranker 及版本；
- 并发、缓存和系统负载；
- Ground Truth 标注质量。

因此，固定问题集只是控制变量法的一部分，不是完整的实验控制方案。

## **第二阶段：理解问题变化造成的实验偏差**

### **8. 同一个检索系统面对不同问题，为什么可能产生明显不同的检索结果？**

因为不同问题对应不同的知识需求和检索难度。

例如：

```
Q1：E1002 是什么故障？
Q2：MODEL-A 主轴出现 E1002 后如何处理？
Q3：主轴温度升高、振动增大且出现 E1002，应该如何排查？
```

Q1 主要需要查找故障代码定义。

Q2 还需要设备型号和处理方法。

Q3 可能需要关联故障定义、设备型号、维修手册、排查步骤等多个证据。

同一个检索系统面对它们时，召回难度和所需证据数量自然不同。

### **9. 为什么简单问题和复杂问题不能被视为相同难度的测试样本？**

因为它们的检索目标、证据范围和语义复杂度不同。

简单问题可能只需要一个 Chunk：

> E1002 表示主轴温度异常。

复杂问题可能需要三个 Chunk：

1. E1002 故障定义；
2. MODEL-A 主轴温度检测流程；
3. 对应维修手册中的温度异常处理步骤。

如果只看问题数量，不考虑证据难度和证据数量，就可能高估或低估某类参数的效果。

### **10. 为什么问题中的设备型号、故障代码、零件编号会影响检索结果？**

因为它们是强约束实体。

例如：

```
MODEL-A + E1002
MODEL-B + E1002
```

即使故障代码相同，不同设备型号的维修流程也可能不同。

同样：

```
轴承型号：6205
轴承型号：6206
```

可能对应不同的尺寸、适配条件和更换要求。

因此，制造业检索不能只关注语义相似度，还应关注实体精确匹配和 Metadata Filter。

### **11. 同一故障问题分别使用准确术语、口语表达和模糊描述，检索结果可能有哪些差异？**

例如，表达同一个知识需求：

| 表达方式 | 问题                                       |
| -------- | ------------------------------------------ |
| 准确术语 | 主轴轴承温升异常的处理方法是什么？         |
| 口语表达 | 主轴那个轴承特别烫，应该怎么办？           |
| 模糊描述 | 机器运行一段时间后，里面有个地方越来越热。 |

准确术语更容易和文档术语匹配。

口语表达需要语义模型理解术语之间的对应关系。

模糊描述可能还需要先澄清设备、部件和故障现象。

固定问题集需要包含这些表达差异，不能全部写成标准化的技术术语。

### **12. 如果第一次实验使用 20 个问题，第二次实验使用另一批 20 个问题，结果差异可能来自哪些因素？**

至少可能来自：

1. 问题难度不同；
2. 问题类别占比不同；
3. 精确关键词与自然语言问题比例不同；
4. 每道问题对应的相关 Chunk 数量不同；
5. 多文档关联问题比例不同；
6. 无答案问题比例不同；
7. 问题所涉及的设备型号不同；
8. Ground Truth 标注范围不同。

因此，两批问题的平均 Recall 不适合直接作为参数优劣的证据。

### **13. 如何区分参数调整带来的效果变化与问题本身难度变化带来的效果变化？**

使用相同 Query ID 进行逐题对照。

例如：

| Query ID | A Recall\@5 | B Recall\@5 | 差值 |
| -------- | ----------- | ----------- | ---- |
| Q001     | 0.5         | 1.0         | +0.5 |
| Q002     | 1.0         | 1.0         | 0    |
| Q003     | 0.0         | 0.5         | +0.5 |

问题本身没有变化，变化来自参数配置或其他实验条件。

进一步还应检查：

- 文档版本是否一致；
- 标注是否一致；
- Embedding 是否一致；
- 检索代码是否一致；
- ANN 是否引入随机性或索引差异。

### **14. 为什么固定问题集能够让不同参数配置形成更公平的比较？**

因为每组参数接受同样的测试挑战。

就像两名运动员参加同一条赛道、同一套规则的比赛。

如果一个人跑平地，另一个人跑山路，时间就不能直接比较。

固定问题集让查询样本一致，文档集合和相关性标注进一步让评价标准一致。

### **15. 固定问题集与随机抽样测试集之间有什么区别？**

| 维度     | 固定问题集         | 随机抽样测试集           |
| -------- | ------------------ | ------------------------ |
| 主要目标 | 可重复比较         | 估计真实分布表现         |
| 样本     | 已确定并版本化     | 每次按抽样规则选取       |
| 可复现性 | 较高               | 取决于抽样种子和数据快照 |
| 覆盖方式 | 可人为分层控制     | 依赖抽样设计             |
| 适合场景 | 参数对照、回归测试 | 线上分布评估             |

两者并不冲突。

实际项目通常应同时保留：

- 固定基准集：用于比较每次参数调整。
- 动态抽样集：用于观察新用户、新问题和新业务分布。

## **第三阶段：设计高质量固定问题集**

### **16. 一个合格的 RAG 检索问题集应该包含哪些基本字段？**

建议至少包括以下字段：

| 字段                | 含义                       |
| ------------------- | -------------------------- |
| queryId             | 问题唯一 ID                |
| queryText           | 问题原文                   |
| queryCategory       | 问题类别                   |
| queryStyle          | 精确、口语、模糊等表达方式 |
| equipmentModel      | 设备型号                   |
| faultCode           | 故障代码                   |
| relevantEvidenceIds | 相关证据 ID                |
| answerable          | 知识库是否有答案           |
| difficulty          | 问题难度                   |
| priority            | 业务重要性                 |
| datasetVersion      | 问题集版本                 |

还建议补充：

- sourceQuery：问题来源，例如真实用户日志、专家构造；
- expectedEvidence：应该召回的证据说明；
- annotationStatus：标注状态；
- annotator：标注人或复核人。

### **17. 为什么问题集不能只包含简单、明确、容易检索的问题？**

因为这样的测试集只能证明系统能处理简单查询，不能证明系统适合真实业务。

制造设备场景中，真实用户经常会：

- 不知道准确故障代码；
- 使用口语表达；
- 混合描述多个故障现象；
- 忘记提供设备型号；
- 只描述结果，不知道故障原因；
- 同时询问原因、处理步骤和备件。

如果问题集只包括“某故障代码是什么意思”，就会高估系统在生产环境中的检索能力。

### **18. 如何根据真实用户提问构建具有代表性的问题集？**

推荐流程：

1. 收集真实用户问题、工单、客服记录和工程师咨询记录。
2. 脱敏处理个人、客户和设备敏感信息。
3. 清理重复问题，但保留不同表达方式。
4. 按设备、故障类别、问题类型分组。
5. 选择典型问题和长尾问题。
6. 让设备专家确认问题含义和预期证据。
7. 生成固定版本并保存原始来源信息。

不要直接将用户日志未经处理地作为评测集。

真实问题可能存在歧义、上下文缺失、答案无法从当前知识库得到等情况，需要先判断是否适合用来评估检索系统。

### **19. 制造设备故障知识库应该覆盖哪些类型的问题？**

建议覆盖：

- 故障代码查询；
- 故障原因分析；
- 故障现象识别；
- 设备型号与参数查询；
- 零件型号与备件信息；
- 维修步骤查询；
- 安全操作要求；
- 设备维护与保养；
- 多故障关联分析；
- 跨文档证据查询；
- 多条件组合查询；
- 无答案或知识库未收录问题。

### **20. 为什么问题集需要覆盖设备型号、故障代码、维修步骤、零件信息和故障原因等不同场景？**

因为不同场景对检索能力的要求不同。

例如：

| 场景     | 主要考验能力               |
| -------- | -------------------------- |
| 设备型号 | 实体匹配、Metadata Filter  |
| 故障代码 | 精确关键词匹配             |
| 维修步骤 | 语义召回、步骤上下文完整性 |
| 零件信息 | 编号精确匹配               |
| 故障原因 | 语义检索、多证据关联       |
| 安全规范 | 证据完整性、版本优先级     |

如果只测一种场景，参数可能针对这一类问题优化，却损害其他场景。

### **21. 如何设计精确关键词查询、自然语言查询、语义查询和模糊查询？**

建议用同一个业务知识点设计多种表达。

假设知识点为 MODEL-A 的 E1002 故障：

```
精确关键词：
MODEL-A E1002

自然语言：
MODEL-A 设备出现 E1002 故障后应该怎么处理？

语义查询：
设备主轴温度超过正常范围，如何排查？

模糊查询：
机器运行一会儿就很烫，还出现报警，怎么办？
```

它们分别测试：

- 精确实体匹配；
- 关键词与自然语言混合检索；
- 同义表达和语义理解；
- 模糊表达下的召回能力。

### **22. 为什么应该纳入知识库中存在答案和不存在答案的两类问题？**

因为 RAG 不仅要能找到证据，也必须知道什么时候找不到证据。

例如：

- 有答案：知识库包含 MODEL-A 的 E1002 维修手册。
- 无答案：知识库完全没有 MODEL-Z 的 E9999 故障说明。

无答案问题主要用于测试：

- 是否错误召回其他设备的相似知识；
- 是否因相似度低而正确返回空结果；
- 是否因为错误的 Top-K 或 Threshold 而召回噪声；
- 后续生成阶段是否能够拒绝无证据回答。

注意：无答案问题不能直接算作普通 Recall\@K 样本，因为它可能没有相关文档，Recall 的分母为零。应单独评估无答案识别、误召回率和拒答质量。

### **23. 如何设计多文档关联、跨章节、多条件组合等复杂问题？**

可以构建需要多个证据共同满足的问题。

例如：

> MODEL-A 设备出现 E1002，同时主轴温度高于规定范围。请根据维修手册说明首先检查哪些部件，以及更换轴承前需要满足什么安全条件。

其证据可能来自：

1. 故障代码说明；
2. 设备温度标准章节；
3. 故障排查步骤；
4. 维修安全规范；
5. 零件更换章节。

此类问题应标注多个相关证据，并记录哪些证据是必需的、哪些是补充的。

### **24. 如何避免测试问题全部集中在某一类设备或某一种故障上？**

采用分层抽样。

先定义分层维度：

- 设备型号；
- 故障代码；
- 问题类别；
- 查询表达风格；
- 难度；
- 有答案/无答案；
- 单文档/多文档。

再设定各类问题的目标数量。

例如，50 道问题可以做一个初始分布：

| 类别           | 数量 |
| -------------- | ---- |
| 设备型号与参数 | 5    |
| 故障代码       | 10   |
| 故障原因       | 10   |
| 维修步骤       | 8    |
| 零件信息       | 5    |
| 多文档关联     | 7    |
| 模糊与无答案   | 5    |

这是项目初期的示例分布，不是通用标准。应以真实业务问题分布和评测目标为准。

### **25. 如何判断固定问题集是否具有足够的代表性？**

需要检查：

1. 是否覆盖主要业务场景；
2. 是否覆盖主要设备型号；
3. 是否覆盖高频和长尾故障；
4. 是否包含精确、口语和模糊表达；
5. 是否包含单文档和多文档问题；
6. 是否包含有答案和无答案问题；
7. 是否覆盖高风险业务问题；
8. 是否来自真实用户问题或专家确认的业务场景。

还可以把问题类别分布与线上日志分布进行对照。

代表性不是“题目越多越好”，而是测试集与目标业务的关键特征相匹配。

### **26. 问题集只有 10 道题、50 道题和 200 道题时，分别可能存在哪些评估风险？**

| 数量   | 可能的风险                                 | 适合用途         |
| ------ | ------------------------------------------ | ---------------- |
| 10 道  | 偶然性强，覆盖不足，单题影响很大           | 开发调试         |
| 50 道  | 可以做初步分层，但统计不确定性仍明显       | 初期参数对照     |
| 200 道 | 覆盖更丰富，但标注成本增加，仍需检查代表性 | 较完整的内部评估 |

数量不是质量保证。

200 道重复问题、简单问题，可能还不如 50 道覆盖充分且标注可靠的问题。

## **第四阶段：问题集与标准答案、相关性标注**

### **27. 为什么固定问题集只有 Query 还不够，还需要相关性判断依据？**

因为只有 Query，只能知道系统检索了什么，却不知道它检索得对不对。

例如：

```
Query：MODEL-A 的 E1002 故障如何处理？

检索结果：
Chunk-A：MODEL-A E1002 故障定义
Chunk-B：MODEL-B E1002 处理步骤
Chunk-C：MODEL-A E1002 维修步骤
```

如果没有相关性标注，就无法准确判断哪些结果应该被计为有效召回。

因此，需要 Query 与标准证据之间的映射。

### **28. 什么是 Query-Document 相关性标注？它在检索评估中有什么作用？**

Query-Document 相关性标注，就是针对一个问题，判断某个文档或 Chunk 是否能够支持该问题的知识需求。

例如：

| Query ID | Evidence ID | 相关性分数 |
| -------- | ----------- | ---------- |
| Q001     | E001        | 2          |
| Q001     | E002        | 1          |
| Q001     | E003        | 0          |

可以定义三级相关性：

- 2：完全相关，直接支持问题的核心需求；
- 1：部分相关，提供有用背景或辅助信息；
- 0：不相关，不能支持问题。

其作用是建立统一评价依据，供 Recall、Precision、MRR、NDCG 等指标使用。

BEIR 的 qrels 文件也使用 query ID、document ID 和 relevance score 来保存相关性判断。

Datasets at Hugging Face



### **29. 什么是 Ground Truth？它与模型生成的答案有什么区别？**

Ground Truth 是经过人工审核或权威数据确认的标准依据。

例如：

```
问题：
E1002 表示什么故障？

Ground Truth：
设备维修手册 V3.2 第 45 页：
E1002 = 主轴温度异常。
```

模型生成答案：

```
E1002 表示主轴温度异常，建议检查冷却系统。
```

两者不是一回事。

Ground Truth 是评估基准；模型生成答案是待评价的输出。

对于检索评估，Ground Truth 的核心是相关证据及其关系，而不是必须先准备一段自然语言标准答案。

Ragas 的评估数据结构也区分了输入、检索上下文、参考上下文和参考答案。

### **30. 为什么不能把某一次检索得到的 Top-K 结果直接当作标准答案？**

因为这样会形成循环验证。

假设：

1. 使用配置 A 检索 Top-K；
2. 把 A 找到的文档当成 Ground Truth；
3. 再用配置 B 与 A 比较。

这相当于把 A 的结果当作标准答案，天然偏向 A。

正确做法是先从权威文档中确定相关证据，再让不同检索配置进行测试。

### **31. 如何判断一个 Chunk 对某个问题是完全相关、部分相关还是不相关？**

可以建立业务相关性规则。

例如：

Query：

> MODEL-A 的 E1002 故障如何排查？

| Chunk 内容                    | 相关性   |
| ----------------------------- | -------- |
| MODEL-A 的 E1002 故障定义     | 1        |
| MODEL-A 的 E1002 详细排查步骤 | 2        |
| MODEL-B 的 E1002 排查步骤     | 0 或极低 |
| 通用主轴温度维护说明          | 1        |
| 与主轴无关的电机润滑说明      | 0        |

这里的关键是：相关性应该根据问题的业务需求判断，而不是只看文字是否相似。

对于存在设备型号约束的查询，其他型号的维修步骤即使语义相似，也不一定具有业务相关性。

### **32. 为什么需要记录一个问题对应的多个相关证据，而不是只记录一个标准 Chunk？**

因为一个问题可能需要多份证据共同回答。

例如：

```
Q001：MODEL-A 的 E1002 应该如何处理？
```

其相关证据可能有：

- E001：故障代码定义；
- E002：温度检测标准；
- E003：故障排查流程；
- E004：安全操作要求。

如果只标注 E003，可能忽略一个事实：系统召回 E001、E002、E004 也可能对回答有价值。

多证据标注还能检查系统是否只检索到了问题的一部分。

### **33. 当不同 Chunk Size 导致原始文档被切分成不同块时，原有 Chunk ID 的相关性标注还能直接复用吗？**

一般不能直接复用。

例如，同一个文档：

Chunk Size = 300：

```
C001：第 1~300 个字符
C002：第 301~600 个字符
C003：第 601~900 个字符
```

Chunk Size = 800：

```
C101：第 1~800 个字符
C102：第 801~1600 个字符
```

旧 Chunk ID 与新 Chunk ID 不再一一对应。

因此，应该把相关性标注尽量维护在更稳定的文档证据层，而不是单纯绑定当前 Chunk ID。

### **34. 如何使用稳定的 sourceId、documentId、原文页码或原文偏移量维护不同切块方案之间的证据对应关系？**

建议维护一套稳定的证据定位信息：

```
sourceId
documentId
documentVersion
pageNumber
startOffset
endOffset
sectionPath
```

例如：

```
{
  "sourceId": "manual-model-a",
  "documentId": "doc-001",
  "documentVersion": "v3.2",
  "pageNumber": 45,
  "startOffset": 1200,
  "endOffset": 1680,
  "sectionPath": "故障处理/主轴温度异常/E1002"
}
```

不同 Chunk Size 生成的 Chunk，可以通过原文偏移范围映射到同一段原始证据。

需要注意：

- 页码必须明确是 PDF 物理页码还是文档标注页码；
- offset 必须明确字符、字节或 Token 单位；
- 文档更新后 offset 可能变化；
- 文档重解析后应保留版本映射关系。

对于当前项目，建议把 sourceId、documentId、documentVersion、pageNumber 和原文位置纳入证据元数据。

### **35. 如何处理多个 Chunk 都包含同一条知识、但内容粒度不同的情况？**

不能简单把它们当成完全独立的多个标准证据。

例如：

```
Chunk-A：完整章节，包含 E1002 定义和处理步骤
Chunk-B：只包含 E1002 定义
Chunk-C：只包含 E1002 处理步骤
```

可以先将原文证据定义为一个或多个稳定的 Evidence Unit，再标注它们与 Query 的关系。

评估 Chunk 时，通过 Chunk 与 Evidence Unit 的覆盖关系判断其有效程度。

否则，Chunk-A 可能因为覆盖了两条知识而被重复计算，Chunk-B 和 Chunk-C 也可能造成相关性计数偏差。

### **36. 当知识库存在相互冲突或不同版本的文档时，应该如何定义相关性标注？**

必须先定义知识权威性规则。

例如：

- 已发布维修手册优先于草稿；
- 当前生效版本优先于历史版本；
- 设备型号专属手册优先于通用手册；
- 厂商正式公告优先于未经确认的内部记录。

不能把所有内容都标记为同等相关。

还需要记录：

```
documentVersion
effectiveFrom
effectiveTo
documentStatus
authorityLevel
```

对历史问题应明确是否允许历史版本作为证据。

对当前维修问题，已经失效的旧步骤可能具有文本相关性，但不应被判为当前业务上的有效证据。

### **37. 为什么相关性标注需要统一规则，并尽可能经过人工复核？**

因为标注本身会影响最终实验结论。

例如，一个评测人员认为通用故障说明属于部分相关，另一个认为完全不相关，那么同样的检索结果可能得到不同分数。

建议：

1. 编写标注规范；
2. 选取样本进行试标；
3. 对分歧进行讨论；
4. 高风险证据由设备专家复核；
5. 记录标注人员和版本；
6. 保留标注修订历史。

必要时可以计算标注人员之间的一致性，但不能只依赖一致性分数，最终仍要保证业务判断正确。

## **第五阶段：固定问题集如何支撑参数对照实验**

### **38. 假设需要对比 Top-K = 3、5、10，为什么必须让三组配置执行完全相同的问题？**

因为 Top-K 本身就改变每个问题能够获取的候选文档数量。

如果三个配置使用同一批问题，就能分析：

- Top-K 从 3 增加到 5 后新增了哪些相关证据？
- 从 5 增加到 10 后是否继续提升 Recall？
- 新增结果中有多少是噪声？
- Precision 是否下降？

例如：

| 配置 | Top-K | Recall\@K |
| ---- | ----- | --------- |
| A    | 3     | 0.60      |
| B    | 5     | 0.75      |
| C    | 10    | 0.85      |

只有查询和标注一致时，才适合把差异归因于 Top-K 的变化。

### **39. 假设需要对比 Chunk Size = 300、500、800，如何确保问题集不变，同时正确处理切块结果变化？**

固定 Query ID、Query Text、原始文档集合和 Ground Truth 证据定义。

只改变 Chunk Size。

实验流程：

```
相同原始文档版本
       |
       +--> Chunk Size 300 --> Embedding --> 检索
       |
       +--> Chunk Size 500 --> Embedding --> 检索
       |
       +--> Chunk Size 800 --> Embedding --> 检索
       |
同一批 Query 和 Evidence Ground Truth
       |
逐题评估
```

注意，不同 Chunk Size 需要重新生成 Chunk 并重新计算 Embedding。

因为 Chunk 内容变了，不能继续使用旧向量。

评估时通过原文位置或 Evidence Unit 映射来判断新 Chunk 是否覆盖标准证据，而不是直接拿旧 Chunk ID 进行比较。

### **40. 假设需要对比 Overlap = 0、50、100，为什么不能同时更换测试问题？**

因为 Overlap 会改变切块边界和 Chunk 之间的内容重复程度。

例如：

- Overlap = 0：相邻 Chunk 不重叠；
- Overlap = 50：相邻 Chunk 共享约定单位的 50 个字符或 Token；
- Overlap = 100：重叠范围进一步增加。

如果问题也发生变化，就无法判断召回差异是切块策略导致的，还是查询变化导致的。

还需要明确 Overlap 的单位，不要在实验中把字符数与 Token 数混用。

### **41. 假设需要测试 Similarity Threshold = 0.60、0.70、0.80，固定问题集能够帮助分析什么？**

它能够让我们观察每道问题在不同阈值下：

- 召回结果数量变化；
- 相关证据是否被过滤；
- 无关 Chunk 是否减少；
- 是否出现空结果；
- Recall 和 Precision 如何变化。

示例：

| Query | Threshold 0.60 | 0.70      | 0.80      |
| ----- | -------------- | --------- | --------- |
| Q001  | 召回 5 个      | 召回 3 个 | 召回 1 个 |
| Q002  | 召回 8 个      | 召回 4 个 | 召回 0 个 |
| Q003  | 召回 2 个      | 召回 1 个 | 召回 0 个 |

可以观察阈值提高后是否误删正确证据。

注意：相似度阈值的具体含义取决于向量数据库的距离度量和框架实现。Spring AI 的 `SearchRequest` 提供 `topK`、`similarityThreshold` 和过滤表达式等检索参数，但具体阈值不能跨模型、跨向量空间直接照搬。

### **42. 为什么实验时还需要固定原始文档集合及其版本？**

因为检索效果既由 Query 决定，也由知识库内容决定。

例如，A 组使用维修手册 V2.0，B 组使用 V3.0。

即使 B 的 Recall 更高，也不能直接认为它的检索参数更好。

可能只是 V3.0 新增了正确证据。

因此必须固定：

- 文档清单；
- 文档内容；
- 文档版本；
- 文档状态；
- 解析结果；
- 文档元数据。

### **43. 除了问题集和文档集合，还应该固定哪些条件，例如 Embedding 模型、向量维度、距离度量和检索算法？**

建议固定以下条件：

| 类别      | 需要记录或固定的条件              |
| --------- | --------------------------------- |
| 查询      | Query ID、文本、预处理            |
| 文档      | 文档清单、内容版本、状态          |
| 切块      | Chunk Size、Overlap、切分算法     |
| Embedding | 模型、版本、维度                  |
| 向量      | 相似度/距离度量、归一化方式       |
| 索引      | HNSW/IVFFlat、关键索引参数        |
| 检索      | Top-K、Threshold、Metadata Filter |
| 排序      | Reranker 模型、版本、排序规则     |
| 运行环境  | PostgreSQL、pgvector、硬件、并发  |
| 数据      | 数据库快照、索引构建方式          |

如果目标是测试某一个参数，其余条件都应保持一致。

如果某个实验明确要测试整个检索策略，就要把改变的因素完整记录下来。

### **44. 为什么实验中不应该同时修改 Chunk Size、Overlap、Top-K 和 Threshold，却把最终效果变化归因于某一个参数？**

因为多个变量同时变化，无法判断每个参数分别造成了什么影响。

例如：

```
实验 A：
Chunk Size = 300
Overlap = 0
Top-K = 5
Threshold = 0.7

实验 B：
Chunk Size = 800
Overlap = 100
Top-K = 10
Threshold = 0.6
```

如果 B 的 Recall 提高，可能是：

- Chunk Size 增大；
- Overlap 增大；
- Top-K 增大；
- Threshold 降低；
- 多个参数之间的交互作用。

无法简单归因于 Chunk Size。

### **45. 什么是控制变量法？它在 RAG 检索参数调优中如何应用？**

控制变量法就是：

**有目的地改变一个实验因素，尽量保持其他因素不变，观察结果变化。**

例如，要研究 Top-K：

```
固定：
问题集
文档版本
Chunk Size
Overlap
Embedding 模型
索引类型
Similarity Threshold

改变：
Top-K = 3、5、10
```

最后比较 Recall\@K、Precision\@K、延迟和返回文档数量。

这可以帮助回答：在当前知识库和当前问题分布下，Top-K 的变化带来了什么影响？

### **46. 什么情况下应该采用单变量实验，什么情况下应该采用多因素组合实验？**

**单变量实验：**

适合初期理解参数影响、排查问题、定位瓶颈。

例如，只调整 Top-K。

**多因素组合实验：**

适合已经了解单个参数影响后，研究参数之间的交互。

例如：

| 组合 | Chunk Size | Overlap | Top-K |
| ---- | ---------- | ------- | ----- |
| A    | 300        | 0       | 5     |
| B    | 300        | 50      | 10    |
| C    | 500        | 0       | 10    |
| D    | 500        | 50      | 5     |

组合实验应使用明确的实验设计，例如全因子、部分因子或其他有计划的设计方式。

不能随意排列几组参数后就声称找到了全局最优配置。

### **47. 如何建立实验记录，确保每组参数配置、问题集版本和运行结果可以追溯？**

建议每次实验生成唯一 `experimentId`，记录：

```
experimentId
datasetVersion
corpusVersion
chunkConfig
embeddingModel
indexConfig
retrievalConfig
environmentVersion
runAt
gitCommit
resultFile
```

每道问题还要记录：

```
experimentId
queryId
retrievedChunkIds
retrievalScores
retrievalRanks
relevantEvidenceIds
metrics
```

这样以后才能复现：

> 为什么 D36 实验中的 Top-K=10 比 Top-K=5 的 Recall 更高？

必须能找到配置、问题、原始检索结果和 Ground Truth。

### **48. 为什么应该使用稳定的 Query ID，而不是仅依靠问题文本作为实验记录的唯一标识？**

因为问题文本可能发生变化，也可能有多种表达方式。

例如：

```
Q001：E1002 代表什么故障？
Q002：请问 E1002 是什么意思？
```

它们可能表达同一知识需求，但文本不同。

另外，问题可能经过修订：

```
Q001 v1：E1002 代表什么故障？
Q001 v2：MODEL-A 的 E1002 代表什么故障？
```

稳定 Query ID 可以保持样本身份，版本字段记录内容变化。

不要简单地把文本 Hash 当作唯一业务 ID，因为修改一个字就会生成新的 Hash，也不利于维护问题的版本关系。

## **第六阶段：实验结果如何比较和解释**

### **49. 固定问题集如何帮助比较不同配置的 Recall\@K？**

Recall\@K 衡量前 K 个检索结果中找到的相关证据，占该问题全部相关证据的比例。

\\[ Recall\@K(q)= \frac{|Relevant(q)\cap Retrieved_K(q)|} {|Relevant(q)|} \\]

例如，Q001 有 4 个标准相关证据：

```
E1、E2、E3、E4
```

配置 A 的 Top-5 找到了：

```
E1、E2
```

那么：

\\[ Recall\@5 = \frac{2}{4}=0.5 \\]

配置 B 找到了：

```
E1、E2、E3
```

那么：

\\[ Recall\@5 = \frac{3}{4}=0.75 \\]

固定问题集和 Ground Truth 使两组配置拥有相同的相关证据分母，因此可以进行比较。

注意：如果使用分级相关性标注，普通 Recall 通常需要先定义哪些等级算作“相关”。例如可以规定相关性分数大于 0 即算相关。

### **50. 为什么不同参数配置应该尽量逐题对比，而不仅仅比较最终平均指标？**

因为平均值会掩盖问题类别和单题差异。

例如：

- A 在故障代码问题上表现很好；
- B 在复杂自然语言问题上表现很好。

只看平均 Recall，可能看不出各自的适用范围。

逐题比较可以明确：

- 哪些问题改善；
- 哪些问题退化；
- 哪些问题没有变化；
- 退化问题是否具有共同特征。

### **51. 如果配置 A 在 30 道题中有 20 道表现更好，但配置 B 的平均 Recall\@K 更高，应该如何分析？**

不能只看“赢了多少题”。

因为每道题的 Recall 值可能不同，每道问题的相关证据数量也不同。

例如：

A 在 20 道题上各提升 0.1，但在另外 10 道题上下降 0.5。

B 可能只在少数题上提升很多，因此平均 Recall 更高。

建议同时分析：

1. Macro Recall：先计算每道题的 Recall，再对题目取平均。
2. Micro Recall：汇总所有问题的相关证据命中数和相关证据总数，再计算整体比例。
3. 逐题胜负和差值。
4. 各类别的指标。
5. 高优先级问题的退化情况。

其中 Macro 与 Micro 的计算口径不同，不能混为一谈。

### **52. 为什么应该关注不同问题类别的检索效果，而不能只看整体平均值？**

因为整体平均值可能掩盖关键业务类别的风险。

例如：

| 类别       | 配置 A Recall\@5 | 配置 B Recall\@5 |
| ---------- | ---------------- | ---------------- |
| 故障代码   | 0.95             | 0.75             |
| 故障原因   | 0.70             | 0.85             |
| 维修步骤   | 0.70             | 0.80             |
| 多文档问题 | 0.55             | 0.75             |

B 的整体效果可能更好，但故障代码检索明显退化。

对于制造设备项目，故障代码和零件编号可能是关键业务场景，不能因为其他类别进步就忽略它们。

### **53. 如何通过逐题结果定位某一组参数配置的优势和劣势？**

建立 Query 级别的结果明细。

例如：

| Query ID | 类别     | A Recall\@5 | B Recall\@5 | 结论   |
| -------- | -------- | ----------- | ----------- | ------ |
| Q001     | 故障代码 | 1.0         | 0.5         | B 退化 |
| Q002     | 故障原因 | 0.5         | 1.0         | B 改善 |
| Q003     | 维修步骤 | 0.5         | 0.5         | 无变化 |
| Q004     | 多文档   | 0.0         | 0.5         | B 改善 |

再结合检索原始结果排查：

- 是否漏掉标准证据；
- 是否召回了错误型号的文档；
- 是否被 Threshold 过滤；
- 是否受到分块边界影响；
- 是否只召回了部分必要证据；
- 是否被无关高分 Chunk 挤占了 Top-K。

### **54. 固定问题集如何帮助判断某次优化是否真正改善了检索质量？**

它提供优化前后的相同测试样本。

例如：

```
D36-实验前：
Recall@5 = 0.70

D36-实验后：
Recall@5 = 0.82
```

还需要验证：

- 是否使用同一问题集版本；
- 是否使用同一文档快照；
- 是否使用同一 Ground Truth；
- 是否只有计划中的参数发生变化；
- 是否有关键类别明显退化；
- 是否存在统计上的不确定性。

只有这些条件成立，才能更有把握地认为优化真正改善了检索质量。

### **55. 如果参数调整后整体 Recall\@K 提高，但某类故障代码问题的 Precision\@K 明显下降，应该如何判断优化是否成功？**

不能直接宣布优化成功。

需要根据业务优先级判断。

例如：

- Recall 提高：找到更多相关证据；
- 故障代码 Precision 下降：可能混入其他设备或其他故障代码的结果。

制造设备场景中，错误设备型号或故障代码可能造成严重后果。

因此建议增加类别级验收门槛，例如：

```
整体 Recall@5 不低于目标值
故障代码 Precision@5 不低于目标值
型号约束命中率达到要求
高风险问题不得出现关键证据遗漏
```

这些阈值应由业务和实际评测结果确定，不宜随意编造通用标准。

### **56. 为什么需要保留每次实验的原始检索结果、排序结果和评估指标，而不是只保存一个平均分？**

因为平均分不能告诉你为什么变好或变差。

必须保留：

- Query ID；
- 每个返回 Chunk 的 ID；
- 排序位置；
- 相似度或距离分数；
- 相关性标注；
- 召回来源；
- Filter 条件；
- 实际检索参数；
- 逐题指标；
- 汇总指标。

这样才能从最终结果追溯到具体失败案例。

### **57. 当测试问题数量较少时，为什么不能过度解读几个百分点的指标变化？**

因为少量样本的指标很容易受到单个问题的影响。

例如，10 道问题中有 1 道题从 0 变为 1，就可能显著改变平均值。

这并不一定意味着系统整体能力发生了稳定变化。

因此，应当关注：

- 样本量；
- 问题覆盖范围；
- 逐题变化；
- 置信区间；
- 多次重复结果；
- 业务重要性。

### **58. 如何通过多次重复运行、置信区间或统计检验判断实验结果是否具有稳定性？**

需要先区分两种情况。

**第一种：确定性检索。**

如果使用相同数据、相同查询、精确向量搜索和确定性排序，结果可能完全一致。此时重复执行主要用于检查环境或实现是否存在非预期差异。

**第二种：包含随机性或近似搜索的检索。**

例如索引构建、并发环境、模型推理或某些 ANN 实现可能带来波动。此时可以重复运行，保存每次结果。

分析方式包括：

- 对 Query 做配对比较；
- Bootstrap 估计指标差值的置信区间；
- 对逐题 Recall 差异使用适合配对数据的统计检验；
- 对多个类别分别分析。

不要把同一道问题重复执行 100 次，当成 100 个独立问题样本。这属于伪重复，会夸大样本量。

### **59. 为什么固定问题集并不意味着每道问题的权重必须相同？**

因为不同问题的业务重要性不同。

例如：

- 普通设备介绍；
- 关键设备停机故障；
- 安全操作规范；
- 高风险维修流程。

这些问题的业务后果不相同。

可以同时计算：

- Macro 平均指标：每道问题等权；
- 类别加权指标：按照预设业务权重；
- 高风险问题单独指标。

权重必须提前定义，不能看到实验结果后再临时调整权重来支持某个方案。

### **60. 如何避免少数高频问题主导整体评估结果？**

可以使用：

1. 查询去重；
2. 按业务场景分层抽样；
3. 限制同一知识点的重复样本数量；
4. 单独报告高频问题与长尾问题；
5. 同时输出 Macro、Micro 和类别级指标；
6. 采用业务权重时提前确定权重。

这样才能避免大量相似问题把整体指标推向某一类场景。

## **第七阶段：固定问题集的边界与生产级应用**

### **61. 固定问题集为什么不能完全代表真实用户的所有提问？**

因为真实用户的提问不断变化。

生产环境会出现：

- 新设备型号；
- 新故障代码；
- 新的口语表达；
- 用户上下文缺失；
- 多轮追问；
- 新维修手册；
- 临时业务需求。

固定问题集只能代表特定时间和特定业务范围内的一组测试样本。

### **62. 固定问题集长期不更新，可能导致哪些评估偏差？**

主要包括：

- 无法反映新增业务；
- 无法覆盖新设备型号；
- 对历史问题过度优化；
- 新的用户表达方式无法被评估；
- 线上问题分布变化导致测试集失真；
- 旧文档与新文档之间的知识变化无法被识别。

所以固定问题集需要版本化，但不能永远保持不变。

### **63. 什么是测试集过拟合？如果开发人员反复针对固定问题集调参，会产生什么风险？**

测试集过拟合，是指系统逐渐针对测试样本进行专门优化，最后在测试集上表现很好，但面对未见过的问题时表现不佳。

例如：

1. 发现 Q001 召回失败；
2. 专门增加 Q001 的关键词；
3. 再调整切块参数以适配 Q001；
4. 多轮反复优化；
5. 最后测试集 Recall 很高。

这可能只是记住了测试集的特征，而不是提高了通用检索能力。

### **64. 为什么应该区分训练集、开发集和最终测试集，或者至少区分参数调优集与独立验收集？**

因为参数调优和最终验收承担不同职责。

| 数据集     | 作用                             |
| ---------- | -------------------------------- |
| 训练集     | 用于模型训练或监督学习           |
| 开发集     | 用于开发、参数调整和方案选择     |
| 最终测试集 | 用于独立验收，尽量不参与反复调参 |

当前 RAG 项目可能没有训练 Embedding 或 Reranker 模型，因此可以先采用：

- 调优集：用于选择 Chunk Size、Top-K、Threshold 等参数；
- 独立验收集：用于验证调优后的配置。

最终测试集应尽量减少被反复观察和针对性优化的机会。

### **65. 当 Embedding 模型、文档内容或 Chunk 策略发生变化时，是否需要重新评估问题集和相关性标注？**

需要重新评估，但不一定全部重新人工标注。

具体区分：

**Embedding 模型发生变化：**

通常不需要重新定义问题，但必须重新生成文档向量和查询向量，并重新执行检索评估。

**Chunk 策略发生变化：**

问题集可以复用，但原始 Chunk ID 的标注映射不能直接复用。需要重新映射新 Chunk 与稳定证据单元之间的关系。

**文档内容发生变化：**

必须检查 Ground Truth 是否仍然正确。如果维修手册更新了处理步骤，旧证据可能失效，需要更新标注并产生新数据版本。

### **66. 如何判断问题集已经无法代表当前线上用户的真实查询分布？**

可以定期比较线上日志和固定问题集的分布：

- 设备型号分布；
- 故障代码分布；
- 问题类别；
- 问题长度；
- 模糊表达比例；
- 无答案问题比例；
- 多轮追问比例；
- 新词和新实体出现频率。

如果线上出现大量新设备、新故障码或新的查询风格，而固定问题集中没有对应样本，就说明需要扩充。

### **67. 为什么应该定期从真实用户日志中抽取新问题，并补充到评测集？**

因为真实日志能够反映系统遇到的实际问题。

例如：

```
用户：主轴工作一段时间就开始抖动。
用户：更换轴承后为什么还是报 E1002？
用户：MODEL-A 和 MODEL-B 的冷却方式有什么区别？
```

这些问题可能是专家构造时容易遗漏的真实表达。

但必须经过：

1. 隐私与敏感信息处理；
2. 去重和分类；
3. 业务语义确认；
4. Ground Truth 标注；
5. 标注复核；
6. 数据集版本更新。

### **68. 如何在固定基准问题集与动态线上问题集之间取得平衡？**

建议拆成两个部分：

**固定基准集（Benchmark Set）：**

- 稳定；
- 版本化；
- 用于参数对照；
- 用于回归测试；
- 不频繁变更。

**动态问题集（Online Evaluation Set）：**

- 定期从生产日志抽样；
- 跟踪新设备和新故障；
- 反映真实用户分布；
- 定期审核和扩充。

每次发布新检索配置时，先跑固定基准集，再跑最新的动态问题集。

### **69. 当知识库新增设备型号或维修手册时，应该如何扩展固定问题集，同时保证历史实验可比较？**

不要直接修改原有版本。

例如：

```
RAG-Eval-v1.0
RAG-Eval-v1.1
RAG-Eval-v1.2
```

新增设备型号时：

- 保留旧 Query ID；
- 新建新设备相关 Query ID；
- 标注新增文档的证据；
- 记录文档版本；
- 保存版本变更说明；
- 保留旧数据集供历史实验复现。

对比不同版本的实验结果时，要明确区分：

- 在同一个数据集版本上的参数比较；
- 在不同数据集版本上的业务覆盖变化。

两者不能混为一谈。

### **70. 如何设计一套可持续迭代、可版本化、可复现的 RAG 检索评测集？**

建议将评测集设计为四类核心数据：

**第一类：查询数据**

```
queryId
queryText
queryCategory
queryStyle
difficulty
answerable
priority
datasetVersion
```

**第二类：文档证据数据**

```
evidenceId
sourceId
documentId
documentVersion
pageNumber
startOffset
endOffset
sectionPath
```

**第三类：相关性标注数据**

```
queryId
evidenceId
relevanceGrade
requiredEvidence
annotationStatus
annotator
```

**第四类：实验结果数据**

```
experimentId
queryId
retrievalConfig
retrievedChunkIds
retrievedRanks
retrievalScores
recallAtK
precisionAtK
mrr
ndcg
latencyMs
```

每次实验必须保存：

- 代码 Git Commit；
- 问题集版本；
- 文档集合版本；
- Chunk 配置；
- Embedding 模型；
- 向量索引参数；
- 检索配置；
- 原始检索结果；
- 指标结果。

这样才能做到可追溯、可复现和可比较。

### **71. 在制造设备故障知识库项目中，如何使用固定问题集验证不同检索参数是否真正改善了故障知识召回？**

建议围绕以下问题类型设计评测集：

| 类型       | 示例                                         |
| ---------- | -------------------------------------------- |
| 故障代码   | MODEL-A 的 E1002 是什么故障？                |
| 设备型号   | MODEL-A 主轴支持哪些温度范围？               |
| 故障原因   | 主轴运行一段时间后温度升高，可能是什么原因？ |
| 维修步骤   | E1002 故障应该如何排查？                     |
| 零件信息   | MODEL-A 主轴轴承的备件型号是什么？           |
| 多证据问题 | E1002 的排查步骤和更换轴承的安全要求是什么？ |
| 模糊问题   | 设备运行一段时间后很烫，还报警怎么办？       |
| 无答案问题 | 知识库没有收录的 MODEL-Z 故障如何处理？      |

然后对比：

```
Chunk Size：
300 / 500 / 800

Overlap：
0 / 50 / 100

Top-K：
3 / 5 / 10

Threshold：
0.60 / 0.70 / 0.80
```

初期不需要直接做所有参数的全组合实验。

先单变量实验：

1. 固定其余参数，测试 Chunk Size；
2. 选取合适 Chunk Size，测试 Overlap；
3. 固定切块配置，测试 Top-K；
4. 固定其他参数，测试 Threshold；
5. 再考虑组合实验。

最后比较：

- Recall\@K；
- Precision\@K；
- MRR；
- NDCG；
- 各类别指标；
- 无答案问题误召回情况；
- 查询耗时；
- 高风险问题的证据命中情况。

这样才能知道检索参数是否真正改善了故障知识召回，而不是只让某个整体平均分变高。

### **72. 如果让你为当前 Spring AI + PostgreSQL + pgvector 项目建立检索参数对照实验体系，你会如何设计问题集、标注规则、实验矩阵和评估流程？**

我建议设计一个轻量、可运行、逐步扩展的评测体系，不需要一开始就引入复杂的评测平台。

#### **72.1 评测目标**

第一阶段只回答四个核心问题：

1. 当前检索配置能否找到正确故障知识？
2. 哪些参数影响了相关证据召回？
3. 哪些问题类别存在明显检索短板？
4. 新配置是否改善了检索效果，同时没有引入关键业务退化？

先评估检索层，不把 LLM 最终回答质量混入第一轮参数对照。

#### **72.2 问题集设计**

建议从 50 道问题开始，作为第一版内部基准集。

| 问题类别         | 建议数量 |
| ---------------- | -------- |
| 故障代码精确查询 | 10       |
| 设备型号和参数   | 5        |
| 故障原因         | 10       |
| 维修步骤         | 8        |
| 零件信息         | 5        |
| 多文档关联       | 5        |
| 口语和模糊表达   | 4        |
| 无答案问题       | 3        |
| **合计**         | **50**   |

这是一份启动配置，不是统计意义上的充分样本量。后续应根据线上流量、风险级别和覆盖缺口扩充。

#### **72.3 Ground Truth 标注规则**

建议使用稳定的 Evidence ID，而不是直接把某个 Chunk ID 作为标准证据。

例如：

```
Query：
Q001

标准证据：
E001、E002、E003

E001：
sourceId = manual-model-a
documentId = doc-001
documentVersion = v3.2
pageNumber = 45
startOffset = 1200
endOffset = 1680
```

相关性分级：

| 分值 | 规则                     |
| ---- | ------------------------ |
| 2    | 能直接回答问题的核心证据 |
| 1    | 有帮助的辅助证据         |
| 0    | 不相关或业务条件不匹配   |

同时标记：

```
requiredEvidence = true/false
answerable = true/false
```

对于需要多个证据共同支持的问题，增加 `requiredEvidence`，避免系统只召回一部分证据却被判定为完整命中。

#### **72.4 实验矩阵**

先做单变量实验：

| 实验    | 改变参数   | 对照值             |
| ------- | ---------- | ------------------ |
| EXP-001 | Chunk Size | 300 / 500 / 800    |
| EXP-002 | Overlap    | 0 / 50 / 100       |
| EXP-003 | Top-K      | 3 / 5 / 10         |
| EXP-004 | Threshold  | 0.60 / 0.70 / 0.80 |

实验过程中固定：

- Query Set；
- 文档快照；
- Ground Truth；
- Embedding 模型及版本；
- pgvector 距离度量；
- Metadata Filter；
- 代码版本；
- 数据库版本。

如果测试 Chunk Size 或 Overlap，必须重新切块和生成向量。不能只修改配置，却继续使用旧 Chunk 和旧向量。

#### **72.5 项目模块设计**

建议新增一个轻量评测模块：

```
evaluation
├── dataset
│   ├── QueryDataset
│   ├── QueryItem
│   └── DatasetVersion
│
├── groundtruth
│   ├── EvidenceItem
│   ├── RelevanceJudgment
│   └── EvidenceMapping
│
├── experiment
│   ├── ExperimentConfig
│   ├── ExperimentRunner
│   └── ExperimentResult
│
├── metrics
│   ├── RecallAtKCalculator
│   ├── PrecisionAtKCalculator
│   ├── MrrCalculator
│   └── NdcgCalculator
│
└── report
    ├── QueryResultReport
    ├── CategorySummary
    └── ExperimentComparison
```

第一版完全可以使用 JSON/CSV 文件存储问题集和结果，不必急着把评测数据全部设计成数据库表。

#### **72.6 实验执行流程**

## **最后总结：这 72 道题真正需要掌握的内容**

固定问题集不是简单地把 50 道问题写进 JSON 文件。

它实际上是一套完整的实验基准：

## **RAG 检索评测的五个核心组成**

1. **固定问题集（Query Set）**

   用相同问题控制查询样本差异。
2. **固定文档集合（Corpus Snapshot）**

   用相同文档和版本控制知识库差异。
3. **相关性标注（Ground Truth / Qrels）**

   明确什么证据才算正确召回。
4. **实验配置（Experiment Config）**

   明确本次究竟改变了什么参数。
5. **逐题结果与指标（Results / Metrics）**

   不只比较平均分，还分析类别、失败案例和业务风险。

最重要的一句话：

**没有固定问题集，检索参数实验就容易受到测试样本变化的干扰；没有相关性标注，就不知道检索结果是否正确；没有逐题记录，就不知道指标变化究竟来自哪里。**

对于你当前的制造设备故障知识库项目，我建议先完成 **50 道固定问题 + 稳定 Evidence ID + Top-K 三组对照实验**，先跑通实验闭环，再扩充 Chunk Size、Overlap、Threshold 和组合实验。

## **补充：这套评测体系中最容易忽略的 6 个细节**

### **1. 固定问题集与随机抽样并不矛盾**

这是一个容易混淆的概念。

**随机抽样**描述的是问题如何从真实用户日志中选出来；**固定问题集**描述的是选出来的问题是否在多次实验中保持一致。

例如：

```
线上日志：10000 条问题
       |
       | 分层随机抽样
       v
选出 200 道问题
       |
       | 人工审核、相关性标注、版本冻结
       v
RAG-Eval-v1.0
       |
       +--> Top-K = 3
       +--> Top-K = 5
       +--> Top-K = 10
```

这 200 道问题既是随机抽样的结果，也是后续实验使用的固定问题集。

### **2. 固定 Query Text，还要固定问题背后的 Information Need**

同样的问题文本，可能对应不同的知识需求。

例如：

> Python 是什么？

可能是询问 Python 编程语言，也可能是在询问蟒蛇。

因此，问题集最好增加一个字段：

```
informationNeed
```

描述这道问题真正希望解决的业务问题。

对于制造设备知识库，可以这样记录：

```
{
  "queryId": "Q001",
  "queryText": "E1002 怎么处理？",
  "informationNeed": "查询 MODEL-A 设备 E1002 故障的排查步骤",
  "equipmentModel": "MODEL-A",
  "faultCode": "E1002"
}
```

信息检索评估关注的是文档是否满足用户的信息需求，而不只是文档是否包含 Query 中的关键词。Stanford《信息检索导论》第 8 章对此有专门说明。

[image](https://www.google.com/s2/favicons?domain=https://nlp.stanford.edu\&sz=32)

斯坦福NLP



### **3. 50 道问题是合理的起点，但不是通用的统计保证**

Stanford《信息检索导论》提到，在传统信息检索测试集合中，50 个 information needs 通常被认为是一个足够的最低参考数量。

但这不是说：

- 50 道问题一定具有代表性；
- 50 道问题一定能得到统计显著结论；
- 任何业务只需要 50 道问题。

你当前项目先从 50 道开始是合理的工程选择，但要结合类别覆盖、标注质量和线上查询分布继续扩充。

[image](https://www.google.com/s2/favicons?domain=https://nlp.stanford.edu\&sz=32)

斯坦福NLP



### **4. 统计检验应以 Query 为比较单位，而不是把重复执行次数当成新样本**

假设配置 A 和 B 分别运行相同的 50 道问题。

应当按 Query ID 配对比较：

```
Q001：A Recall@5 - B Recall@5
Q002：A Recall@5 - B Recall@5
...
Q050：A Recall@5 - B Recall@5
```

可以对这些逐题差值进行 Bootstrap，估计平均指标差异的置信区间。

例如：

```
B - A 的平均 Recall@5 差值：+0.04
95% Bootstrap CI：[+0.01, +0.07]
```

这里仅为格式示例，不是你的项目实验数据。

如果使用 ANN 或其他存在非确定性因素的组件，可以额外重复运行，观察运行波动。但重复执行 Q001 十次，不能当成十道独立问题。

### **5. Chunk Size 与 Overlap 必须明确单位**

例如：

```
Chunk Size = 500
Overlap = 50
```

必须进一步说明：

```
Chunk Size：500 Tokens
Overlap：50 Tokens
```

还是：

```
Chunk Size：500 Characters
Overlap：50 Characters
```

两种切块策略的含义完全不同。

还需要记录分词器、文本清洗规则和切块算法版本，否则即使参数数字相同，也不一定生成相同的 Chunk。

### **6. 相关性标注应尽量落到稳定证据，而不是依赖检索系统当前的 Chunk ID**

Ragas 的评测数据结构支持 `retrieved_context_ids` 和 `reference_context_ids`，其 ID-Based Context Recall 可以直接比较检索上下文 ID 与参考上下文 ID。

[image](https://www.google.com/s2/favicons?domain=https://docs.ragas.io\&sz=32)

Ragas+1



但在你的项目里，不同 Chunk Size 会改变 Chunk ID。因此可以进一步建立：

```
Query
  |
  v
Evidence Unit（稳定的原文证据）
  |
  v
Chunk Mapping（某个切块方案生成的 Chunk 与 Evidence 的对应关系）
  |
  v
Retrieved Chunk
```

这样既可以借鉴 ID-Based Recall，又不会因为 Chunk 重新生成而丢失 Ground Truth。
