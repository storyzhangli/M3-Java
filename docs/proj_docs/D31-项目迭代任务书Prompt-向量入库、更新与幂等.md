## 二、本次功能需求

实现文档切分后的 chunks 向量化、持久化、更新、删除及幂等处理。

1. 将 chunks 通过现有 Embedding 实现向量化，写入 PostgreSQL + pgvector。
2. 建立文档与 chunks 的可靠关联关系，设计稳定 ID 和数据库唯一约束。
3. 同一文档重复导入不得产生重复文档、重复 chunks 或孤儿数据。
4. 文档内容更新时，正确处理旧版本和新版本向量。
5. 删除文档时，清理其关联 chunks 和向量数据。
6. 支持失败重试、部分失败识别及恢复。
7. 分析原文库与向量库不同步风险，设计可执行的补偿和数据核对策略。

**核心验收不是一次写入成功，而是重复操作、失败重试、更新、删除和恢复后数据仍然正确。**

### 2. 稳定 ID 与幂等设计

根据实际仓库设计并实现：

- 稳定的 document ID。
- 稳定的 chunk ID。
- 文档内容指纹或版本标识。
- Chunk 与所属文档的关联关系。
- 数据库唯一约束。
- 重复导入的 Upsert 或等效幂等机制。

设计要求：

1. 同一文档、相同输入重复导入，生成相同业务标识，不产生重复记录。
2. 不同文档即使内容相同，也必须能够正确区分归属。
3. 同一文档内容变化时，能够识别新版本。
4. 相同输入在失败重试时，不生成新的无关 ID。
5. ID 算法应考虑文档来源、文档标识、Chunk 顺序或内容指纹，以及必要的切分版本。
6. 不能只依赖 Java 层先查后插；必须通过数据库唯一约束等机制防止并发重复写入。

如果现有 Spring AI VectorStore 已管理向量表结构，先检查其 ID、Metadata 和删除能力，不得未经验证修改框架管理的表。

### 3. 文档与 Chunk 数据关系

确保能够通过 document ID 查询其全部 chunks，并支持按文档更新和删除。

检查或设计以下数据：

- 文档唯一标识。
- 文档内容指纹及版本。
- Chunk 唯一标识。
- Chunk 所属 document ID。
- Chunk 顺序及必要的切分信息。
- Embedding 向量。
- 入库状态及必要的失败信息。

使用外键、唯一约束或现有可靠机制维护关联关系，避免孤儿数据。

具体表结构沿用仓库已有设计；确需新增表时，先说明用途及与 Spring AI VectorStore 的关系。

### 4. 更新、删除与失败恢复

明确实现以下处理逻辑：

- **新增：** 文档切分、向量化并写入。
- **重复导入：** 识别相同文档和版本，避免重复写入。
- **更新：** 识别文档新版本，保证新旧 chunks 切换正确，不遗留无效向量。
- **删除：** 按文档标识清理关联 chunks 和向量记录。
- **失败重试：** 使用稳定 ID 和幂等写入，重复执行不会产生重复数据。
- **部分失败恢复：** 记录处理阶段及失败状态，能够识别未完成任务并继续恢复。

更新策略应避免先删除旧版本、再因新版本向量化失败而导致文档向量全部丢失。优先采用适合现有项目的事务或版本切换方案。

不得为实现恢复而无条件引入复杂分布式事务框架。

### 5. 原文库与向量库一致性

明确原文存储与向量存储是否属于同一个数据库、同一个事务边界。

必须遵守：

- 数据库本地事务只能保证其事务边界内的数据一致性。
- Embedding 模型调用属于外部操作，不能假设能够与数据库事务原子提交。
- 原文库和向量库属于不同系统时，不能宣称普通数据库事务自动保证跨系统一致性。
- 分析写入成功但状态更新失败、原文更新成功但向量入库失败、删除失败、超时重试等情况。
- 根据现有架构设计状态记录、Outbox / 重试任务、补偿删除或定期数据核对等机制。
- 说明失败状态如何识别、重试次数如何控制、最终失败如何处理，以及如何检测孤儿数据和版本不一致。

优先使用项目已有机制，避免无必要增加新组件。
