## 三、同构副本结论

D31 是与 D30 同构的累计代码库完整副本（D01–D30 全部能力）：

- `PgVectorStoreProperties`（前缀 `app.pgvector`）默认表名 **d31_vector_store**（独立于 d30_vector_store），
  `initializeSchema=true`，`maxDocumentBatchSize=10000`，连接池 5；
- `PgVectorStoreConfiguration` 手动装配：`@Primary` MySQL 数据源 + 非主 `pgVectorDataSource`(Hikari)
  + `pgVectorJdbcTemplate` + `PgVectorStore` Builder（schema/table/dimensions 取 `EmbeddingProperties`，
  COSINE_DISTANCE、HNSW、启动期模型维度断言）。

## 四、框架能力取证（反编译 spring-ai 1.1.8 真实字节码）

- **写入 SQL**：`INSERT INTO <table> (id, content, metadata, embedding) VALUES (?, ?, ?::jsonb, ?)
  ON CONFLICT (id) DO UPDATE SET content=?, metadata=?::jsonb, embedding=?` —— 框架原生 DB 级 Upsert，
  传确定性 UUID 后重复 add 即幂等更新，不产生重复行；
- **删除 SQL**：`DELETE FROM <table> WHERE id=?`，重复删除已不存在的 id 不报错；
- **建表**：`id uuid PRIMARY KEY, content text, metadata json, embedding vector(384)`；
  `convertIdToPgType` 用 `UUID.fromString`，故稳定 chunk ID 必须是合法 UUID；
- **Document Builder**：`Document.builder().id(String).text(String).metadata(Map).build()`，
  doAdd 字节码 offset 53 为 `UUID.fromString`，尊重传入 id，id 为空才随机；
- **Embedding 调用链**：`PgVectorStore.doAdd` → `EmbeddingModel.embed(List<Document>, EmbeddingOptions,
  BatchingStrategy)`，默认方法经 BatchingStrategy 分批后对每批调 `call(EmbeddingRequest)`。
  因此用 `@SpyBean` 包装 EmbeddingModel 并 stub `call(EmbeddingRequest)` 即可在真实 PG/真实模型下注入故障。

## 六、结论

D31 与 D30 同构、技术基线一致，框架原生提供 DB 级 Upsert 与可重复删除；本迭代的工程增量聚焦在
稳定 ID、MySQL 唯一约束、状态机版本切换、失败重试与跨系统核对补偿，而非重复实现向量写入。
