# D31 证据 04：六场景真实集成测试与故障注入

> 取证方式：`DocumentVectorIndexIntegrationTest` 连接真实 PostgreSQL 与真实 MySQL，真实执行。
> 故障仅通过 `@SpyBean` 包装真实 EmbeddingModel 注入异常，不 Mock 数据库，不伪造持久化。

## 一、测试门控与真实性

- 注解 `@EnabledIfPgVector`：以 TCP 探测判断 PG 是否可达；本次数据库可达，11 个测试真实运行，未跳过；
- `@SpringBootTest` 完整加载上下文；`@SpyBean EmbeddingModel` 保留真实 384 输出，仅在指定用例 stub
  `call(EmbeddingRequest)` 注入异常，用完 `reset`；
- 数据隔离：documentId 前缀 `d31vi-`，`@BeforeEach/@AfterEach` 清理 PG 与 MySQL 作用域行。

## 四、故障注入是否真正生效（取证结论）

- 注入点为 EmbeddingModel 的 `call(EmbeddingRequest)`，正是 PgVectorStore 分批后实际调用的方法
  （反编译调用链见证据 01）；
- 真实日志可见故障被触发并进入失败处理：
  `向量写入中断 documentId=d31vi-... processed=0 reason=injected first-attempt failure`；
- 场景 6 用 `doAnswer` 在第 2 次调用抛错、其余 `callRealMethod`，真实出现「部分写入」（1–4 行），
  证明故障发生在真实分批链路中而非整体短路；
- 因 `@SpyBean` 包装的是容器内唯一 EmbeddingModel Bean，PgVectorStore 持有的就是该 spy 引用，
  无需额外 `@TestConfiguration`。
