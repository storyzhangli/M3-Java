# D31 证据 06：跨系统核对与一致性补偿

> 取证方式：以真实数据库为唯一事实来源，核对 MySQL（原文/状态库）与 PG（向量库）；真实集成测试验证。
> 组件：`VectorReconciliationService`；接口：`POST /api/v1/vector-index/reconcile`。

## 一、为什么不用分布式事务

任务书明确不引入分布式事务框架。MySQL 与 PG 各自本地原子，跨系统在崩溃/超时/部分失败下必然出现短暂不一致，
因此采用「状态机 + 核对补偿」最终收敛：

- 写入与版本切换只依赖各库本地事务；
- 核对以真实数据回读为准，差异分类后补偿；
- 补偿动作复用稳定 ID 与框架 Upsert，重复执行安全。

## 二、四类差异（reconcile 真实判定）

| 差异类型 | 判定逻辑 | 补偿动作（非 dryRun） |
| --- | --- | --- |
| 孤儿向量 orphan | PG 有行，但无关联行，或所属任务非活动/已取代 | 按稳定 ID 补偿删除 |
| 缺失向量 missing | 关联行存在但 PG 无对应行 | 用 Outbox 快照幂等重建 |
| 数量不一致 mismatch | 版本级关联数 ≠ PG 实际数 | 归入缺失/孤儿后重建或删除 |
| 卡住任务 stuck | PENDING/INDEXING 且超过 stuckMinutes | recoverStuckTasks 恢复 |

- PG 行读取：`SELECT id, metadata::text` + Jackson 解析，不依赖第二套向量库；
- dryRun 只出报告不动作；非 dryRun 才执行补偿，并记录 `actionsTaken`。

## 三、真实集成测试验证

| 测试 | 制造方式 | 断言 | 结果 |
| --- | --- | --- | --- |
| reconcile_dryRunCleanSystemHasNoIssues | 干净系统 | totalIssues=0、actionsTaken 为空 | 通过 |
| reconcile_detectsOrphansAndCompensatingDeletes | 删除 MySQL 关联与状态，制造 PG 孤儿 | dryRun 报 3 孤儿；非 dryRun 补偿删除后 PG=0 | 通过 |

## 四、卡住任务恢复（recoverStuckTasks）

- 按 `stuckMinutes`（默认 30）扫描 PENDING/INDEXING 行；
- 尊重 `maxAttempts`（默认 5）：达上限跳过并提示人工介入，不无限重试；
- 有 Outbox 快照（document_chunk_index.content）→ 用快照幂等重建；
- 无快照（写入前崩溃）→ 置 FAILED、errorCode=NO_SNAPSHOT，要求重新触发，不伪造成功。

## 五、补偿删除的幂等性

- `deleteVectorsByIds` 走框架 `DELETE ... WHERE id=?`，PG 对已不存在的 id 不报错，重复执行安全；
- 该入口不自动删 MySQL 关联，由核对按差异类型决定是否联动，避免误删。

## 六、结论

跨系统一致性以真实回读 + 分类补偿收敛，孤儿删除、缺失重建、卡住恢复均有真实集成测试支撑；
不引入分布式事务，也不引入第二套向量库，补偿动作天然幂等、可重复执行。
