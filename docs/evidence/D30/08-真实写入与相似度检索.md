# D30 证据 08：真实写入与相似度检索（384 基线，端到端 HTTP）

> 取证方式：真实启动 Spring Boot 应用（端口 8080），经 HTTP 调用三个端点。
> 临时脚本：`http_demo_384.ps1`；应用启动日志：`logs/D30/12-app-run-384.log`；原始输出：`http_demo_out_384.md`。
> 本轮为 384 基线整改后的重新取证，旧的 256 取证输出仅作历史保留，不作为本迭代结论。

## 一、写入前统计

```json
{
  "code": 200,
  "data": { "table": "\"public\".\"d30_vector_store\"", "count": 0 }
}
```

## 二、真实写入 3 条

请求文本（均带 `testRun` 标记，便于严格清理）：

```text
1. postgres pgvector 向量数据库 存储与索引
2. java spring boot 后端服务 开发与配置
3. redis 缓存 会话 设计与过期策略
```

响应：

```json
{ "code": 200, "msg": "success", "data": 3 }
```

`data=3` 表示 3 条文本经 EmbeddingModel 真实向量化为 **384 维** 后写入 `vector(384)` 列。

## 三、真实余弦相似度检索（真实结果）

查询：`pgvector 向量 数据库 索引`，topK=3，threshold=0.0。

```text
排名  文本                                   score                distance
1    postgres pgvector 向量数据库 存储与索引   0.743731826543808    0.25626817
2    java spring boot 后端服务 开发与配置       0.17588162422180176  0.8241184
3    redis 缓存 会话 设计与过期策略             0.05884897708892822  0.941151
```

### 关键核验点

1. **语义相关命中第一**：与查询共享「pgvector/向量/数据库/索引」的文档真实排名第一；
2. **降序正确**：score 严格降序，符合 `<=>` 余弦距离排序；
3. **score + distance ≈ 1**：第一名 `0.743731826543808 + 0.25626817 ≈ 1.0`，
   印证 pgvector 余弦距离到相似度（`1 - distance`）的换算真实生效；
4. **分数区间合理**：所有 score 落在 [0,1]，非人为编造；
5. **维度真实**：若模型仍输出 256 维，写入 `vector(384)` 会直接报维度错误，写入成功即反证一致。

## 四、写入后统计

```json
{ "code": 200,
  "data": { "table": "\"public\".\"d30_vector_store\"", "count": 3 } }
```

count 由 0 真实增长到 3，与写入条数一致。

## 五、维度不匹配的真实拒绝（集成测试）

`PgVectorStoreIntegrationTest.wrongDimensionInsertIsRejected`：
向 `vector(384)` 列原始写入 3 维向量，**断言抛出 DataAccessException**，对应 pgvector
`expected 384 dimensions, not 3` 的 fail-closed 约束，错误维度无法落库。

## 六、取证后清理

- 执行 `http_cleanup_384.py`：`DELETE 3`，回读 `remaining = 0`；
- 停止应用，确认端口 8080 已释放；
- 演示数据按标记严格清理，未触碰任何用户数据。

## 七、结论

真实端到端链路（HTTP → 服务 → 本地 Embedding（float[384]） → pgvector 写入 → 余弦 `<=>` 排序 → 结果回读）
已在 384 基线上实际跑通，排序、相似度换算、行数变化、维度拒绝均有真实数据支撑；
这是「检索成功」的直接证据，而非仅「连接成功」。
