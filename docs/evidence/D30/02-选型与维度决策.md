## 二、维度基线：确定为 384

### 2.1 基线出处（原文可追溯）

任务书 `docs/proj_docs/D30 项目迭代任务书 Prompt｜PostgreSQL + pgvector.md` 第 3.5 节明确记载：

> - `EmbeddingProperties` 默认维度为 256。
> - `LocalHashingEmbeddingModel` 是基于 signed feature hashing 的词面向量模型。
> - D29 的部分证据记录了 256 维配置。
> - **当前环境上下文中另有本地 Embedding 384 维的配置要求。**
>
> 因此，**256 与 384 之间存在待核实差异**。

并规定：若采用 384，必须确保模型真实输出 384，同步模型配置、向量校验、元数据、vectorSpaceId 与 DDL，
并通过测试证明输出维度与数据库字段一致，**不得仅将数据库字段修改为 VECTOR(384)**。

**本轮按环境基线统一为 384，并完成上述全部同步与验证。**

### 2.2 整改前 256 结论的错误归因（如实记录）

整改前判定为「384 在仓库内不存在可落地引用」，直接原因是**取证范围错误**：
当时的 `384` 全目录检索只覆盖了 `M3-Java\D30` 模块目录，**未覆盖 `docs/proj_docs` 下的任务书本身**，
而任务书正是「384 配置要求」的载体。该结论已撤回，不作为任何技术依据。

### 2.3 为什么 384 是「真实输出」而非「只改配置」

`LocalHashingEmbeddingModel` 的维度即特征哈希的桶数量，由配置驱动：

```java
this.dimensions = properties.getDimensions();   // 构造期读取
this.embeddingDimensions.set(dimensions);       // 同步父类维度缓存

private float[] embedSingle(String text) {
    float[] vector = new float[dimensions];     // 真实分配 384 长度数组
    for (String feature : TextFeatureExtractor.extract(text)) {
        int bucket = FeatureHasher.bucket(feature, dimensions);   // 桶下标 0..383
        vector[bucket] += FeatureHasher.sign(feature);
    }
    l2Normalize(vector);
    return vector;
}
```

因此把维度统一为 384 后，模型**真实输出 `float[384]`**（非填充、非截断），
并由单测 `LocalHashingEmbeddingModelTest` 断言 `vector.length == 384`。

## 三、五层一致性（统一后的真实状态）

| 层 | 位置 | 真实值 |
| --- | --- | --- |
| 配置默认值 | `EmbeddingProperties.dimensions` | 384 |
| 运行配置 | `application.yml` `app.ai.embedding.dimensions` | `${EMBEDDING_DIMENSIONS:384}` |
| 模型真实输出 | `LocalHashingEmbeddingModel.embed()` | `float[384]`（测试断言） |
| 向量空间标识 | `vectorSpaceId` | `local\|local-hashing-embedding\|local-v1\|384` |
| 正式表 DDL | `public.d30_vector_store.embedding` | `vector(384)`（psql 独立回读） |
| 集成测试 | `PgVectorStoreIntegrationTest` | 断言 `vector(384)` |

启动期仍保留 fail-closed 断言：`EmbeddingModel.dimensions() != 配置维度` 时抛
`IllegalStateException`，禁止创建向量表。

## 四、向量空间兼容性口径

```text
vectorSpaceId = provider | model | modelVersion | dimensions
默认：local | local-hashing-embedding | local-v1 | 384
```

- 异维度：`DIMENSION_MISMATCH`；
- 同维度异模型：`MODEL_SPACE_MISMATCH`；
- 完全一致：`COMPATIBLE`。

维度相同不代表空间兼容，384 与 256 两套向量**永不可混写**。

## 五、从 256 迁移到 384 的真实操作（已完成）

前置核验：迁移前 `public.d30_vector_store` **行数为 0**、`embedding = vector(256)`（见证据 12）。
因 pgvector 不支持不同维度间的直接类型转换，采用干净重建：

1. `DROP TABLE public.d30_vector_store;`（0 行，无数据损失；同时移除旧 HNSW 索引）；
2. 应用启动 `initializeSchema` 自动重建为 `vector(384)` 并创建 HNSW（`vector_cosine_ops`）；
3. 独立 psql 回读确认 `vector(384)` + HNSW（见证据 07）。

## 六、若未来需要再次切换维度

1. 先确认新模型真实输出维度，禁止只改 DDL；
2. 以新 `vectorSpaceId`（新 modelVersion 或新维度）标识新空间，不与旧空间混写；
3. 新建对应维度表与 HNSW 索引，对存量内容**重新 Embedding** 后导入；
4. 切换 `indexVersion`，旧空间按策略保留或下线。

## 七、结论

向量库唯一选型仍为 pgvector；维度基线统一为 **384**，模型、配置、元数据、vectorSpaceId、正式表 DDL
五个层面全部一致，并有真实测试与独立 psql 回读佐证；256 旧结论已撤回并记录错误归因。
