# D30 证据 02：向量库选型与 256/384 维度决策

> 决策原则：先核验真实环境与模型真实输出，再定正式表 DDL；禁止「只改库不同步模型」。

## 一、向量库选型复核

| 检查项 | 结论 | 依据 |
| --- | --- | --- |
| 仓库内是否已有向量库 / VectorStore | 无 | 全目录无 VectorStore 实现，模块 POM 无向量库依赖 |
| 是否引入第二套向量库 | 否 | 不引入 Milvus / Elasticsearch / Redis Vector 等 |
| 唯一向量库 | PostgreSQL + pgvector | 任务书默认 + 环境已具备 pgvector 0.8.7 |
| MySQL 职责 | 保持主业务库不变 | 独立 PG 数据源，不替换 MySQL |

结论：在无现成向量存储的前提下，**pgvector 为唯一向量库**，且全工程仅维护这一套，不产生多套并存。

## 二、维度唯一决策：256

### 2.1 决策必须先核验模型真实输出

正式表 `vector(N)` 的 N 不是拍脑袋取值，必须与 `EmbeddingModel` 真实输出维度一致。
本轮在定 DDL 前做了三项核验：

1. **模型真实输出**：本地哈希 Embedding（D29 已验证）真实输出为 256 维，`EmbeddingModel.dimensions()=256`。
2. **配置默认值**：`EmbeddingProperties` 内置默认 `dimensions=256`。
3. **全目录检索**：对 D30 全目录执行 `384` 关键字检索，**零命中**
   ——任务书提到的「外部 384 维配置要求」在当前仓库内不存在任何引用，不构成可落地的真实约束。

### 2.2 决策结论

| 维度候选 | 是否采纳 | 理由 |
| --- | --- | --- |
| 256 | **采纳（唯一决策）** | 与模型真实输出、配置默认值、真实测试三者一致 |
| 384 | 不采纳 | 仓库无任何 384 引用，模型并不输出 384，强行建表会维度不符 |

### 2.3 代码层面的强制一致性

`PgVectorStoreConfiguration` 在构造 `PgVectorStore` 时显式断言：

```java
int modelDimensions = embeddingModel.dimensions();
if (modelDimensions != dimensions) {
    throw new IllegalStateException("EmbeddingModel 维度与配置维度不一致……禁止创建向量表");
}
```

这保证「模型维度」与「表维度」在启动期被强制对齐，维度不符直接 fail-closed，而不是带病建表。

## 三、维度相同 ≠ 兼容：vectorSpaceId 权威口径

沿用 D29 口径，向量空间标识为：

```text
vectorSpaceId = provider | model | modelVersion | dimensions
默认本地：local | local-hashing-embedding | local-v1 | 256
```

- 异维度写入：`DIMENSION_MISMATCH`；
- 同维度但模型空间不同：`MODEL_SPACE_MISMATCH`；
- 完全一致：`COMPATIBLE`。

## 四、若未来确需 384 维的兼容方案

当前不实现，但给出明确迁移路径（写进正式文档）：

1. 由真实模型先产出 384 维，确认 `EmbeddingModel.dimensions()=384`；
2. 以新 `vectorSpaceId`（含新 modelVersion）标识新空间，**不与 256 数据混写**；
3. 新建 `vector(384)` 表与 HNSW 索引，对存量内容**重新 Embedding** 后导入；
4. 切换 `indexVersion`，旧 256 空间按策略保留或下线。

## 五、结论

向量库唯一选型为 pgvector；维度唯一决策为 **256**，且该决策由模型真实输出驱动、有代码断言兜底、
有全目录零命中 384 的证据支撑，不存在「只改库不同步模型」的情况。
