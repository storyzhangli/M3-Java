# D30 证据 12：维度基线整改记录（256 → 384）

> 本文记录整改的触发原因、根因、实际动作与复测结果，作为本轮最重要的可追溯证据。
> 结论：维度基线已统一为 **384**，模型、配置、元数据、vectorSpaceId、正式表 DDL 全部一致。

## 一、问题（用户判定）

此前提供的强制环境基线为**本地 Embedding 384 维**，而 D30 实际落地为 256：

| 项目 | 整改前实际值 |
| --- | --- |
| `LocalHashingEmbeddingModel` | 256 维 |
| `EmbeddingProperties` | 256 维 |
| `PgVectorStore` 配置 | 256 维 |
| PostgreSQL 正式表 | `vector(256)` |
| 集成测试 | 验证 `vector(256)` |

文档当时以「D29 已验证模型实际输出 256 维」解释 256 的选择，但该解释不能覆盖后续明确的 384 基线。
判定：存在硬性配置冲突，必须统一真实模型输出、环境基线和数据库表维度。

## 二、根因（如实归因到取证方法）

整改前得出「384 在仓库内无引用」的结论，直接原因是**取证范围错误**：

- 当时的 `384` 检索**只覆盖 `M3-Java\D30` 模块目录**；
- **未覆盖 `docs/proj_docs/D30 项目迭代任务书 Prompt｜PostgreSQL + pgvector.md`**；
- 而任务书 3.5 节原文正是：「**当前环境上下文中另有本地 Embedding 384 维的配置要求。**」
  并明确要求如采用 384 需同步模型、校验、元数据、vectorSpaceId 与 DDL，且不得只改数据库字段。

因此「零命中」是扫描边界的产物，不是真实结论；该结论已撤回。整改后检索确认：
384 要求在任务书中有明确原文，属真实基线要求。

| 序号 | 文件 | 修改 |

模型维度是特征哈希桶数、由配置驱动，因此修改后是**真实输出 `float[384]`**，不是填充/截断，也不是只改 DDL。

## 四、数据库迁移（0 行前提下干净重建）

迁移前独立核验（psql，真实输出）：

```text
 row_count
-----------
         0

 embedding_type
----------------
 vector(256)
```

pgvector 不支持不同维度间的直接类型转换（256→384 会报维度错误），故执行：

```sql
DROP TABLE public.d30_vector_store;
```

- 该表由本轮迭代创建、行数为 0，**无数据损失**；
- 旧 HNSW 索引随表删除；
- 应用启动 `initializeSchema` 重建为 `vector(384)` + HNSW(`vector_cosine_ops`)。

迁移后独立回读：`embedding = vector(384)`，索引 `d30_vector_store_index hnsw (embedding vector_cosine_ops)`（证据 07）。
